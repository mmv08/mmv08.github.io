Chapter 15: How Monad Differs From Ethereum

monad-client-book/15-how-monad-differs-from-ethereum.md View source →

Most of this book explained Monad on its own terms. That is the right way to learn a codebase, but it leaves one practical question open: which parts still match Ethereum, and which parts differ for structural reasons? Now that the internal mechanics are on the table, we can answer that question without flattening everything into short labels.

Why This Chapter Matters#

If you compare Monad to Ethereum too early, you lose the Monad-specific invariants. If you compare them too late, you miss the practical intuition many engineers already have from Ethereum. The goal here is precision, not a broad comparison.

15.1 Start With What Does Not Change#

Monad is still working with the core execution objects Ethereum developers already know.

An account is one entry per address. It carries a balance in native currency, a nonce that counts outgoing transactions, optional contract code, and per-contract storage. Monad keeps the same Ethereum account semantics.

An Ethereum-style transaction is a signed payload that transfers value, deploys code, or calls a contract. It uses the familiar RLP-encoded shape. RLP means Recursive Length Prefix, Ethereum’s compact encoding for nested byte strings and lists.

EVM bytecode is the stack-based instruction format compiled contracts run on. Solidity is the most common high-level language that compiles down to that bytecode. Monad also keeps the usual receipts (per-transaction execution summaries with status, gas used, and emitted logs), logs (indexed contract events for off-chain consumers), and familiar JSON-RPC method names. JSON-RPC is the HTTP+JSON request protocol Ethereum clients expose to wallets and tools.

That is why “Ethereum-compatible” is the right starting phrase. If you deploy an ordinary Solidity contract, the first model should still be “same EVM world.” The biggest differences are around ordering, execution timing, validator-set plumbing, stale-state safety rules, and gas accounting in current Monad revisions.

The compatibility boundary also includes hashing. Consensus-side object identity is Blake3-shaped in this codebase, while EVM transaction hashes, addresses, storage slots, and block-header-style execution hashes remain Ethereum or Keccak-shaped where Ethereum semantics require them. So “Ethereum-compatible” should not be over-read as “every surrounding hash in the client is Keccak.”

15.2 Both Systems Split Consensus And Execution, But Monad Pushes The Split Further#

Modern Ethereum already has a consensus client and an execution client. So the existence of a split is not the difference. The deeper difference is that Ethereum executes the proposed block in the ordinary block-production cadence, while Monad orders blocks first and lets execution trail behind. That second step is the architectural leap that drives many other differences.

15.3 Delayed Execution Is The Biggest Structural Difference#

Ethereum’s short mental model is “propose block N, execute block N, verify the resulting transition for block N.” Monad’s better mental model is “order block N, keep consensus moving, execute block N later, and carry finalized execution outputs for older work in later blocks.” That is why Monad block headers carry fields such as execution_inputs and delayed_execution_results. Those fields are the visible shape of delayed execution.

If you want the canonical worked timeline, go back to Chapter 16. In this checkout, the examples in the book assume the current runtime wiring of EXECUTION_DELAY = 3.

15.4 Coherency Matters More In Monad Because Ordering Sees Stale State#

Ethereum readers often use “valid” to mean almost everything. Monad needs a sharper word: “coherent.” Because execution is delayed, a block can be structurally valid but not yet coherent relative to the state knowledge the node currently has. That is why Monad consensus distinguishes invalid block, incoherent block, and missing ancestor more aggressively than many Ethereum mental models do.

15.5 Reserve Balance Exists Because Ordering Happens Before Fresh Execution#

Reserve balance is one of the clearest Monad-only rules.

Ethereum#

Ethereum execution sees the state it is about to mutate. It does not need a special delayed-window reserve rule to protect against stale-state overbooking during ordering.

Monad#

Monad leaders and validators order new transactions while execution is lagging. So they need protection against promising more spend than the stale ordering window can safely justify. That is what reserve balance provides. It is not just a mempool heuristic — it is a cross-layer safety rule, with Rust-side policy checks during ordering and C++ execution enforcement when execution catches up.

15.6 Reserve-Balance Enforcement And Reserve-Balance Precompile Exposure Are Different#

These two ideas must stay separate.

ConceptCurrent gate in codeMeaning
reserve-balance enforcementMONAD_FOUR+validation and execution enforce the rule
reserve-balance precompile exposureMONAD_NINE+contracts and tools can query reserve-balance information through the precompile

If you merge those into one sentence, the revision story becomes wrong.

15.7 Monad Blocks Carry More Cross-Time Bookkeeping Than Ethereum Blocks#

An Ethereum block mainly carries the current payload and the current execution result. A Monad block can also carry the current execution request for this ordered block plus delayed execution results for older blocks. That is why later Monad blocks may help finalize earlier execution work.

So a useful comparison is this: Ethereum block N is mostly about executing block N, while Monad block N is about ordering block N and possibly carrying finalized execution information for older delayed work. That bookkeeping requirement is a direct consequence of delayed execution.

15.8 Validator-Set Plumbing Lives Closer To Execution In Monad#

Ethereum validators stake through execution-side objects like the deposit contract — a specific contract at a fixed address on Ethereum’s execution layer that receives staking deposits and emits events the beacon chain reads — but active validator accounting and duties are much more consensus-side from the reader’s point of view.

Monad moves validator-set plumbing closer to execution state. In the current code, staking is exposed as a protocol precompile from MONAD_FOUR, staking state lives in execution-owned storage, and consensus reads validator-set data from execution state through triedb-backed paths. That is why read_valset(...) and its boundary-delay behavior matter so much. In Monad, validator-set transitions are not only a consensus-local story — they are tightly coupled to execution-visible staking state.

15.9 Monad Makes Protocol-Owned Execution Work More Explicit#

Ethereum has protocol-managed effects too. Monad makes more of that work explicit as deterministic system transactions that both sides of the boundary must derive the same way. That is especially visible around rewards, snapshots, and epoch changes. The point is not cosmetic — it keeps protocol-owned execution work visible, reviewable, and testable as ordered transaction-like objects.

15.10 Gas Accounting Needs Very Careful Wording#

This is one of the easiest places to be imprecise.

On-Chain Monad Transaction Execution#

In current Monad execution behavior, the Monad-specific transaction gas path makes a different choice from Ethereum’s familiar refund-heavy model. The execution tests show that in Monad revisions starting from MONAD_ONE, gas refunds are effectively zero in the Monad path.

So the full gas limit is what matters economically. The practical consequence is that oversized gas limits are more expensive than many Ethereum developers expect. That lines up with delayed execution’s need to reason conservatively about gas obligation up front.

Hosted eth_call Is Not The Same Thing As On-Chain Fee Charging#

The caveat is important. Hosted eth_call uses the same execution library, but it is still a local simulation surface. It does not mutate chain state, it does not include a transaction in a canonical block, and it does not charge actual network fees.

So the precise statement is this: on-chain Monad transaction accounting follows Monad revision rules during real block execution, and hosted eth_call does not charge fees.

The top-level hosted result still reports actual gas used. Traced final call frames can still report gas_used equal to the gas limit because refunds are zero in current Monad revisions. That distinction matters because “the same execution library is used” does not mean “RPC simulation and block inclusion are economically identical events.”

15.11 Protocol Precompiles Are Stricter Than Ordinary Contracts#

Staking in Monad is not just a normal user contract at a special address. It is a protocol precompile. That matters because the entry path in monad_precompiles.cpp enforces precompile-specific call semantics.

The important model is that it looks contract-like from the outside, but it behaves like protocol machinery, not like an arbitrary deployed contract. That is why wording such as “staking contract” is directionally useful but incomplete. The more accurate phrasing is “staking precompile with protocol-owned call semantics.”

15.12 Monad’s Fee Header Carries More State Than Ethereum’s Familiar Default Picture#

Ethereum readers are used to a single baseFeePerGas field. Monad headers currently carry base_fee, base_fee_trend, and base_fee_moment. You do not need the full fee equation here — the important point is simpler: Monad’s current fee-market control plane carries more explicit fee-state than Ethereum’s most familiar one-field mental model.

15.14 The Right Final Comparison#

If you want one precise sentence, use this: Monad keeps the EVM world that Ethereum developers recognize, but changes the ordering and execution relationship so deeply that several surrounding rules — especially coherency, reserve balance, validator-set reads, and gas accounting — have to change with it. That is the right high-level comparison after reading the whole book.

15.15 Architecture, Current Code, Current Caveat#

Architecture Monad keeps the EVM execution world but changes the ordering/execution relationship deeply enough that surrounding rules have to change with it.

Current code Delayed execution, reserve-balance enforcement, execution-backed validator reads, richer fee-header state, and the Blake3-versus-Keccak boundary are all visible directly in the checked-out implementation.

Current caveat Hosted eth_call shares Monad execution rules underneath, but its user-visible outputs are not identical to block inclusion: the top-level result still reports actual gas used, while traced final call frames can still report gas_used equal to the gas limit because refunds are zero.

What To Remember#

  • Monad keeps the familiar EVM account, transaction, receipt, log, and JSON-RPC world.
  • The structural difference is delayed execution: consensus orders first, execution catches up later.
  • Delayed execution makes coherency, reserve balance, delayed results, and read-surface freshness first-class concepts.
  • Validator-set plumbing is execution-backed and read through narrow triedb-backed paths.
  • System transactions make protocol-owned execution work explicit.
  • Current Monad gas behavior and hosted eth_call reporting should not be collapsed into one sentence.
  • Protocol precompiles are stricter than ordinary contracts.
  • Ethereum compatibility does not mean every surrounding consensus, storage, or hashing rule is Ethereum-shaped.
