Appendix: Glossary, Timelines, and Reading Maps

This appendix is the compact reference companion to the main chapters.

Use it when you need:

  • the one delayed-execution timeline the whole book assumes
  • a quick refresher on clocks, IDs, and freshness words
  • a global glossary
  • function-level code navigation maps

Why This Appendix Exists#

The main chapters teach the system in order.

That is good for first understanding. It is less good when you later want to answer a narrow question such as:

  • what exactly is the difference between block_round and proposal_round?
  • which surface answers eth_getBalance?
  • where does sync decide it is safe to go live?
  • which functions should I open first for proposal handling?

This appendix is the fast answer layer.

Source links in this appendix are pinned to the reviewed monad-bft and monad commits for this edition.

The Canonical Delayed-Execution Timeline#

This is the single most important timeline in the whole book.

The current monad-node wiring uses:

  • EXECUTION_DELAY = 3

The exact mechanics are spread across consensus, execution, txpool, and sync code. The table below is the compact version.

High-Level Picture#

Ordered blockWhat the block means immediatelyWhat later blocks do with it
Nconsensus orders the blockexecution for N completes later
N+1chain ordering advances againexecution is still catching up
N+2validators may still reason over a lagged execution viewstale-state safety rules still matter
N+3delayed results for older work such as N can now be carried and checkedexecution validates those delayed results against canonical earlier block history

The Same Picture In System Terms#

TimeConsensus sideExecution sideWhy it matters
block N is orderedSeqNum(N) exists nowexecution of N is not yet the newest visible resultordering and execution are intentionally split
blocks N+1 and N+2 are orderedmore consensus history accumulatesordering still sees a lagged execution statereserve balance and coherency checks matter
block N+3 is ordereda later header can carry delayed results for older workexecution can now validate delayed results for N against canonical block historydelayed results are not standalone blobs

What This Timeline Explains#

If this table clicks, these later design choices become easier to explain:

  • a block can be valid but not yet coherent
  • block headers carry execution_inputs
  • later block headers also carry delayed_execution_results
  • state sync targets a delayed execution anchor rather than an arbitrary tip
  • reserve balance exists because ordering sees stale state
  • “latest ordered block” and “latest executed state” are different questions

Freshness And Read Surfaces Cheat Sheet#

The question “what is latest?” is underspecified in Monad.

Ask two questions instead:

  • latest according to which subsystem?
  • latest from which storage or live-output surface?

Freshness Words#

WordShort meaningTypical place it appears
proposednewest observed headledger head marker, triedb metadata, event stream, RPC
votedstronger intermediate headledger head marker, triedb metadata, event stream
finalizeddurable committed anchorledger head marker, triedb metadata, event stream, restart logic
verifiedexecution outputs and state root have been included in a finalized later blockexecution events

verified is intentionally listed with a narrower “typical place.” It is part of the execution-event vocabulary, not another ledger head marker beside proposed, voted, and finalized.

Global Glossary#

Consensus Terms#

round
One consensus attempt. A round can end with a QC or with a timeout path.

seq_num
The consensus-side block height.

epoch
A validator-set era. Epoch activation is scheduled in round-space, not by block height alone.

block_round
The round in which a block was first authored. Stored as a field on the block header itself.

proposal_round
The round in which the current proposal message is being sent. Stored as a field on the proposal message, not on the header. On the happy path proposal_round == block_round; on recovery paths (reproposals) they can diverge.

QC
QuorumCertificate: threshold proof that enough stake signed the same vote statement.

TC
TimeoutCertificate: threshold proof that enough stake timed out the same round, together with recovery context.

NEC
NoEndorsementCertificate: threshold proof that enough stake refused endorsement of the same recovered tip.

FPC
FreshProposalCertificate: fresh-proposal authority. In current code this is an enum that can carry Nec(...) or NoTip(...).

high certificate
The current best round-ending certificate held by the pacemaker. It can be QC-backed or TC-backed.

high extend
The best extension point carried by a timeout certificate. This is what recovery logic later tries to reuse or replace.

committable
A block that satisfies the protocol’s certified parent-child relationship for commit. This is not identical to “coherent.”

Validity Terms#

valid
Structurally and cryptographically acceptable.

coherent
Valid and consistent with the chain and delayed-execution state context currently visible to the node.

missing ancestor
The block may be fine, but local ancestry is incomplete.

lagging state
The node’s execution-side state is too far behind to safely participate as live.

Restart And Sync Terms#

forkpoint
The restart anchor: committed root plus high certificate plus nearby validator context.

block sync
Fetch missing consensus blocks and ancestry.

state sync
Fetch recent execution state so the node does not replay everything from genesis.

delayed anchor
The execution-side target around root_seq_num - execution_delay used in sync readiness checks.

Storage And Read-Surface Terms#

triedb / MonadDB
The retained recent execution database.

event ring
The freshest execution-event stream. Good for live subscriptions, not for durable replay.

archive
Older block-oriented history such as old blocks, receipts, traces, and indexes. Not a general historical world-state engine.

WAL
Write-ahead log of node input events for replay and debugging.

verified Execution-event state meaning the execution outputs and state root for a block have been included in a finalized later block. ExecEventsBuffer ignores this state because its head trackers are proposed, voted, and finalized heights.

Networking Terms#

WireAuth
Authenticated UDP session layer with replay filtering and cookie-based anti-spoofing defenses.

LeanUDP
Direct-message fragmentation and reassembly over UDP.

EMA
Exponential moving average. Used in peer-scoring logic to smooth noisy recent behavior over time.

When To Re-Read This Appendix#

Come back here when:

  • Chapter 3 recovery objects start to blur together
  • Chapter 5 sync uses the delayed anchor and you want the big picture again
  • Chapter 8 or 12 makes you ask “latest according to which surface?”
  • Chapter 9 makes you ask why txpool randomness is acceptable
  • Chapter 15 makes you compare Monad gas and stale-state behavior to Ethereum

The appendix is not meant to replace the main chapters. It is a quick refresher for material covered in detail elsewhere.
