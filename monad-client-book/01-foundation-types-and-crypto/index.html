Chapter 1: Foundation — Types and Cryptography

monad-client-book/01-foundation-types-and-crypto.md View source →

Before reading consensus behavior, we need the smallest nouns the rest of the code is written in.

This chapter covers:

  • the main clocks
  • typed identities
  • stake accounting
  • hashing
  • signing domains
  • signature roles
  • bounded decode helpers

These are not “small implementation details.” They are the grammar the rest of the client speaks.

Why Typed Foundations Matter#

Consensus code becomes hard to trust when it passes raw integers and raw byte arrays everywhere.

Monad avoids a lot of that ambiguity by using typed wrappers:

  • Round instead of a naked u64
  • SeqNum instead of “some height-like number”
  • Epoch instead of “current validator era, probably”
  • BlockId instead of “32 bytes that happen to be a block hash”
  • NodeId instead of “whatever key happened to sign this thing”

That choice matters because the code is full of places where the numbers are all small, integer-shaped, and easy to confuse. The types exist to make those confusions harder to express.

Why This Chapter Matters#

Later chapters only become comfortable once these small distinctions become clearly important.

For example:

  • the pacemaker can only work if Round and SeqNum stay separate
  • certificate verification only makes sense if validator identity and certificate key stay separate
  • replay defense only works if message kinds have distinct signing domains
  • protocol decode is only safe if length and integer bounds are enforced early

So the point of this chapter is not just to meet the types. It is to see what bug each type is preventing.

Read the chapter as a short ladder. Clocks locate a statement in protocol time. Identities say which object or validator the statement is about. Stake says how much weight the statement carries. Hashes make objects nameable. Signing domains make signatures non-reusable across message kinds. Decode bounds keep hostile input from becoming unbounded work. Later consensus code combines those pieces over and over.

1.1 The Three Main Clocks#

The most important types in this chapter are the three clocks introduced in the introduction.

TypeWhat it meansCore question it answers
Roundone consensus attemptwhich consensus attempt are we on?
SeqNumordered consensus block heightwhich block in the ordered chain is this?
Epochvalidator-set erawhich validator set is allowed to act here?

The source makes those distinctions real types, not comments on integers. Abridged from monad-types/src/lib.rs:

pub struct Round(pub u64);

impl Round {
    pub fn immediately_follows(self, previous_round: Self) -> bool {
        previous_round
            .as_u64()
            .checked_add(1)
            .is_some_and(|next_round| next_round == self.as_u64())
    }
}

pub struct Epoch(pub u64);
pub struct SeqNum(pub u64);
pub struct BlockId(pub Hash);

The type system carries the vocabulary. A round can immediately follow another round, but it cannot be silently passed where a sequence number, epoch, or block ID is expected.

Round#

Round is the pacemaker’s clock, and a round is one attempt to advance consensus. A happy round might produce a proposal, votes, and a QC (quorum certificate: an aggregate signature proving that enough stake voted for the same block, introduced properly in Chapter 3). An unhappy round might instead produce timeouts, a TC (timeout certificate: an aggregate signature proving that enough stake gave up on this round, also detailed in Chapter 3), and recovery logic.

So the right question for Round is “which attempt is consensus on?”, not “which block number is this?”

SeqNum#

SeqNum is the ordered chain height. It is the number closest to block.number in an Ethereum developer’s mental model, but it still belongs to the consensus side of the client. The simplest invariant is that parent and child blocks differ by exactly one SeqNum.

Epoch#

Epoch is the validator-set era. Consensus needs epochs because stake accounting only makes sense if honest nodes agree on which validator set is active while a given round is being processed.

Later chapters will show three separate steps: boundary blocks lock epochs in block-space, EpochManager schedules activation in round-space, and the new epoch becomes active only when that scheduled round arrives. Keeping those steps separate makes the later code easier to follow.

1.2 Why Epoch Starts At 1#

This looks small, but it is the kind of detail that causes confusion later if it is not said plainly.

In current code, GENESIS_ROUND = 0, GENESIS_SEQ_NUM = 0, and the synthetic genesis QC anchors epoch 1. So the useful rule is that rounds and sequence numbers begin at 0, while the first live validator era is epoch 1. A reader should not assume every integer-like protocol clock shares the same zero point.

1.3 Boundary Blocks And Locked Epochs#

Some sequence numbers are boundary blocks: they sit at the end of an epoch-sized block interval.

Boundary blocks matter because they lock the validator information for the next epoch. The important distinction is that the boundary block still belongs to the current epoch even though it locks the next one.

Example with epoch_length = 4:

SeqNumCurrent epochBoundary block?Locked epoch
01non/a
11non/a
21non/a
31yes2

The three mistakes to avoid are:

  1. assuming epoch numbering starts at 0
  2. assuming a boundary block belongs to the next epoch
  3. assuming “next epoch locked” and “next epoch active” are the same moment

Only the first two are type-level mistakes. The third becomes a lifecycle mistake in Chapter 2.

SeqNum also carries the epoch-boundary math that later chapters rely on:

impl SeqNum {
    pub fn is_boundary_block(&self, epoch_length: SeqNum) -> bool {
        *self % epoch_length == epoch_length - SeqNum(1)
    }

    pub fn get_locked_epoch(&self, epoch_length: SeqNum) -> Epoch {
        assert!(self.is_boundary_block(epoch_length));
        (*self).to_epoch(epoch_length) + Epoch(1)
    }
}

That is the small code shape behind the phrase “boundary blocks lock the next epoch.” The boundary is computed from sequence number, not from the current consensus round.

1.4 Genesis Anchors#

These constants recur everywhere:

pub const GENESIS_SEQ_NUM: SeqNum = SeqNum(0);
pub const GENESIS_ROUND: Round = Round(0);
pub const GENESIS_BLOCK_ID: BlockId = BlockId(Hash([0_u8; 32]));

They matter because restart, safety, timeout ranking, and initial QC construction all need an exact “beginning of history” value.

The point is not that genesis is special. The point is that history begins with precise typed anchors instead of informal sentinel values.

1.5 Stake Is Not A Node Count#

Monad is stake-weighted.

That means questions like:

  • do we have enough votes?
  • is this a supermajority?
  • has the honest threshold been crossed?

are answered over Stake, not over “how many validators signed.”

Stake wraps U256, which is a quiet reminder that these values are protocol-sized and not meant to be casual application counters.

The practical lesson is that duplicate signers do not help, one validator does not get to inflate influence by appearing twice, and stake arithmetic — not signer count — is the real threshold logic.

1.6 Typed Identities#

BlockId#

BlockId is the typed identity of a consensus block header. The wrapper matters because it stops block identity from getting mixed up with arbitrary 32-byte values, body hashes, state roots, or other payload-related hashes that happen to look the same shape.

block_body_id#

block_body_id is a related but different identifier: the hash identity of the body payload. The important invariant is that header identity and body identity are different objects, and block construction checks that the body’s actual ID matches the header’s block_body_id. That split exists so the code can talk separately about which block header is being referred to and which body payload that header is claiming to bind to.

NodeId#

NodeId<P> is the validator identity type. The useful detail is that it is generic over the public-key type, which lets the same higher-level logic work with production key types, mock test key types, and different certificate setups. The reader-level lesson is that NodeId means “who this validator is in protocol terms,” not “whatever key happened to sign this thing.”

1.7 Identity Versus Certificate Key#

Consensus needs two related answers: which validator is this, and which key verifies this validator’s certificate contribution? That is why validator identity and certificate-verification keys are modeled separately. NodeId answers the first question. ValidatorMapping answers the second. This is not extra structure for its own sake; it is the type-level expression of a real protocol distinction.

Later, when you validate a QC, TC, or NEC (no-endorsement certificate: aggregate proof that enough stake refused to endorse a recovered tip, covered in Chapter 3), you need both validator-set membership (for stake accounting) and the certificate key for each signer’s contribution. If those roles are blurred together, certificate validation becomes hard to reason about.

1.8 Hashing#

Hash#

Hash is the shared 32-byte digest type defined in monad-crypto/src/hasher.rs. Its formatting behavior matters more than it first looks: Display prints a full hex string, and Debug wraps that printable form. So when logs abbreviate block IDs or hashes, that is a higher-level formatting choice, not a limitation of the hash type.

Hasher#

The core trait is:

pub trait Hasher: Sized {
    fn new() -> Self;
    fn update(&mut self, data: impl AsRef<[u8]>);
    fn hash(self) -> Hash;
}

Two details matter: update takes anything byte-like, and hash consumes the hasher rather than leaving it reusable.

Global Default: Blake3#

The global alias is:

pub type HasherType = Blake3Hash;

Blake3 is a modern, parallel-friendly cryptographic hash function. In this book, the useful meaning is simpler: it is the 32-byte hash the consensus side defaults to. That means consensus-side object identities are usually Blake3 unless code explicitly says otherwise.

Blake3 Here, Keccak Elsewhere#

The right short rule is that consensus object identity is usually Blake3-shaped, while EVM rules still use Ethereum hashing where Ethereum semantics require it. The EVM is the Ethereum Virtual Machine, the stack-based execution engine that runs smart-contract bytecode. Keccak-256 is the hash Ethereum uses to compute addresses, storage slots, and transaction hashes.

So “which hash does Monad use?” is not one question. It depends on the layer.

1.9 Signing Domains#

Signing domains stop one signature from being replayed as a different statement type.

The Monad codebase makes this explicit with SigningDomain.

At the reader level, the purpose is simple:

  • a vote signature should not be reusable as a timeout signature
  • a timeout signature should not be reusable as a tip signature
  • a no-endorsement signature should not be reusable as a vote

This is the same design instinct as domain separation in other protocols: sign the payload, but sign it under an explicit domain label too. That small choice prevents large classes of accidental signature reuse bugs.

The implementation is deliberately boring and explicit. Abridged from monad-crypto/src/signing_domain.rs:

pub trait SigningDomain {
    const PREFIX: &'static [u8];
}

pub struct ConsensusMessage;
impl SigningDomain for ConsensusMessage {
    const PREFIX: &'static [u8] = b"\x1Amonad/consensus-message/1\n";
}

pub struct Tip;
impl SigningDomain for Tip {
    const PREFIX: &'static [u8] = b"\x0Cmonad/tip/1\n";
}

pub struct Vote;
impl SigningDomain for Vote {
    const PREFIX: &'static [u8] = b"\x0Dmonad/vote/1\n";
}

pub struct Timeout;
impl SigningDomain for Timeout {
    const PREFIX: &'static [u8] = b"\x10monad/timeout/1\n";
}

The important detail is that the domain is chosen at the type level. A vote and a timeout can serialize similar-looking payload fields, but they are signed under different domains.

1.10 Two Signature Roles, Not One#

This distinction is easy to miss, and later consensus types get much easier to read once you keep the two roles separate. Consensus uses two broad signature roles: one outer authorship signature role, and one certificate-style statement signature role.

The reason for the split is that “this node sent a message” and “this validator contributed to a threshold proof” are different claims. A network message needs an author. A QC, TC, or NEC needs many validators signing the same protocol statement. Keeping those roles separate lets the code verify ordinary message authorship without confusing it with stake-weighted certificate evidence.

Outer Signatures#

The outer signature role answers “who sent this network message?” and “who signed this tip as the original block-round leader?” In the generic code, this is the ST side.

As a concrete example, a ProposalMessage carries a signed ConsensusTip, and that outer signature says the original block-round leader authored this tip.

Certificate-Style Statement Signatures#

The certificate-style role answers:

  • which validator voted for this block?
  • which validator timed out this round?
  • which validator refused endorsement of this recovered tip?

These are the signatures that later aggregate into QCs, TCs, and NECs. In the generic code, this is the SCT::SignatureType side.

Aggregates#

Once enough per-validator statement signatures have accumulated, the aggregate SCT object becomes the threshold proof.

That gives the system three layers instead of one:

LayerWhat it proves
outer message signatureone validator sent this message or authored this tip
per-validator protocol statement signatureone validator made one protocol statement
aggregate certificateenough stake signed the same statement

That separation is a conceptual distinction the later consensus chapters rely on.

1.11 Production Intuition#

The current production-shaped intuition lines up with those two roles.

Outer message and tip authorship are secp-shaped — meaning they use secp256k1, the same elliptic-curve signature scheme Ethereum uses for transaction signatures. These signatures are cheap to verify individually, one at a time.

Certificate contributions and aggregates are BLS-shaped — meaning they use BLS (Boneh-Lynn-Shacham) signatures, a scheme whose defining property is that many individual signatures over the same message can be combined into one aggregate signature that proves “all of these validators signed.” This is what makes certificates compact regardless of how many validators contributed.

That is why validator plumbing later needs both a validator identity (by NodeId) and a validator-to-certificate-key mapping. Those questions are related, but they are not the same question.

1.12 Bounded Decode Helpers#

Two helper types do a lot of quiet safety work.

LimitedVec<T, N>#

This is a vector whose decode path is bounded by N.

That prevents one hostile or malformed payload from claiming an absurd list length and forcing the node into unbounded allocation.

BoundedU64<MAX>#

This is the same idea for integer values.

These helpers are not glamorous, but they are part of why protocol-layer decoding is stricter than ordinary application code.

They exist because network-facing code has to assume hostile inputs eventually arrive.

1.13 One Concrete Example That Uses The Whole Chapter#

Suppose a validator says, “I vote for block B in round 17, during epoch 4.” Even that short sentence already depends on most of this chapter:

  • Round(17) says which consensus attempt this statement belongs to
  • Epoch(4) says which validator set is allowed to sign it
  • BlockId(B) says which header is being certified
  • stake weighting decides how much this vote contributes toward a QC
  • domain separation stops the signature from being replayed as a timeout or no-endorsement
  • validator mapping may be needed later to verify the certificate contribution

That is why these types matter. They make small protocol statements unambiguous.

What To Remember#

  • Round, SeqNum, and Epoch are different clocks for different jobs.
  • Epoch begins at 1, while genesis round and sequence number begin at 0.
  • Boundary blocks lock the next epoch; they do not instantly activate it.
  • BlockId and block_body_id are different identities for different objects.
  • NodeId and validator certificate keys are related but distinct roles.
  • Consensus object hashing is usually Blake3; EVM hashing rules still stay Ethereum-shaped where they should.
  • Monad uses separate roles for outer authorship signatures and certificate-style statement signatures.
  • Bounded decode helpers are part of protocol safety, not just style.
