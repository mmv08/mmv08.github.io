Chapter 13: Failure Modes and Defenses

monad-client-book/13-failure-modes-and-defenses.md View source →

Distributed systems become easier to understand once you stop reading only the happy path.

Monad’s code is full of refusal rules. It can refuse stale traffic, bad signatures, invalid blocks, and blocks that are not yet coherent. It can refuse an identity story that does not line up. It can refuse to let queues and caches grow forever. It can also refuse to keep pretending the node is live when execution or state is too far behind.

A coherent block is structurally and cryptographically valid, and also consistent with the chain and delayed-execution state the node currently has. Coherence is stronger than validity, and §13.6 unpacks the distinction. This chapter explains those negative paths one layer at a time.

Why This Chapter Matters#

If you classify a failure precisely, the code stops looking like one large set of “if bad, drop” branches. The important categories are different: invalid, incoherent, missing ancestor, lagging state, bad identity, overloaded local resource, and missing dependency. Those are not synonyms. The client stays understandable largely because it does not collapse them into one generic failure bucket.

That table is the shortest honest map of the negative paths in the system.

13.2 The Code Usually Tries The Narrowest Safe Response#

Monad often takes the smallest response that preserves the invariant. That is why the client distinguishes between actions such as drop, reject, prune, keep-but-do-not-vote, sync, throttle, and degrade.

Those distinctions matter. One bad signer inside a certificate candidate should not necessarily kill the whole round. One missing ancestor should not make the descendant block invalid. One lagging WebSocket client should not poison the event ring for everyone else. The general pattern is: fail cheap when possible, blame the smallest bad thing, preserve the invariant first, and recover second.

13.3 Stale Traffic Is Normal, Not Exceptional#

The network is asynchronous. Old traffic is expected. So the node has to distinguish “too old to matter” from “late but still usable” from “wrong context entirely.”

That logic appears early in the consensus path, before deeper state-machine handling. The point of that prefiltering is to keep the deep consensus code focused on live decisions, not to make stale traffic somebody else’s problem. This is one reason monad-state/src/consensus.rs matters so much: it filters a lot of old noise before it reaches deeper consensus handling.

13.4 Bad Signatures Usually Lead To Narrow Pruning, Not Blanket Failure#

Votes and timeouts are aggregated objects built from many individual signatures. That creates an obvious failure mode: one or more included signatures may be bad. The client handles that narrowly when it can.

Votes#

VoteState::process_vote(...) can:

  1. detect invalid signatures during aggregation
  2. mark those senders as invalid
  3. remove them from the candidate set
  4. continue with the remaining honest stake

Timeouts#

Timeout aggregation follows the same general idea. That is a strong design choice: one bad signer should not stall an otherwise progress-capable round.

13.5 Honest Nodes Also Need Local Safety#

Not every failure comes from the network. A node can also fail by contradicting itself. That is what the consensus Safety logic is for.

It tracks local monotonic markers such as highest_vote, highest_propose, highest_no_endorse, and highest_recovery_request. Those fields are small, but the class of bugs they prevent is large. The important model is that safety logic is not only about checking other validators. It also prevents this validator from producing self-contradictory protocol actions.

13.6 Invalid, Incoherent, And Missing-Ancestor Are Different#

This distinction is central to understanding the blocktree.

Invalid Block#

An invalid block fails structural or cryptographic validation. Examples include malformed contents, wrong signature or leader claim, static block-limit violations, and execution-side block-shape mismatch. The answer is simple: reject it.

Incoherent Block#

An incoherent block may be structurally valid, but the node cannot yet prove that it fits available chain and state context. Because execution is delayed, that is a real category in Monad. The correct response is often to keep the block locally and refuse to vote on it yet. That is a very different action from rejection.

Missing Ancestor#

A third case is that the block may be fine, but local history is incomplete. That calls for block sync, not block rejection. If those three cases blur together, the consensus chapters become much harder to trust.

13.7 Lagging Execution Or State Pushes The Node Toward Catch-Up#

There is a broader failure mode where the node’s execution state is simply too far behind live ordering. In that case, the correct response is not “keep pretending the node is fully live.” The correct response is to transition toward catch-up logic, request missing blocks or state, and later rejoin live consensus safely. The client prefers controlled temporary degradation over unsafe half-live behavior.

13.8 Txpool Refusal Paths Are Their Own Defense Layer#

The txpool is more than a queue. It is also a defense boundary. Its refusal paths include malformed or unsupported transaction structure, reserved system sender on user ingress, restricted system-like behavior on ordinary ingress, nonce or balance mismatch against current state, reserve-balance-aware failure, and future nonces that can be stored but not yet sequenced.

That last category is especially important. The txpool distinguishes between rejecting entirely and keeping but not yet sequencing, which mirrors the invalid-versus-incoherent distinction on the block side.

13.9 Some Defenses Only Exist On The Execution Side#

Consensus is not the only place where blocks or transactions can be refused. Execution-owned validation adds another defense layer: static Monad block validation, delayed execution result validation, Monad-specific transaction validation, reserve-balance enforcement, and precompile call-semantics checks.

That matters because some things that look like “consensus accepted the block” still need to pass execution-side shape and state-transition validation. The two repos are cooperating on one correctness story.

13.10 Network Identity Defenses Happen Below Consensus#

Several important refusal rules live entirely below the consensus engine. Examples include NameRecord validation, pending peer promotion only after ping-or-pong reachability proof, socket-collision handling in discovery, wireauth cookie challenge under load, and wireauth replay filtering on counters.

These rules protect a different invariant: identity, address, and live session state should line up. That is why not every networking drop belongs in a consensus chapter.

13.11 Bounded Structures Are Part Of The Defense Story#

The client also protects itself by refusing unbounded local growth. Examples include bounded recent event buffers, bounded replay windows, bounded WebSocket broadcast channels, bounded queue structures in networking and RPC, and bounded fair-queue allocations. These limits are denial-of-service defenses. A node that accepts infinite local growth is not more correct; it is less robust.

13.12 Live Feeds Fail Differently From Durable Reads#

A live subscription feed and a durable database do not fail the same way. The event-ring path makes that visible.

WebSocket Path#

WebSocket subscriptions close on explicit Gap, on broadcast lag, and on event-server shutdown. That is the right behavior for a live feed: if the server knows the client missed part of the stream, pretending the stream is still continuous would be worse.

Recent Buffers#

ExecEventsBuffer is more permissive. It ignores Gap as an insertion event and keeps buffering whatever later events it does receive. That makes it a useful freshness cache, not a canonical replay log. This is a good example of the system using different failure behavior for live-feed consumers versus a best-effort freshness cache.

13.13 Broken Dependencies Usually Cause Degraded Capability, Not Total Process Failure#

Some failures are not protocol failures at all. They are missing local resources. Typical examples include the txpool bridge being unavailable in monad-rpc, the archive reader being unavailable, the event ring being unavailable, or the eth-call handler being unavailable.

The common response is to degrade the capability graph, not to pretend the process is fully functional. This is why the assembly chapter matters: many apparent bugs are missing-resource situations that the process partially tolerates.

What To Remember#

  • The client usually takes the narrowest safe response: drop, reject, prune, keep-but-do-not-vote, sync, throttle, or degrade.
  • Invalid, incoherent, and missing-ancestor are different states with different responses.
  • Bad signatures inside aggregate candidates can often be pruned without throwing away the whole round.
  • Txpool refusal is a defense layer, not just queue management.
  • Networking identity defenses happen below consensus.
  • Bounded queues, caches, replay windows, and buffers are part of the denial-of-service story.
  • Live feeds fail differently from durable reads, and buffer discontinuity is not itself a durable-data failure.

The next chapter explains how the repos build confidence in these paths through tests, simulation, fixtures, fuzzing, and workflow gates.
