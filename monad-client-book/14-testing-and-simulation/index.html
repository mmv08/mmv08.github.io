Chapter 14: Testing and Simulation

monad-client-book/14-testing-and-simulation.md View source →

Monad is not one program. It is a system split across two repos and several runtime boundaries. So the testing story should never be summarized as “the tests passed.” That sentence hides the important question: which part of the system was pressured, and what kind of failure was that pressure designed to catch? This chapter explains the confidence model across both monad-bft and monad.

Why This Chapter Matters#

If this book teaches architecture but not confidence, it leaves out half the story. A reader needs to know how the consensus side is pressured, how the execution side is pressured, where deterministic simulation stops and fixture-driven compatibility starts, what workflow files expose as automated gates, and what exists mainly as local or targeted tooling.

Once those layers are clear, the codebase is easier to trust.

14.1 There Is No One Perfect Test Layer#

Monad uses a ladder of pressure, not one perfect test framework. Across the two repos, the important layers are unit tests, property-style generated tests, deterministic multi-node simulation, adversarial twins scenarios, seeded randomized schedules, assembled local stacks, fixture-driven Ethereum compatibility suites, targeted C++ execution tests, VM-focused tests and fuzzing, benchmarks, and CI workflows that keep major layers visible.

Three of those words deserve a quick inline definition.

CI stands for continuous integration: an automated system, here GitHub Actions, that runs tests and checks on every pull request and every merge so regressions are caught before humans have to notice. Fuzzing means feeding the code random or adversarial inputs and watching for crashes, panics, or invariant violations. A fixture is a pre-built input bundle, typically JSON, that drives a specific test scenario end-to-end without the test needing to construct the state from scratch.

That is the whole-system picture.

14.2 A Compact Verification Ladder#

That table is a better mental model than imagining one universal test command.

14.3 The monad-bft Confidence Model Starts With Ordinary Rust Tests#

At the bottom, monad-bft still uses ordinary crate-level tests. This is where the repo catches things like serialization round-trips, signature and hashing behavior, queueing and scheduling rules, fee or policy math, and networking helper invariants. Property-style testing also shows up where generated variation buys real confidence, especially around smaller logic-heavy crates. This layer matters because it keeps small rules cheap to change.

14.4 monad-mock-swarm Is The Core Consensus Simulator#

monad-mock-swarm is the heart of the deterministic simulation story. It builds many in-memory nodes and advances them in virtual time. The important architectural point is that it still feels like the production design:

event source -> executor -> MonadState -> commands -> executor -> emitted messages

The environment is mocked; the protocol style is not. That makes it much more valuable than a toy model that only vaguely resembles the client.

What It Is Good For#

monad-mock-swarm is the right tool when you want to pressure safety under complex schedules, liveness under delays, state-machine behavior across multiple nodes, or invariants that only appear once several roles interact.

Abridged from production code. The important detail is that the simulator still drives MonadState through events and commands:

pub fn step_until(
    &mut self,
    until: Duration,
    emitted_messages: &mut Vec<(Duration, LinkMessage<_, _>)>,
) -> Option<(
    Duration,
    MonadEvent<S::SignatureType, S::SignatureCollectionType, S::ExecutionProtocolType>,
)> {
    while let Some((tick, event_type)) = self.peek_event() {
        if tick > until {
            break;
        }

        self.update_rng();
        let event = match event_type {
            SwarmEventType::ExecutorEvent => {
                let executor_event = self.executor.step_until(tick);
                match executor_event {
                    Some(MockExecutorEvent::Event(event)) => {
                        let event_clone = event.lossy_clone();
                        let commands = self.state.update(event);
                        self.executor.exec(commands);
                        (tick, event_clone)
                    }
                    Some(MockExecutorEvent::Send(to, serialized)) => {
                        emitted_messages.push(LinkMessage { from: self.id, to, serialized });
                        continue;
                    }
                    None => continue,
                }
            }
            // timer and inbound-message cases omitted
        };

        return Some(event);
    }
    None
}

That is why the simulator is valuable: it mocks the environment, not the core state-machine contract.

14.5 monad-twins And monad-randomized-tests Push Harder On Bad Schedules#

Two more monad-bft surfaces matter a lot.

monad-twins#

monad-twins is for adversarial cases where one logical validator identity effectively appears in several places at once. It is especially useful for equivocation-like scenarios, partitions, reconnection behavior, and proving that safety does not silently depend on an unrealistically clean network.

monad-randomized-tests#

monad-randomized-tests uses a numeric seed and iterates over registered randomized cases. That is valuable because many consensus failures are not one obvious invariant bug — they are one unfortunate interleaving that a hand-written scenario never happened to cover. The binary also writes tests_results.xml, which makes seeded random runs easier to plug into automation when needed.

Abridged from production code. The important detail is that twins scenarios are data-driven and include expected-failure cases:

const TWIN_DEFAULT_SEED: u64 = 1;

#[test_case("./tests/happy_path.json"; "happy_path")]
#[test_case("./tests/one_twin.json"; "one_twin")]
#[test_case("./tests/one_twin_partition.json"; "one_twin_partition")]
#[test_case("./tests/make_progress.json"; "make_progress")]
fn twins_testing(path: &str) {
    let test_case = read_twins_test::<MonadMessageNoSerSwarm>(path);
    run_twins_test::<_, _, _, MonadMessageNoSerSwarm>(TWIN_DEFAULT_SEED, test_case)
}

#[should_panic]
#[test_case("./tests/too_much_twin.json"; "too_much_twin")]
#[test_case("./tests/too_much_twin_with_big_delay.json"; "too_much_twin_with_big_delay")]
#[test_case("./tests/mal_formed.json"; "mal_formed json")]
fn twins_should_fail_testing(path: &str) {
    let test_case = read_twins_test::<MonadMessageNoSerSwarm>(path);
    run_twins_test::<_, _, _, MonadMessageNoSerSwarm>(TWIN_DEFAULT_SEED, test_case)
}

And randomized tests are registered and replayed by seed:

pub struct RandomizedTest {
    pub name: &'static str,
    pub func: fn(u64),
}

for t in inventory::iter::<RandomizedTest> {
    let start = Instant::now();
    let result = panic::catch_unwind(|| (t.func)(seed));
    results.insert(
        String::from(t.name),
        TestResults {
            pass: result.is_ok(),
            time: start.elapsed(),
        },
    );
}

summarize(seed, results)?; // writes tests_results.xml

That gives bad schedules two important properties: they are adversarial enough to matter, and deterministic enough to reproduce.

14.6 monad-testground And monad-debugger Sit Between Unit Tests And Operations#

monad-testground and monad-debugger are worth calling out separately because they sit in a middle layer.

monad-testground#

This gives you more of a system feel than a tiny unit test, but with less operational weight than a full deployment. It is useful when you want several assembled subsystems, reproducible coordination, and more realism than a narrow isolated test.

monad-debugger#

monad-debugger is a browser-facing or WASM-facing simulation and visualization surface built on the same general simulator ideas. That continuity matters. It is not a separate hidden protocol implementation.

14.7 monad-bft Also Has Fuzzing, Benchmarks, And Workflow Gates#

The public monad-bft workflow set shows which broad layers are currently visible in automation. The workflow names below are the public workflows visible in the source version reviewed here; they are a good map of what this repo exposes in CI here, not a claim that every validation path everywhere is listed.

One reproducibility caveat applies to both repos: workflow files show what this source version exposes as automated gates, not a promise that every gate is reproducible outside Category Labs infrastructure without the same runners, images, caches, and secrets.

rust.yml#

The main Rust workflow currently runs things like:

  • lockfile verification — confirms Cargo.lock is in sync with Cargo.toml
  • unused-dependency linting via cargo shear — a tool that flags crates declared in Cargo.toml but not actually used in code
  • fmt — cargo fmt, the standard Rust code formatter, enforces consistent whitespace and style
  • clippy — Rust’s extensive lint checker, catches common mistakes and anti-patterns beyond what the compiler warns about
  • cargo check — fast compile-only pass that confirms the code type-checks without producing binaries
  • cargo test --release --all-targets --all-features — runs every test in every crate with every feature flag enabled, in release mode
  • docs and doc tests — verifies rustdoc builds and the examples embedded in documentation comments still compile and run
  • wasm check for monad-debugger — confirms the debugger crate still compiles to WASM (WebAssembly, a portable binary format that runs in browsers and other sandboxed hosts) so the browser-facing simulator stays shippable

fuzz.yml#

Fuzzing is separate from the normal Rust gate. The workflow installs cargo-afl — the Rust wrapper around AFL (American Fuzzy Lop), a coverage-guided fuzzer that mutates inputs and watches which code paths they hit — temporarily removes monad-fuzz from the excluded workspace members, and runs a quick fuzz pass. That is good evidence that parser and decoder robustness are treated as their own concern, not as an accidental side effect of normal tests.

benchmarks.yml#

Benchmark comparison runs on pull requests to master. That matters because performance regressions in this client can come from queueing, routing, proposal construction, or storage access — not only from cryptography.

openrpc.yml#

The OpenRPC workflow regenerates RPC documentation, validates it against the meta-schema, and comments diffs on PRs. That is not a protocol-correctness test, but it is still part of the confidence model: the public RPC surface is being checked as an artifact of code changes.

14.8 The Execution Repo Has Its Own Confidence Model#

The execution repo is not only C++ code with a few unit tests. It has several distinct test surfaces that cover different kinds of risk.

14.9 test/ethereum_test Is The Big Compatibility Anchor#

test/ethereum_test is the main execution-compatibility surface in the repo. Its CMakeLists.txt downloads execution-spec-test fixtures, builds monad-ethereum-test, and registers per-fork test suites from homestead through osaka.

That means the execution repo is not only validating hand-written local examples. It is also validating itself against a broad external compatibility corpus. This is the main execution-spec regression suite in the repo.

What This Layer Is Good At#

It is especially good at catching fork-specific EVM behavior mismatches, transaction and blockchain execution regressions, and unexpected incompatibilities with known Ethereum test fixtures. So when you ask “how do we know the execution engine still behaves like the intended EVM family?”, test/ethereum_test is one of the first answers.

Abridged from production code. The important detail is that fixture compatibility is a registered CMake test matrix across forks:

ExternalProject_Add(
  ExecutionSpecTestFixtures
  URL "https://github.com/ethereum/execution-spec-tests/releases/download/v5.4.0/fixtures_develop.tar.gz"
  URL_HASH "SHA256=3e2b02d49fe903eda4fd8caca5cbf0d139c470e97e1de9a85299b1b034f97099"
  CONFIGURE_COMMAND ""
  BUILD_COMMAND ""
  INSTALL_COMMAND "")

add_executable(monad-ethereum-test)
target_link_libraries(monad-ethereum-test PRIVATE
  nlohmann_json::nlohmann_json
  monad_execution
  GTest::gtest)

function(add_ethereum_test)
  set(ONE_VALUE_ARGS FORK)
  cmake_parse_arguments(ADD_ETHEREUM_TEST "" "${ONE_VALUE_ARGS}" "" ${ARGN})
  add_test(NAME ${ADD_ETHEREUM_TEST_FORK}_monad_ethereum_test
           COMMAND monad-ethereum-test
                   --fork ${ADD_ETHEREUM_TEST_FORK}
                   --record-exec-events
                   --gtest_filter=${FILTER})
endfunction()

This is not a few hand-written smoke tests. It is a fixture-driven compatibility surface wired into the execution build.

14.10 Targeted C++ Tests Cover Monad-Specific Execution Rules#

The execution repo also has many narrower C++ test files under category/. Representative areas include category/execution/ethereum/*_test.cpp, category/execution/monad/*_test.cpp, category/execution/monad/staking/test_read_valset.cpp, category/execution/monad/reserve_balance/reserve_balance_contract_test.cpp, category/rpc/monad_executor_test.cpp, and category/mpt/test/*. This layer is where the repo exercises detailed local rules that are too specific for the large fixture suites.

A Few Examples#

  • category/execution/ethereum/execute_transaction_test.cpp checks gas-charging and refund behavior across revisions
  • category/execution/monad/validate_monad_block_test.cpp checks Monad block-shape rules
  • category/execution/monad/staking/test_read_valset.cpp checks before-boundary and in-delay-period validator-set reads
  • category/rpc/monad_executor_test.cpp checks hosted execution behavior such as call results, gas reporting, reserve-balance-related behavior, and trace expectations

That gives a more precise execution-side confidence story than “we have some unit tests.”

14.11 category/rpc/monad_executor_test.cpp Deserves Special Attention#

This one file deserves its own section because it sits exactly on the boundary this book talks about so often: hosted execution inside an RPC-style surface. It tests eth_call-style execution behavior, gas-used and gas-refund reporting, reserve balance behavior under hosted execution, and call-frame and trace expectations.

That makes it a direct bridge between execution internals and RPC-observable semantics. If you change anything around hosted execution or RPC simulation semantics, this is one of the first files to read.

14.12 test_read_valset.cpp Is A Small File With Outsized Importance#

category/execution/monad/staking/test_read_valset.cpp is small, but it covers one of the easiest places for readers to form an incorrect model: how validator-set reads behave before and during the in-epoch delay period.

The tests explicitly check the current epoch before the boundary, the next epoch before the boundary, the current epoch during the delay period, and the next epoch during the delay period. That is exactly the kind of edge case that would be easy to explain too loosely in prose and much harder to get wrong once you have read the test.

14.13 VM Tests Are Their Own Large Surface#

The execution repo also has a substantial test/vm tree, including test/vm/unit, test/vm/blockchain, test/vm/fuzzer, test/vm/compile_benchmarks, test/vm/execution_benchmarks, and test/vm/data/regression_tests. This is not one more folder of miscellaneous tests. It is a separate test surface around the VM itself.

Why This Layer Exists#

The execution repo does not only care that block execution eventually works. It also cares that the VM interpreter and compiler behave correctly, that VM-facing regressions are caught close to the engine, and that performance-sensitive VM paths can be benchmarked or fuzzed directly. That is why the repo also has local scripts such as scripts/vm/test.sh and scripts/vm/fuzzer.sh.

14.14 scripts/test.sh Is The Local Top-Level Execution Entry Point#

The execution repo’s scripts/test.sh is worth mentioning explicitly because many developers will use it first. In the current code, it runs:

  • ctest --output-on-failure --timeout 500 --test-dir build — ctest is CMake’s test runner (the execution repo uses CMake as its C++ build system), which invokes every test registered with add_test(...) in the build configuration
  • pytest-3 --pyargs monad — runs the pytest suite shipped inside the installed monad Python package (pytest is the standard Python testing framework)

with a small conditional skip for certain callgrind or disassembly-heavy tests outside the preferred build configuration. That means the local top-level test path is already a combination of compiled C++ tests and Python-side package or integration-style tests.

14.15 The Execution Repo Also Has Public Workflow Gates#

The current workflow set in monad shows which broad layers are visible in automation.

docker.yaml#

This workflow builds the main build_and_test Docker stage across multiple compilers and build types. That is effectively the broad execution build-and-test gate.

rust.yml#

The execution repo also has its own Rust-facing workflow for Rust subcomponents and Rust-side code-quality stages. That matters because the execution repo is not purely C++ anymore.

code-quality.yml#

This workflow covers formatting, trait-instantiation checks, and clang-tidy-related quality gates.

test-vm.yml#

This workflow focuses on VM tests and VM fuzzing, which is exactly the right shape for a repo where VM behavior deserves dedicated pressure.

So the execution confidence model is larger than local tests. It is local entrypoints plus several public workflow gates, with the same infrastructure caveat as the Rust-side workflows.

14.16 Where To Add Coverage Depends On The Kind Of Change#

If you are changing:

  • small Rust-side consensus logic, start with a crate test or simulation scenario in monad-bft
  • multi-node safety or liveness behavior, reach for monad-mock-swarm, monad-twins, or seeded randomized runs
  • Ethereum execution semantics, start with execution C++ tests and test/ethereum_test
  • Monad-specific execution rules, add targeted category/execution/monad/*_test.cpp coverage
  • hosted execution or eth_call behavior, add or update category/rpc/monad_executor_test.cpp
  • VM compiler or interpreter behavior, add test/vm coverage

That mapping helps you choose the right test surface for the change.

14.17 The Right Whole-System Confidence Model#

If you want one compact mental model, use this: monad-bft proves a lot through deterministic simulation and protocol-shaped Rust tests; monad proves a lot through fixture-driven EVM compatibility suites and targeted C++ tests; the boundary between them is pressured by hosted-execution and RPC-side tests; and both repos keep performance and documentation surfaces visible through dedicated workflows. That is the real confidence story behind the architecture described in the earlier chapters.

Open These Files First#

  • monad-mock-swarm: deterministic multi-node simulation
  • monad-twins: adversarial twins and partition scenarios
  • monad-randomized-tests/src/main.rs: seeded randomized schedules
  • .github/workflows/rust.yml: main Rust gate in monad-bft
  • .github/workflows/fuzz.yml: dedicated fuzz workflow in monad-bft
  • .github/workflows/benchmarks.yml: benchmark comparison workflow
  • .github/workflows/openrpc.yml: RPC documentation generation and validation
  • test/ethereum_test/CMakeLists.txt: execution-spec fixture suite registration across forks
  • test/ethereum_test/src/blockchain_test.cpp: blockchain-fixture execution path
  • test/ethereum_test/src/transaction_test.cpp: transaction-fixture execution path
  • category/rpc/monad_executor_test.cpp: hosted execution, gas semantics, reserve balance, traces
  • category/execution/monad/staking/test_read_valset.cpp: staking-backed validator-set edge cases
  • category/execution/monad/validate_monad_block_test.cpp: Monad block validation
  • category/execution/ethereum/execute_transaction_test.cpp: gas-charging and refund behavior across revisions
  • test/vm: VM-focused test, fuzz, and benchmark tree
  • scripts/test.sh: local top-level execution test entrypoint
  • scripts/vm/test.sh: local VM test entrypoint
  • .github/workflows/docker.yaml: broad build-and-test workflow in the execution repo
  • .github/workflows/code-quality.yml: code-quality workflow in the execution repo
  • .github/workflows/test-vm.yml: VM-specific workflow

What To Remember#

  • Monad’s confidence model is a ladder, not one test command.
  • monad-bft gets a lot of confidence from Rust tests, deterministic simulation, twins scenarios, and seeded randomized schedules.
  • monad gets a lot of confidence from Ethereum fixture suites, targeted C++ tests, VM tests, fuzzing, and benchmarks.
  • Hosted execution and RPC semantics deserve boundary-specific tests such as category/rpc/monad_executor_test.cpp.
  • The right place to add coverage depends on the kind of change.
  • Workflow files show current automated gates, but local reproducibility can depend on matching infrastructure.

The final chapter compares Monad back to Ethereum now that the internal mechanics and confidence model are in view.
