Chapter 3: Consensus Data Structures

monad-client-book/03-consensus-data-structures.md View source →

Chapter 2 explained who is allowed to act.

This chapter explains what those actors actually send.

The main consensus objects are:

  • votes
  • quorum certificates
  • block headers and full blocks
  • tips and proposal messages
  • timeout messages and timeout certificates
  • recovery-side messages
  • fresh-proposal certificates
  • restart objects such as checkpoints

If the previous chapter was about the social structure of consensus, this chapter is about its documents.

Why This Chapter Matters#

Many later functions look intimidating only because they manipulate several proof objects at once. If you can answer four questions about an object — what statement is it making, who signed it, what threshold does it need, and what later object can it become — then the state-machine chapters get much easier.

3.1 Vote#

A vote is the smallest meaningful consensus statement, carrying a block ID, a round, and an epoch. Conceptually, it says, “In epoch E, during round R, I vote for block B.” That is intentionally small: the block carries the richer structure, and the vote carries the smallest statement needed to certify one block for one round.

3.2 QuorumCertificate#

A QC is one vote statement plus enough signatures over that exact vote. So the mental model is simple: the vote is the statement, and the QC is proof that enough stake signed that statement.

Genesis QC#

Consensus needs a starting point, so the code provides a synthetic genesis QC. It anchors the genesis block ID, the genesis round, and epoch 1. That lets the first real block extend a well-defined certified parent instead of special-casing “history starts here” everywhere.

Why The Commit Rule Needs Parent Precision#

The code’s committable-block logic is more precise than the vague phrase “QC on QC.” The useful reader-level version is: a new QC certifies block B; block B itself carries a QC for parent A; and if the child certification has the required next-round relationship to the parent certification, then A becomes committable.

So the key idea is not “some newer QC exists.” It is “a specific certified parent-child relationship exists.” That precision is why the commit rule is safe to automate.

3.3 proposal_round Versus block_round#

This distinction is essential.

block_round#

block_round is the round in which the block was originally authored.

proposal_round#

proposal_round is the round in which the current proposal message is being sent.

Why The Split Exists#

Suppose block B was first proposed in round 10, but recovery later decides B is still the right tip and re-sends it in round 12. Then block_round(B) = 10 while proposal_round = 12. That means the node has to validate two different leader claims: was B originally authored by the correct leader for round 10, and is this current proposal message allowed to be sent by the leader for round 12? Without that split, recovery paths stop making sense.

3.4 ConsensusBlockHeader#

The header is dense, but it becomes easier once you read it in layers.

Layer 1: Consensus Position#

  • block_round
  • epoch
  • qc
  • author
  • seq_num

This layer says where the block sits in consensus history and who authored it.

Layer 2: Time And Round-Linked Proof#

  • timestamp_ns
  • round_signature

This is where the block carries a round-linked proof that execution later cares about too.

Layer 3: Delayed Execution Boundary#

  • execution_inputs
  • delayed_execution_results

This is the first place where Monad’s delayed execution model becomes visible directly in the block format. The useful plain-English reading is that execution_inputs is what this block wants execution to do later, and delayed_execution_results is finalized execution output for older blocks whose delayed work has now matured. This is why a Monad header talks in two time directions at once — new work for this block, and completed work for earlier ordered blocks.

Layer 4: Payload Identity And Fee State#

  • block_body_id
  • base_fee
  • base_fee_trend
  • base_fee_moment

This layer ties the header to the body payload and to the current fee-market state.

One Small But Important base_fee_trend Nuance#

The code stores base_fee_trend as u64, but that unsigned field is just the storage and wire representation of a signed trend value. So the right mental model is: it is stored as unsigned, interpreted as signed movement encoded in two’s complement form, and cast back to signed form in fee math and debug formatting.

You do not need the full math yet. You do need to notice that the header carries more fee-market state than a simple Ethereum-style single base fee.

3.5 ConsensusFullBlock#

The full block is header plus body. Construction enforces that the body’s actual ID matches the block_body_id claimed by the header, so header and body are separate types but not independent objects. That split exists because the node often wants to talk separately about block identity and ancestry on one hand and payload availability and payload sync on the other.

3.6 The Block Model Versus The Proposal Wire Object#

This is another place where the code is more exact than the usual summary.

Block Model#

The block model separates header and body. That helps with persistence, sync, staged validation, and typed code paths.

Proposal Wire Object#

The ordinary proposal wire message carries the signed tip, the block body, and optionally the previous round’s TC — a timeout certificate, introduced in detail in §3.9, which is the aggregate proof that enough stake gave up on the previous round. So the proposal path is not “header now, body later”; on the normal wire path, both are present.

3.7 ConsensusTip#

The signed proposal object is not the raw header. It is the tip: a block header, an outer leader signature over the header, and an optional fresh-proposal certificate. This is one of the places where readers often flatten too much. A block can carry a round signature inside the header, an outer tip signature over the whole header, and later vote or timeout signatures over related statements — different proofs for different jobs.

3.8 Timeout Objects#

Timeout recovery needs more context than a simple “I gave up.” That is why timeout objects carry which round timed out, the highest QC round the validator knew, possibly a higher reusable tip round the validator knew, the validator’s timeout signature, and optional piggybacked voting information.

The key lesson is that timeouts do not only signal failure — they also carry recovery context. That is why a TC is richer than a QC.

3.9 Timeout Certificates And high_extend#

A TC is not just “2f+1 timeout signatures.” It also preserves enough structure to guide the next recovery step. The most important extra field is the recovery-side extension hint usually discussed through high_extend: it is not generic timeout context, it is the ranked best-known extension candidate carried through timeout aggregation, so recovery can first try to reuse the strongest known extension rather than going fresh too early.

The compact mental model is that a QC proves enough stake signed one block vote statement, while a TC proves enough stake timed out one round and preserves the best known extension point those validators reported. That extension point is what recovery later tries to reuse before falling back to a truly fresh proposal.

3.10 Recovery Messages#

Once a round times out, several smaller message types become important.

AdvanceRoundMessage#

This carries a QC or TC so peers can move their pacemakers forward quickly. It says, in effect, “here is round-ending evidence; advance if you trust it.”

RoundRecoveryMessage#

This asks the current leader to deal with a specific recovered tip after a timeout path. It is the “please judge this reusable tip candidate” message.

NoEndorsementMessage#

This says “I refuse to endorse reuse of this recovered tip.” Enough such refusals can later aggregate into a certificate.

3.11 NEC, NoTipCertificate, And FreshProposalCertificate#

This is the recovery-side cluster that needs the most careful reading.

NEC#

NEC means NoEndorsementCertificate. It is threshold proof that enough stake refused endorsement of the same recovered tip. It does not mean “the round failed in the abstract” — it means something more precise: the attempted tip-reuse path was refused strongly enough that a fresh proposal path can now be justified.

NoTipCertificate#

NoTipCertificate is the sibling concept: the “there is no reusable tip worth endorsing” proof. So the two fresh-proposal-enabling certificates are different:

CertificateWhat it says
NECthis recovered tip was actively refused
NoTipCertificatethere is no reusable tip to endorse at all

FreshProposalCertificate#

This is the unifying type. In current code it is an enum, not one magical monolithic proof, with two variants: FreshProposalCertificate::Nec(...) and FreshProposalCertificate::NoTip(...). That distinction matters because the leader is not always going fresh for the same reason — sometimes the reusable-tip path was explicitly refused, and sometimes there simply was no reusable-tip path worth endorsing.

3.12 The Recovery Decision Tree#

This is the recovery subprotocol in one picture:

flowchart LR
    Timeout["validators timeout round r"] --> TC["TC(r) forms"]
    TC --> Reuse{"reusable tip?"}
    Reuse -->|yes| Reproposal["try reusing tip"]
    Reuse -->|no| NoTip["NoTip path"]
    Reproposal -->|endorsed| ReuseTip["repropose recovered tip"]
    Reproposal -->|refused| NEC["NEC forms"]
    NEC --> Fresh["fresh proposal allowed"]
    NoTip --> Fresh2["NoTipCertificate allows fresh proposal"]

Later chapters make the state-machine transitions precise. This chapter’s job is just to keep the object meanings straight.

3.14 BlockPolicy: Valid Is Not The Same Thing As Coherent#

Consensus separates two questions: is this block valid, and is this block coherent with the chain and delayed-execution context? BlockPolicy is where the second question becomes concrete. That distinction matters because delayed execution means a block can be structurally valid enough to store but not yet coherent enough to vote on. This distinction drives later blocktree and voting behavior, and if you blur it away, later blocktree behavior becomes mysterious.

3.15 Execution-Side Mirrors#

Execution mirrors these block shapes in C++ so the execution daemon can consume typed block data. The important nuance is that the mirror is close but also versioned. That matters for historical compatibility — the execution side does not pretend the block format was always identical across revisions.

3.16 Checkpoints, Roots, And Restart State#

A restart anchor needs more than “latest block.” The relevant restart-side objects capture the current committed root, the highest carried round-ending certificate, and the bounded locked-epoch validator window needed to verify that certificate and survive nearby epoch transitions.

Why The Validator Window Is Bounded#

The checkpoint does not need the whole historical validator schedule forever. It only needs enough nearby locked-epoch information to verify the carried high certificate, resume around the current root safely, and survive nearby epoch transition boundaries. That is why the stored window is bounded instead of unbounded historical metadata.

What To Remember#

  • A vote is one small protocol statement; a QC is threshold proof over that statement.
  • proposal_round and block_round are different because reproposal is a real path.
  • Block headers carry delayed-execution structure directly.
  • Tips add an outer leader signature on top of the block header.
  • Timeout objects preserve recovery context, not just “failure happened.”
  • NEC means NoEndorsementCertificate.
  • FreshProposalCertificate is an enum carrying fresh-proposal authority, not one undifferentiated proof type.
  • BlockPolicy is where “coherent” becomes a real code distinction.
  • Checkpoints keep a bounded validator window because restart safety only needs local validator context, not infinite validator history.
