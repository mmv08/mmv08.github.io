Chapter 3: Consensus Data Structures

monad-client-book/03-consensus-data-structures.md View source →

Chapter 2 explained who is allowed to act. This chapter is about what those actors send to each other.

Validators do not see one another. They communicate by signed messages over an untrusted network, where anything can be delayed, dropped, replayed, or forged. So they do not trust each other’s claims — they verify each other’s signatures. Every consensus object is built around that constraint. Each one is a small, signed answer to a specific protocol question, designed so that any node can check it without trusting the sender.

The questions, and the objects that answer them, are:

  • “Did you vote for this block?” — Vote
  • “Did enough validators vote for this block?” — QuorumCertificate
  • “What block are you proposing?” — ConsensusBlockHeader and ConsensusFullBlock
  • “I am the leader, here is the signed proposal.” — ConsensusTip and proposal messages
  • “We gave up on this round.” — Timeout and TimeoutCertificate
  • “We refuse to reuse this tip” or “there is no reusable tip worth endorsing.” — NEC, NoTipCertificate, FreshProposalCertificate
  • “Here is where we should resume after restart.” — checkpoints

If the previous chapter was about the social structure of consensus, this chapter is about its documents.

Why This Chapter Matters#

Many later functions look difficult because they manipulate several proof objects at once. For each object, ask four questions: what statement is it making, who signed it, what threshold does it need, and what later object can it become? Once those answers are clear, the state-machine chapters become easier to read.

Another useful pattern is statement, proof, consequence. A Vote is a statement. A QuorumCertificate is proof that enough stake made that same statement. The consequence is that some later handler can advance a round, extend a certified parent, or mark an ancestor committable. Most objects in this chapter fit that same shape, even when recovery adds more branches.

3.1 Vote#

A vote is the smallest meaningful consensus statement. It does not try to describe a whole block, run execution, or prove a chain. It only says that one validator supports one block ID in one round and epoch. Conceptually, it says, “In epoch E, during round R, I vote for block B.” That small shape is what lets many votes later aggregate cleanly into one certificate.

The production type is exactly that small. Abridged from monad-consensus-types/src/voting.rs:

pub struct Vote {
    /// id of the proposed block
    pub id: BlockId,
    /// the round that this vote is for
    pub round: Round,
    /// the epoch of the round that this vote is for
    pub epoch: Epoch,
}

There is no body, transaction list, or execution payload here. A vote is only a signed statement about one block ID in one round and epoch.

3.2 QuorumCertificate#

A QC is one vote statement plus enough signatures over that exact vote. So the mental model is simple: the vote is the statement, and the QC is proof that enough stake signed that statement.

That distinction matters because later protocol code often passes QCs around as if they were facts about the chain. They are facts only because the statement is exact and the signature collection crosses the validator-set threshold from Chapter 2. If either side changes — the vote statement or the validator set used to verify the signatures — the certificate no longer proves the same thing.

That is the first full example of the statement-proof-consequence pattern. The statement says “block B received my vote in round R.” The proof says “enough stake signed that same statement.” The consequence is not always immediate commit, but the QC becomes certified evidence that later proposal, pacemaker, and commit logic can use.

Genesis QC#

Consensus needs a starting point, so the code provides a synthetic genesis QC. It anchors the genesis block ID, the genesis round, and epoch 1. That lets the first real block extend a well-defined certified parent instead of special-casing “history starts here” everywhere.

Why The Commit Rule Needs Parent Precision#

The code’s committable-block logic is more precise than the phrase “QC on QC.” The useful reader-level version is this: a new QC certifies block B; block B itself carries a QC for parent A; and if the child certification has the required next-round relationship to the parent certification, then A becomes committable.

In code terms, a QC for block B can make B’s parent committable when QC(B).round == B.qc.round + 1; the commit target is B.parent_id, not B itself.

So the key idea is not “some newer QC exists.” It is “a specific certified parent-child relationship exists.” That precision is why the commit rule is safe to automate.

The QC type and commit helper show that precision:

pub struct QuorumCertificate<SCT> {
    pub info: Vote,
    pub signatures: SCT,
}

pub fn genesis_qc() -> Self {
    let vote = Vote {
        id: GENESIS_BLOCK_ID,
        epoch: Epoch(1),
        round: GENESIS_ROUND,
    };
    // ...
}

pub fn get_committable_id<ST, EPT>(
    &self,
    qc_parent_block: &ConsensusBlockHeader<ST, SCT, EPT>,
) -> Option<BlockId> {
    assert_eq!(self.info.id, qc_parent_block.get_id());
    if self.info.round == qc_parent_block.qc.info.round + Round(1) {
        Some(qc_parent_block.get_parent_id())
    } else {
        None
    }
}

The certificate stores the vote statement and signatures. The commit helper then uses the block pointed to by that vote to identify the parent that can be committed.

Why Consecutive Rounds Make This Safe#

The consecutive-round rule is not arithmetic coincidence. It is the structural fact that makes the whole commit logic safe, and the argument is short enough to keep nearby.

A QC carries signatures from at least two-thirds of stake. Any two QCs in the same round must therefore overlap in at least one honest validator, because two two-thirds slices of the same total cannot fit without intersecting in more than one-third of stake — and at most one-third can be Byzantine. Honest validators do not sign two conflicting blocks in the same round. So at most one block can have a QC in any given round.

That observation propagates forward. When a QC forms at round R for block A, honest validators record A as their highest QC and refuse to vote at round R+1 for anything that does not extend it. If a QC also forms at round R+1, it must therefore be for a block whose chain runs through A. The consecutive-round condition rules out the only alternative — a hidden competing branch that quietly gathered enough votes to undo A — because there was no round R+1 left in which to do so.

This is why a child QC at the immediately next round is the structural fact that makes the parent safe to commit.

3.3 proposal_round Versus block_round#

This distinction is essential.

block_round#

block_round is the round in which the block was originally authored.

proposal_round#

proposal_round is the round in which the current proposal message is being sent.

Why The Split Exists#

Suppose block B was first proposed in round 10, but recovery later decides B is still the right tip and re-sends it in round 12. Then block_round(B) = 10 while proposal_round = 12.

The node now has to validate two leader claims. First, was B originally authored by the correct leader for round 10? Second, is this current proposal message allowed to be sent by the leader for round 12? Without that split, recovery paths stop making sense.

3.4 ConsensusBlockHeader#

The header is dense because it is the meeting point of several jobs. It has to identify where the block belongs in consensus, prove what parent it extends, bind the transaction payload, carry fee-market state, and connect ordered consensus to delayed execution. Reading it as one flat list hides that purpose; reading it in layers makes the structure easier to follow.

The code is trying to make one compact object do two kinds of work. First, the header must be enough for consensus to reason about ancestry, authorship, certificates, and ordering without opening the whole body. Second, it must carry the execution-facing promises and results that let delayed execution stay connected to ordered consensus. That is why the fields feel mixed at first: they are the boundary between two subsystems, not a pure consensus-only record.

The generic execution fields are defined by a small trait before they appear in the header. Abridged from monad-types/src/lib.rs and monad-eth-types/src/lib.rs:

pub trait ExecutionProtocol {
    /// inputs to execution
    type ProposedHeader;
    type Body;

    /// output of execution
    type FinalizedHeader: FinalizedHeader;
}

pub trait FinalizedHeader {
    fn seq_num(&self) -> SeqNum;
}

pub struct EthExecutionProtocol;
impl ExecutionProtocol for EthExecutionProtocol {
    type ProposedHeader = ProposedEthHeader;
    type FinalizedHeader = EthHeader;
    type Body = EthBlockBody;
}

That is the consensus/execution vocabulary in one place: proposed header and body are inputs to execution; finalized headers are outputs from earlier execution work.

Layer 1: Consensus Position#

  • block_round
  • epoch
  • qc
  • author
  • seq_num

This layer says where the block sits in consensus history and who authored it.

Layer 2: Time And Round-Linked Proof#

  • timestamp_ns
  • round_signature

This is where the block carries a round-linked proof that execution later cares about too.

Layer 3: Delayed Execution Boundary#

  • delayed_execution_results
  • execution_inputs

This is the first place where Monad’s delayed execution model becomes visible directly in the block format. The field order in the Rust and C++ block models is delayed_execution_results first, then execution_inputs.

The plain-English reading is easier in time order. execution_inputs is what this block wants execution to do later. delayed_execution_results is finalized execution output for older blocks whose delayed work has now matured. This is why a Monad header talks in two time directions at once: completed work for earlier ordered blocks, and new work for this block.

A concrete picture helps. With the wired EXECUTION_DELAY = 3, suppose the chain is at block 100. The header for block 100 carries execution_inputs requesting new execution work for itself and delayed_execution_results for block 97, whose execution finished while consensus was busy ordering blocks 98, 99, and 100. So the same header simultaneously says “please run me later” and “here is the now-final outcome of work I asked for three blocks ago.”

The delayed-result list is also bounded in the wire/storage decode path. In this source version, ConsensusBlockHeader decodes delayed_execution_results through LimitedVec with MAX_DELAYED_RESULTS = 4, so the header does not accept an unbounded pile of delayed execution outputs.

Layer 4: Payload Identity And Fee State#

  • block_body_id
  • base_fee
  • base_fee_trend
  • base_fee_moment

This layer ties the header to the body payload and to the current fee-market state.

Here is the field shape all four layers come from:

pub struct ConsensusBlockHeader<ST, SCT, EPT>
where
    EPT: ExecutionProtocol,
{
    pub block_round: Round,
    pub epoch: Epoch,
    pub qc: QuorumCertificate<SCT>,
    pub author: NodeId<CertificateSignaturePubKey<ST>>,

    pub seq_num: SeqNum,
    pub timestamp_ns: u128,
    pub round_signature: RoundSignature<SCT::SignatureType>,

    pub delayed_execution_results: Vec<EPT::FinalizedHeader>,
    pub execution_inputs: EPT::ProposedHeader,
    pub block_body_id: ConsensusBlockBodyId,

    pub base_fee: u64,
    pub base_fee_trend: u64,
    pub base_fee_moment: u64,
}

The header is the cross-layer object: it names consensus position, carries parent proof, binds a body payload, requests new execution work, and reports delayed execution output.

The manual RLP implementation around this header is intentional. The code avoids a trailing-field derive path because a trailing 0x80 value is ambiguous in that context: it can decode like an absent value or a zero-like present value. That is a serialization safety choice, not just local style.

One Small But Important base_fee_trend Nuance#

The code stores base_fee_trend as u64, an unsigned 64-bit integer. That field is the storage and wire representation of a signed trend value: stored unsigned, interpreted as signed movement encoded in two’s complement form, and cast back to signed form in fee math and debug formatting.

The full math comes later. The point at this stage is that the header carries more fee-market state than a simple Ethereum-style single base fee.

3.5 ConsensusFullBlock#

The full block is header plus body. Construction enforces that the body’s actual ID matches the block_body_id claimed by the header, so header and body are separate types but not independent objects. That split exists because the node often wants to talk separately about block identity and ancestry on one hand and payload availability and payload sync on the other.

3.6 The Block Model Versus The Proposal Wire Object#

A consensus block is the typed model that consensus stores and validates. A proposal message is the wire object that carries a signed tip, the body, and optional timeout evidence to other nodes.

This split exists because local reasoning and network delivery are different jobs. The block model should make stored history easy to validate, index, and commit. The proposal message should give a receiving node enough signed material to judge the current round without first reconstructing the block from somewhere else. They often contain overlapping data, but they are shaped around different moments in the protocol.

Block Model#

The block model separates header and body. That helps with persistence, sync, staged validation, and typed code paths.

Proposal Wire Object#

The ordinary proposal wire message carries the signed tip, the block body, and optionally the previous round’s TC. A TC is a timeout certificate: aggregate proof that enough stake gave up on the previous round. So the proposal path is not “header now, body later”; on the normal wire path, both are present.

3.7 ConsensusTip#

The signed proposal object is not the raw header. It is the tip: a block header, an outer leader signature over the header, and an optional fresh-proposal certificate. Keep those proof layers separate. A block can carry a round signature inside the header, an outer tip signature over the whole header, and later vote or timeout signatures over related statements. Those are different proofs for different jobs.

3.8 Timeout Objects#

A timeout is not just a complaint that nothing happened. It is also a report about what the validator safely knew when it gave up on the round. Recovery needs that report because the next leader should not throw away useful certified structure if there is still a safe tip to reuse.

That is why timeout objects carry which round timed out, the highest QC round the validator knew, possibly a higher reusable tip round the validator knew, the validator’s timeout signature, and optional piggybacked voting information.

The code is trying to preserve useful information at the moment of failure. If a validator only said “I timed out,” the next leader would know that progress stalled but would not know which certified branch was still safe to continue. By carrying the highest known extension evidence, the timeout path gives recovery a starting point instead of forcing it to discard recent work.

The key lesson is that timeouts do not only signal failure — they also carry recovery context. That is why a TC is richer than a QC.

Two details in the code are worth pinning down. First, timeout messages carry HighExtendVote, not only the plainer HighExtend concept; that wrapper can include an optional vote signature when it is still safe to piggyback one. Second, the timeout object can also carry a last_round_certificate, which matters when the highest extension evidence is not itself from the immediately previous round.

3.9 Timeout Certificates And high_extend#

A TC is not only “enough timeout signatures.” It also preserves enough structure to guide the next recovery step. The most important extra field is the recovery-side extension hint usually discussed through high_extend. This is not generic timeout context. It is the ranked best-known extension candidate carried through timeout aggregation, so recovery can first try to reuse the strongest known extension rather than going fresh too early.

The compact mental model is that a QC proves enough stake signed one block vote statement, while a TC proves enough stake timed out one round and preserves the best known extension point those validators reported. That extension point is what recovery later tries to reuse before falling back to a truly fresh proposal.

That still does not mean the extension is already committed. A certificate can make an ancestor committable, but the block tree only commits once the relevant blocks are present and coherent in the local tree.

3.10 Recovery Messages#

Once a round times out, several smaller message types become important.

AdvanceRoundMessage#

This carries a QC or TC so peers can move their pacemakers forward quickly. It says, in effect, “here is round-ending evidence; advance if you trust it.”

RoundRecoveryMessage#

This asks the current leader to deal with a specific recovered tip after a timeout path. It is the “please judge this reusable tip candidate” message.

NoEndorsementMessage#

This says “I refuse to endorse reuse of this recovered tip.” Enough such refusals can later aggregate into a certificate.

3.11 NEC, NoTipCertificate, And FreshProposalCertificate#

This is the recovery-side cluster that needs the most careful reading.

The simple temptation is to say, “the round timed out, so the next leader can make a fresh block.” Monad’s recovery objects are stricter than that. A fresh proposal needs proof that the safer reuse path was either refused or unavailable. These types are the proof objects for that decision.

That extra proof matters because a fresh proposal can abandon a candidate tip that some validators still consider the best safe continuation. The protocol therefore requires explicit authority before the leader goes fresh. It must show either that enough stake refused the specific reusable tip, or that there was no reusable tip to endorse in the first place.

NEC#

NEC means NoEndorsementCertificate. It is threshold proof that enough stake refused endorsement of the same recovered tip. It does not mean “the round failed in the abstract” — it means something more precise: the attempted tip-reuse path was refused strongly enough that a fresh proposal path can now be justified.

NoTipCertificate#

NoTipCertificate is the sibling concept: the “there is no reusable tip worth endorsing” proof. So the two fresh-proposal-enabling certificates are different:

CertificateWhat it says
NECthis recovered tip was actively refused
NoTipCertificatethere is no reusable tip to endorse at all

FreshProposalCertificate#

This is the unifying type. In current code it is an enum with two variants: FreshProposalCertificate::Nec(...) and FreshProposalCertificate::NoTip(...). That distinction matters because the leader is not always going fresh for the same reason. Sometimes the reusable-tip path was explicitly refused. Sometimes there was no reusable-tip path worth endorsing.

3.12 The Recovery Decision Tree#

This is the recovery subprotocol in one picture:

flowchart LR
    Timeout["validators timeout round r"] --> TC["TC(r) forms"]
    TC --> Reuse{"reusable tip?"}
    Reuse -->|yes| Reproposal["try reusing tip"]
    Reuse -->|no| NoTip["NoTip path"]
    Reproposal -->|endorsed| ReuseTip["repropose recovered tip"]
    Reproposal -->|refused| NEC["NEC forms"]
    NEC --> Fresh["fresh proposal allowed"]
    NoTip --> Fresh2["NoTipCertificate allows fresh proposal"]

Later chapters make the state-machine transitions precise. This chapter’s job is to keep the object meanings straight.

3.14 BlockPolicy: Valid Is Not The Same Thing As Coherent#

Consensus separates two questions: is this block valid, and is this block coherent with the chain and delayed-execution context? BlockPolicy is where the second question becomes concrete. That distinction matters because delayed execution means a block can be structurally valid enough to store but not yet coherent enough to vote on. The same distinction drives later blocktree and voting behavior.

The simple version is this: validation checks the block as an object; coherency checks the block as a continuation of this node’s current view. A block may have the right signatures, body hash, author, and basic shape, but still depend on execution results or ancestors the node cannot yet confirm. BlockPolicy keeps that second judgment out of the generic block type and puts it behind the policy that understands the delayed-execution window.

The trait boundary is narrow. Abridged from monad-consensus-types/src/block.rs:

pub trait BlockPolicy<ST, SCT, EPT, SBT, CCT, CRT>
where
    EPT: ExecutionProtocol,
    SBT: StateBackend<ST, SCT>,
{
    type ValidatedBlock: Deref<Target = ConsensusFullBlock<ST, SCT, EPT>>;

    fn check_coherency(
        &self,
        block: &Self::ValidatedBlock,
        extending_blocks: Vec<&Self::ValidatedBlock>,
        blocktree_root: RootInfo,
        state_backend: &SBT,
        chain_cnfig: &CCT,
    ) -> Result<(), BlockPolicyError>;

    fn get_expected_execution_results(
        &self,
        block_seq_num: SeqNum,
        extending_blocks: Vec<&Self::ValidatedBlock>,
        state_backend: &SBT,
    ) -> Result<Vec<EPT::FinalizedHeader>, StateBackendError>;

    fn update_committed_block(&mut self, block: &Self::ValidatedBlock);
    fn reset(&mut self, last_delay_committed_blocks: Vec<&Self::ValidatedBlock>);
}

Consensus does not need to know every Ethereum or Monad execution rule. It needs a validated block type and a policy object that can answer whether that block is coherent in the current delayed-execution context.

The same file also defines the commit-state payload that later becomes storage and RPC freshness:

pub enum OptimisticPolicyCommit<ST, SCT, EPT, BPT, SBT, CCT, CRT> {
    Proposed {
        block: BPT::ValidatedBlock,
        is_canonical: bool,
    },
    Voted(BPT::ValidatedBlock),
    Finalized(BPT::ValidatedBlock),
}

pub enum OptimisticCommit<ST, SCT, EPT> {
    Proposed {
        block: ConsensusFullBlock<ST, SCT, EPT>,
        is_canonical: bool,
    },
    Voted(ConsensusFullBlock<ST, SCT, EPT>),
    Finalized(ConsensusFullBlock<ST, SCT, EPT>),
}

Those three words are not only glossary terms. They are command payload states that later drive ledger heads, execution events, and RPC tag semantics.

3.15 Execution-Side Mirrors#

Execution mirrors these block shapes in C++ so the execution daemon can consume typed block data. The important nuance is that the mirror is close but also versioned. That matters for historical compatibility — the execution side does not pretend the block format was always identical across revisions.

3.16 Checkpoints, Roots, And Restart State#

A restart anchor needs more than “latest block.” The relevant restart-side objects capture the current committed root, the highest carried round-ending certificate, and the bounded locked-epoch validator window needed to verify that certificate and survive nearby epoch transitions.

Why The Validator Window Is Bounded#

The checkpoint does not need the whole historical validator schedule forever. It only needs enough nearby locked-epoch information to verify the carried high certificate, resume around the current root safely, and survive nearby epoch transition boundaries. That is why the stored window is bounded instead of unbounded historical metadata.

What To Remember#

  • A vote is one small protocol statement; a QC is threshold proof over that statement.
  • proposal_round and block_round are different because reproposal is a real path.
  • Block headers carry delayed-execution structure directly: code lists delayed_execution_results before execution_inputs, while the concept is easiest to read as old matured work plus new requested work.
  • Tips add an outer leader signature on top of the block header.
  • Timeout objects preserve recovery context, not just “failure happened.”
  • NEC means NoEndorsementCertificate.
  • FreshProposalCertificate is an enum carrying fresh-proposal authority, not one undifferentiated proof type.
  • BlockPolicy is where “coherent” becomes a real code distinction.
  • Checkpoints keep a bounded validator window because restart safety only needs local validator context, not infinite validator history.
