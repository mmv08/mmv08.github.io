Chapter 12: Node Assembly and RPC

monad-client-book/12-node-assembly-and-rpc.md View source →

By this point we have seen the main subsystems in isolation: consensus state, execution boundaries, txpool, networking, and storage. This chapter puts them back together into long-running binaries. The two main Rust-side binaries are monad-node and monad-rpc. One reminder has to stay in view the whole time: the execution engine still lives in the separate monad repo. So this chapter is about how the Rust-side binaries are assembled around that separate execution world.

Why This Chapter Matters#

Many production bugs are not consensus bugs or EVM bugs. They are assembly bugs — the right resource was missing, the wrong process never started, a service was optional in the type graph but assumed present in the main startup path, or the data existed but not in the process serving the request. That is why assembly matters.

If you only open one node-side function first, open maybe_start_consensus() in monad-state/src/lib.rs. If you only open one RPC file first, open monad-rpc/src/main.rs. One operational risk is worth carrying from the start: standard WebSocket newHeads and logs are currently proposed-only feeds, while Monad-specific WebSocket subscriptions preserve commit state explicitly.

12.1 Start With The Process Boundary#

The cleanest first picture is the process map itself.

flowchart LR
    Clients["wallets / apps / operators"] --> RPC["monad-rpc"]

    subgraph Rust["Rust-side binaries from monad-bft"]
        Node["monad-node"]
        RPC
    end

    subgraph Exec["execution repo surfaces"]
        ExecDaemon["monad execution daemon"]
        Triedb["triedb / MonadDB"]
        Ring["execution event ring"]
        Hosted["hosted execution APIs"]
    end

    RPC -->|Unix socket| Txpool["txpool IPC"]
    Node -->|owns| Txpool
    Node -->|ledger files| ExecDaemon
    ExecDaemon --> Triedb
    ExecDaemon --> Ring
    Node -->|FFI / hosted reads| Hosted
    RPC -->|FFI / hosted reads| Hosted
    Hosted --> Triedb
    RPC --> Ring

A few of the terms in that diagram are worth pinning down before going further:

  • the execution event ring is a shared-memory ring buffer that the execution daemon writes freshest execution events into and that Rust-side processes read without blocking either side; covered in Chapter 8
  • FFI stands for foreign function interface — the arrows labeled “FFI / hosted reads” mean a Rust process calling into execution-owned C/C++ functions linked into the same process
  • IPC stands for inter-process communication — here specifically a Unix domain socket between monad-rpc and the txpool that lives inside monad-node

That picture already explains several important facts. monad-node is not the execution engine. monad-rpc is a separate process, not just a library inside the node. Transaction submission crosses a local IPC boundary. Recent RPC reads depend on execution-owned outputs. And repo boundaries and process boundaries are related, but not identical.

12.2 NodeState::setup() Turns Generic Code Into One Concrete Node#

monad-node/src/main.rs is intentionally thin. The real “become this specific node” work happens earlier in NodeState::setup().

That setup phase prepares identity keys, certificate keys, node config, forkpoint config, validator config, the ledger/triedb/WAL/IPC paths, tracing and runtime settings, and persisted peer state. The forkpoint is the restart anchor. It captures the committed root plus the high certificate plus nearby validator context, so the node can resume consensus safely instead of from a raw “latest block” pointer. Chapter 5 covers the full shape.

This is also where startup can replace stale local bootstrap data with fresher remote bootstrap data. So startup is not only “read local files and go.” It can also be “compare local bootstrap state against remote bootstrap state, and refresh local files when they are too stale.”

That is an operational fact of the current code path, not only a documentation note.

12.3 monad-node Starts In Sync Mode, Not Live Consensus Mode#

After setup, the node still does not immediately act like a live validator. MonadStateBuilder starts it in ConsensusMode::Sync. That sync-mode state is anchored around the forkpoint root, the forkpoint high certificate, and the locked-epoch validator context loaded at startup.

Then maybe_start_consensus() decides whether the node still needs committed block sync, state sync, or a live transition.

This is the runtime fact to keep in view: startup and sync are one continuous story. The node does not first “boot fully” and then separately “do sync.”

12.4 The Current Node Wiring Bakes In Important Runtime Facts#

Some facts in monad-node/src/main.rs are architectural, and some are current assembly facts. The most important current wiring facts are these: EXECUTION_DELAY = 3 in this source version, the consensus-side state backend is a dedicated triedb worker thread plus cache, and the txpool/router/ledger/state sync/timers/local control interfaces are all child executors under one parent executor.

The WAL is also created in the node process and written before events reach state.update(...).

The ConsensusConfig built in main.rs also wires in thresholds such as statesync_to_live_threshold, live_to_statesync_threshold, and start_execution_threshold. These are runtime assembly choices in this source version, not timeless architectural laws.

12.5 ParentExecutor Is The Glue Layer#

ParentExecutor is what makes many child executors look like one event source and one command sink. That is the main orchestration layer of the node process.

Command Fan-Out#

state.update(...) returns a mixed list of commands. ParentExecutor::exec(...) splits them by subsystem and forwards each slice to the right child executor. That keeps protocol logic out of main.rs.

Poll Order#

ParentExecutor also polls child streams in a fixed order. In the current code, the order is:

  1. timer
  2. control panel
  3. ledger
  4. txpool
  5. validator-set updater
  6. timestamp updater
  7. loopback
  8. router
  9. state sync
  10. config loader

This is worth stating carefully.

Current code. Fixed poll order affects local process behavior and debugging.

Not the protocol. It is not itself the consensus protocol’s correctness rule.

That distinction matters throughout the second half of this book.

Abridged from production code. The important detail is that command fan-out and polling live in one orchestration layer:

pub struct ParentExecutor<R, T, L, C, V, TS, TP, CP, LO, SS, CL> {
    pub router: R,
    pub timer: T,
    pub ledger: L,
    pub config_file: C,
    pub val_set: V,
    pub timestamp: TS,
    pub txpool: TP,
    pub control_panel: CP,
    pub loopback: LO,
    pub state_sync: SS,
    pub config_loader: CL,
    // if you add an executor here, add it to BOTH exec AND poll_next
}

fn exec(&mut self, commands: Vec<Command<E, OM, ST, SCT, EPT, BPT, SBT, CCT, CRT>>) {
    let (
        router_cmds,
        timer_cmds,
        ledger_cmds,
        config_file_cmds,
        val_set_cmds,
        timestamp_cmds,
        txpool_cmds,
        control_panel_cmds,
        loopback_cmds,
        state_sync_cmds,
        config_reload_cmds,
    ) = Command::split_commands(commands);

    self.router.exec(router_cmds);
    self.timer.exec(timer_cmds);
    self.ledger.exec(ledger_cmds);
    self.config_file.exec(config_file_cmds);
    self.val_set.exec(val_set_cmds);
    self.timestamp.exec(timestamp_cmds);
    self.txpool.exec(txpool_cmds);
    self.control_panel.exec(control_panel_cmds);
    self.loopback.exec(loopback_cmds);
    self.state_sync.exec(state_sync_cmds);
    self.config_loader.exec(config_reload_cmds);
}

And the fixed poll order is equally explicit:

fn poll_next(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Option<Self::Item>> {
    let this = self.deref_mut();

    if let Poll::Ready(Some(e)) = this.timer.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.control_panel.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.ledger.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.txpool.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.val_set.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.timestamp.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.loopback.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.router.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.state_sync.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    if let Poll::Ready(Some(e)) = this.config_loader.next().poll_unpin(cx) { return Poll::Ready(Some(e)); }
    Poll::Pending
}

This is node assembly as code: one parent executor makes many child services look like one event loop.

12.6 The Node Runtime Is A Small Event Loop Around A Larger State Machine#

Once setup is done, the main loop is conceptually:

  1. wait for an event from ParentExecutor
  2. write the event to WAL
  3. pass it into state.update(...)
  4. execute the returned commands through ParentExecutor

The three roles are: MonadState owns most protocol behavior, ParentExecutor owns orchestration and fan-out, and main.rs owns startup and the small outer event loop. The rest of the node assembly hangs off that split.

This is the shortest honest node-side dependency graph:

That graph is more useful than a crate list because it shows which resources the node actually needs before it can become live.

12.8 monad-rpc Is Its Own Process With Its Own Resource Graph#

monad-rpc is not a thin wrapper embedded inside the node. It is a separate binary and its own process. That separation is useful because consensus stays focused on protocol work, RPC owns its own thread pools and caches, RPC can restart without taking down consensus, and resource availability can degrade differently on the RPC side than on the node side. The startup path in monad-rpc/src/main.rs makes that explicit.

12.9 The RPC Startup Graph#

The main RPC startup graph looks like this:

flowchart TD
    Args["CLI args + node config"] --> Main["monad-rpc main"]
    Main --> TxBridge["optional txpool bridge"]
    Main --> TriedbEnv["optional TriedbEnv"]
    Main --> Archive["optional archive reader"]
    Main --> EthCall["optional EthCallHandler"]
    Main --> EventRing["optional event ring client"]
    EventRing --> EventServer["EventServer"]
    EventServer --> Buffer["ExecEventsBuffer"]
    TriedbEnv --> Data["DataProvider"]
    Archive --> Data
    Buffer --> Data
    Data --> Handlers["JSON-RPC handlers"]
    EventServer --> WS["WebSocket server"]

That graph has an important consequence: not every RPC capability depends on exactly the same local resource set.

The DataProvider node in the graph is conditional. In the current main startup path, no triedb path means no TriedbEnv; no TriedbEnv means no DataProvider; and no DataProvider means most triedb-backed state handlers are unavailable even if archive or event resources exist.

Abridged from production code. The important detail is that the event ring controls both WebSocket availability and the freshest recent cache:

let (events_client, events_for_cache) = if let Some(exec_event_path) = args.exec_event_path {
    let event_ring_path =
        EventRingPath::resolve(exec_event_path).expect("Execution event ring path resolves");
    let event_ring = EventRing::new(event_ring_path).expect("Execution event ring is ready");

    let events_client = EventServer::start(event_ring);
    let events_for_cache = events_client
        .subscribe()
        .expect("Failed to subscribe to event server");

    (Some(events_client), Some(events_for_cache))
} else {
    if args.ws_enabled {
        panic!("exec-event-path is not set but is required for websockets");
    }
    (None, None)
};

let event_buffer = if let Some(mut events_for_cache) = events_for_cache {
    let event_buffer = Arc::new(ExecEventsBuffer::new(1024));
    tokio::spawn(async move {
        loop {
            match events_for_cache.recv().await {
                Ok(event) => event_buffer.insert(event).await,
                Err(RecvError::Lagged(lag_count)) => {
                    warn!(?lag_count, "event server channel lagged, events will be missing");
                }
                Err(RecvError::Closed) => break,
            }
        }
    });
    Some(event_buffer)
} else {
    None
};

let data_provider = triedb_env.map(|t| DataProvider::new(event_buffer, t, archive_reader));

This is the assembly distinction from Chapter 8 in one place: the buffer is useful only if the event ring exists, and the main DataProvider path is still triedb-rooted.

12.10 Be Precise About Type Capability Versus Main Startup Wiring#

The right wording pattern here is: separate architecture from current code from runtime assembly fact. For example, DataProvider<TriedbEnv> can be constructed with or without an event buffer, and can also be constructed with or without an archive reader. But in the current main startup path, if there is no triedb path then there is no TriedbEnv, if there is no TriedbEnv then there is no DataProvider, and if WebSocket support is enabled without an execution event path, startup panics.

So the precise statement is this: DataProvider is not a type-system law that requires every auxiliary resource, and the current main RPC wiring still makes triedb the hard prerequisite for the main chain-state read surface. That distinction matters because current startup wiring is not the same thing as a permanent architectural rule.

12.11 The RPC Process Degrades By Resource#

Different missing resources disable different capabilities.

Missing resourceWhat degrades
txpool IPC pathtransaction submission is unavailable
triedb pathmost stateful chain reads are unavailable because the main DataProvider is not built
archive readerhistorical block-oriented reads are limited to recent retained data
execution event pathWebSocket server cannot run; freshest event-buffered reads disappear
eth-call handlerhosted execution surfaces such as eth_call and trace-style simulation are unavailable

This table is a better model than “RPC is either up or down.” Often the process is up, but only part of its capability graph is available.

12.12 Architecture, Current Code, Current Caveat#

Architecture monad-node is the protocol process and monad-rpc is a separate edge process. Each assembles a different capability graph around execution-owned resources.

Current code maybe_start_consensus() gates the node’s live transition, while monad-rpc/src/main.rs conditionally assembles tx submission, triedb, archive, hosted execution, and event-ring-backed WebSocket resources.

Current caveat Standard WebSocket newHeads and logs are currently filtered to BlockCommitState::Proposed. Readers who want explicit commit state need the Monad-specific subscription variants.

12.13 One Important latest Nuance#

DataProvider::get_latest_block_number() deliberately returns triedb’s latest proposed block number, not the event buffer’s freshest seen height. The code comment explains why.

There is a race between the live event buffer and triedb-backed state queries. If a wallet calls eth_getBlockByNumber and then immediately calls eth_getBalance, RPC wants those reads to line up more predictably with triedb-backed state. So this is a good example of RPC preferring internal read-surface consistency over whichever component saw the newest event first.

For Ethereum block tags, the practical mapping is: latest resolves to the proposed height, safe resolves to the voted height, and finalized resolves to the finalized height. The event buffer helps track those fresh heights, but triedb-backed account and storage data still come from triedb through DataProvider.

12.14 Common Wallet Gas And Fee RPCs#

Three RPC methods are worth naming because wallets hit them frequently and they cross several surfaces at once.

MethodCurrent shape in the source version used by this book
eth_estimateGasresolves a triedb-backed block context, runs hosted execution, and searches for a gas limit that lets the simulated transaction succeed
eth_fillTransactionfills missing transaction fields such as nonce, fee fields, chain ID, value, and gas; for missing gas it uses estimation mode that can accept execution failure or reserve-balance violation as terminal enough to produce a gas limit
eth_feeHistoryreads retained fee/header history through the triedb-backed RPC surface

The important distinction is that eth_call, eth_estimateGas, and eth_fillTransaction all use hosted execution-shaped machinery, but they do not promise the same thing. A call reports simulated execution output, estimate gas asks for a successful gas limit, and fill transaction constructs a signable transaction shape.

12.15 Request Walkthroughs#

The easiest way to make assembly concrete is to follow a few requests end to end.

eth_sendRawTransaction#

  1. client sends JSON-RPC to monad-rpc
  2. RPC uses the txpool bridge over the Unix socket
  3. the txpool inside monad-node performs ingress validation
  4. later, a leader may select that transaction into a proposal

That means transaction submission is really RPC edge in one process and txpool ownership in another process.

Abridged from production code. The important detail is that RPC decodes and applies user-protection checks, then hands the transaction to the txpool bridge:

pub async fn monad_eth_sendRawTransaction(
    txpool_bridge_client: &EthTxPoolBridgeClient,
    params: MonadEthSendRawTransactionParams,
    chain_id: u64,
    allow_unprotected_txs: bool,
) -> JsonRpcResult<String> {
    let tx = validate_and_decode_tx(
        &params.hex_tx.0,
        chain_id,
        allow_unprotected_txs,
        JsonRpcError::txn_decode_error,
    )?;

    let tx_hash = *tx.tx_hash();
    submit_to_txpool(txpool_bridge_client, tx).await?;
    Ok(tx_hash.to_string())
}

fn validate_and_decode_tx(
    hex_tx: &[u8],
    chain_id: u64,
    allow_unprotected_txs: bool,
    decode_error_fn: impl FnOnce() -> JsonRpcError,
) -> Result<TxEnvelope, JsonRpcError> {
    let tx = TxEnvelope::decode_2718_exact(hex_tx).map_err(|_| decode_error_fn())?;

    if !allow_unprotected_txs && tx.chain_id().is_none() {
        return Err(JsonRpcError::custom(
            "Unprotected transactions (pre-EIP155) are not allowed over RPC".to_string(),
        ));
    }
    if let Some(tx_chain_id) = tx.chain_id() {
        if tx_chain_id != chain_id {
            return Err(JsonRpcError::invalid_chain_id(chain_id, tx_chain_id));
        }
    }
    Ok(tx)
}

async fn submit_to_txpool(
    txpool_bridge_client: &EthTxPoolBridgeClient,
    tx: TxEnvelope,
) -> Result<(), JsonRpcError> {
    let Some(_tx_inflight_guard) = txpool_bridge_client.acquire_tx_inflight_guard() else {
        return Err(JsonRpcError::overloaded());
    };

    let (tx_status_recv_send, tx_status_recv_recv) = tokio::sync::oneshot::channel();
    txpool_bridge_client.try_send(tx, tx_status_recv_send)
        .map_err(|_| JsonRpcError::overloaded())?;
    // async status wait omitted
}

RPC validates the edge request and enforces local backpressure. It still does not own sequencing.

eth_getBalance#

  1. request arrives at monad-rpc
  2. handler resolves a block tag or hash into a triedb BlockKey
  3. TriedbEnv reads retained state from triedb
  4. response returns without involving the archive path

The event buffer may help the process know fresh proposed/voted/finalized heights, but it does not serve the account balance itself. The account data comes from triedb through DataProvider. The important caveat is that old balance reads only work while the needed version is still retained.

eth_getTransactionReceipt#

  1. RPC first tries ExecEventsBuffer
  2. if not found there, it tries triedb lookup data
  3. if still not found and archive is configured, it tries archive index data

So the receipt path is a good example of a composed read surface: freshest recent path, then retained recent path, then historical block-oriented path.

eth_syncing#

One current RPC caveat: eth_syncing is not a rich consensus-sync status surface in this source version. The handler returns false, which is a compatibility answer, not detailed Monad statesync progress.

eth_subscribe#

  1. monad-rpc reads the execution event ring
  2. EventServer fans those events out to local consumers
  3. one consumer populates ExecEventsBuffer
  4. WebSocket clients get their own broadcast subscriptions

That is why WebSocket freshness and WebSocket reliability are tied to the event-stream path, not to triedb alone.

12.16 Standard And Monad-Specific WebSocket Subscriptions Are Different#

SubscriptionKind includes both standard Ethereum-shaped and Monad-specific kinds: newHeads, logs, monadNewHeads, and monadLogs. The important distinction is that standard subscriptions hide commit-state detail behind the usual Ethereum-shaped result, while Monad-specific subscriptions keep commit state attached.

In the current WebSocket handler, standard newHeads and logs are filtered by COMMIT_STATE_FILTER = BlockCommitState::Proposed. So current standard subscriptions are effectively a proposed-head live feed, while Monad-specific subscriptions can surface all commit states explicitly.

12.17 The Event Ring Is A Live Feed, Not A Replay Log#

This point needs unusually careful wording because it affects operators and downstream consumers. The execution event ring provides fresh live events from execution; it does not provide a replayable canonical forever log. That is why two different consumers treat gaps differently.

ExecEventsBuffer#

ExecEventsBuffer::insert(...) ignores Gap events and keeps buffering whatever live events it does see. That is useful for a freshest-recent cache; it is not a proof that no events were missed.

In the main RPC startup path in this source version, the buffer is constructed as ExecEventsBuffer::new(1024). The background cache task also logs broadcast lag and continues, which reinforces the same model: this is a bounded best-effort freshness cache, not proof of continuous event history.

WebSocket Clients#

The WebSocket handler is stricter. It closes the connection on Gap and on local lag on the broadcast channel. That is the correct behavior for a live subscription feed: if the stream is known to have skipped data, the safe thing is to terminate the subscription and force the client to reconnect and resync by normal RPC.

So the right operational model is that WebSocket subscriptions are live feeds, WAL is the node’s replay log, and archive is historical block data — and these are not interchangeable.

Abridged from production code. The important detail is that standard subscriptions are proposed-filtered, while gap and lag are fatal to the WebSocket stream:

const COMMIT_STATE_FILTER: BlockCommitState = BlockCommitState::Proposed;

match events.recv().await {
    Ok(msg) => handle_notification(session, subscriptions, msg, max_response_size).await?,
    Err(broadcast::error::RecvError::Lagged(skipped_messages)) => {
        return Some(CloseReason {
            code: ws::CloseCode::Error,
            description: Some("ws server lagging, please try again later".to_string()),
        });
    }
    Err(broadcast::error::RecvError::Closed) => {
        return Some(CloseReason {
            code: ws::CloseCode::Error,
            description: Some("ws server shutdown".to_string()),
        });
    }
}

match msg {
    EventServerEvent::Gap => {
        return Err(CloseReason::from((CloseCode::Error, "websocket server gapped")));
    }
    EventServerEvent::Block { commit_state, header, transactions } => {
        for (id, _) in subscriptions
            .get(&SubscriptionKind::MonadNewHeads)
            .map(|x| x.iter())
            .unwrap_or_default()
        {
            send_notification(session, id, header.as_ref(), max_response_size).await?;
        }

        if commit_state == COMMIT_STATE_FILTER {
            for (id, _) in subscriptions
                .get(&SubscriptionKind::NewHeads)
                .map(|x| x.iter())
                .unwrap_or_default()
            {
                send_notification(session, id, header.as_ref(), max_response_size).await?;
            }
        }
    }
}

That is why a standard newHeads subscription and a Monad-specific monadNewHeads subscription are not equivalent in this source version.

12.18 The Runtime In One Paragraph#

In one paragraph: monad-node owns protocol state, sync transitions, and child executors; ParentExecutor turns many local subsystems into one node event loop; monad-rpc is a separate process that assembles whatever read and submission resources are available; and the execution repo supplies triedb, hosted execution APIs, the execution daemon, and the live event ring. That is the runtime architecture of a node in this source version.

Open These Files First#

  • monad-node/src/state.rs: startup setup and bootstrap-state loading
  • monad-node/src/main.rs: top-level node assembly, EXECUTION_DELAY = 3, child executors
  • monad-state/src/lib.rs: maybe_start_consensus(...), sync-to-live transition, DoneSync
  • monad-updaters/src/parent.rs: ParentExecutor
  • monad-rpc/src/main.rs: RPC startup graph and resource gating
  • monad-rpc/src/data/mod.rs: DataProvider, get_latest_block_number(), recent or retained or archive composition
  • monad-rpc/src/data/buffer.rs: ExecEventsBuffer
  • monad-rpc/src/websocket/handler.rs: standard versus Monad-specific subscriptions, gap or lag handling
  • monad-rpc/src/types/eth_json.rs: subscription kinds and Monad notification shape
  • cmd/monad/runloop_monad.cpp: execution daemon side of ledger ingestion
  • category/rpc/monad_executor.cpp: hosted execution surface used by RPC-style calls

What To Remember#

  • monad-node and monad-rpc are separate Rust-side processes assembled around execution-owned resources.
  • NodeState::setup() builds one concrete node from config, keys, paths, forkpoint state, and peer or bootstrap state.
  • monad-node starts in sync mode and only becomes live through maybe_start_consensus().
  • ParentExecutor fans commands out to child executors and polls them in a fixed current-code order.
  • monad-rpc loses capabilities according to which resource is missing; it is not simply all-up or all-down.
  • latest for RPC is intentionally triedb-oriented for cross-method consistency.
  • Standard WebSocket subscriptions are proposed-only in this source version; Monad-specific subscriptions preserve commit state.
  • The event ring is a live feed, and ExecEventsBuffer is a bounded freshness cache, not a replay log.

The next chapter reads the same architecture from the negative path: what happens when messages, blocks, peers, queues, or local resources fail.
