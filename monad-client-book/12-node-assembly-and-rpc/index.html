Chapter 12: Node Assembly and RPC

monad-client-book/12-node-assembly-and-rpc.md View source →

By this point we have seen the main subsystems in isolation — consensus state, execution boundaries, txpool, networking, and storage. This chapter puts them back together into long-running binaries. The two main Rust-side binaries are monad-node and monad-rpc, and one reminder has to stay in view the whole time: the execution engine still lives in the separate monad repo. So this chapter is mostly about how the Rust-side binaries are assembled around that separate execution world.

Why This Chapter Matters#

Many production bugs are not consensus bugs or EVM bugs. They are assembly bugs — the right resource was missing, the wrong process never started, a service was optional in the type graph but assumed present in the main startup path, or the data existed but not in the process serving the request. That is why assembly matters.

If you only open one node-side function first, open maybe_start_consensus() in monad-state/src/lib.rs. If you only open one RPC file first, open monad-rpc/src/main.rs. One operational footgun is worth carrying from the start: standard WebSocket newHeads and logs are currently proposed-only feeds, while Monad-specific WebSocket subscriptions preserve commit state explicitly.

12.1 Start With The Process Boundary#

The cleanest first picture is the process map itself.

flowchart LR
    Clients["wallets / apps / operators"] --> RPC["monad-rpc"]

    subgraph Rust["Rust-side binaries from monad-bft"]
        Node["monad-node"]
        RPC
    end

    subgraph Exec["execution repo surfaces"]
        ExecDaemon["monad execution daemon"]
        Triedb["triedb / MonadDB"]
        Ring["execution event ring"]

    end

    RPC -->|Unix socket| Txpool["txpool IPC"]
    Node -->|owns| Txpool
    Node -->|ledger files| ExecDaemon
    ExecDaemon --> Triedb
    ExecDaemon --> Ring
    Node -->|FFI / hosted reads| Hosted
    RPC -->|FFI / hosted reads| Hosted
    Hosted --> Triedb
    RPC --> Ring

A few of the terms in that diagram are worth pinning down before going further:

  • the execution event ring is a shared-memory ring buffer that the execution daemon writes freshest execution events into and that Rust-side processes read without blocking either side; covered in Chapter 8
  • FFI stands for foreign function interface — the arrows labeled “FFI / hosted reads” mean a Rust process calling into execution-owned C/C++ functions linked into the same process
  • IPC stands for inter-process communication — here specifically a Unix domain socket between monad-rpc and the txpool that lives inside monad-node

That picture already explains several important facts. monad-node is not the execution engine. monad-rpc is a separate process, not just a library inside the node. Transaction submission crosses a local IPC boundary. Recent RPC reads depend on execution-owned outputs. And repo boundaries and process boundaries are related, but not identical.

12.2 NodeState::setup() Turns Generic Code Into One Concrete Node#

monad-node/src/main.rs is intentionally thin. The real “become this specific node” work happens earlier in NodeState::setup(). That setup phase prepares identity keys, certificate keys, node config, forkpoint config, validator config, the ledger/triedb/WAL/IPC paths, tracing and runtime settings, and persisted peer state. (The forkpoint is the restart anchor, capturing the committed root plus the high certificate plus nearby validator context, so the node can resume consensus safely instead of from a raw “latest block” pointer — see Chapter 5 for the full shape.)

This is also where startup can replace stale local bootstrap data with fresher remote bootstrap data. So startup is not only “read local files and go.” It can also be “compare local bootstrap state against remote bootstrap state, and refresh local files when they are too stale.” That is an operational fact of the current code path, not just a documentation nicety.

12.3 monad-node Starts In Sync Mode, Not Live Consensus Mode#

After setup, the node still does not immediately act like a live validator. MonadStateBuilder starts it in ConsensusMode::Sync, with that sync-mode state anchored around the forkpoint root, the forkpoint high certificate, and the locked-epoch validator context loaded at startup. Then maybe_start_consensus() decides whether the node still needs committed block sync, state sync, or a live transition.

This is the runtime fact to keep in view: startup and sync are one continuous story. The node does not first “boot fully” and then separately “do sync.”

12.4 The Current Node Wiring Bakes In Important Runtime Facts#

Some facts in monad-node/src/main.rs are architectural, and some are just current assembly facts. The most important current wiring facts are that EXECUTION_DELAY = 3 in this checkout, the consensus-side state backend is a dedicated triedb worker thread plus cache, the txpool/router/ledger/state sync/timers/local control interfaces are all child executors under one parent executor, and the WAL is created in the node process and written before events reach state.update(...).

The ConsensusConfig built in main.rs also wires in thresholds such as statesync_to_live_threshold, live_to_statesync_threshold, and start_execution_threshold. These are runtime assembly choices in this checkout — important to understand, but not to be confused with timeless architectural laws.

12.5 ParentExecutor Is The Glue Layer#

ParentExecutor is what makes many child executors look like one event source and one command sink. That is the main orchestration seam of the node process.

Command Fan-Out#

state.update(...) returns a mixed list of commands. ParentExecutor::exec(...) splits them by subsystem and forwards each slice to the right child executor. That keeps protocol logic out of main.rs.

Poll Order#

ParentExecutor also polls child streams in a fixed order. In the current code, the order is:

  1. timer
  2. control panel
  3. ledger
  4. txpool
  5. validator-set updater
  6. timestamp updater
  7. loopback
  8. router
  9. state sync
  10. config loader

This is worth stating carefully.

Current code. Fixed poll order affects local process behavior and debugging.

Not the protocol. It is not itself the consensus protocol’s correctness rule.

That is exactly the kind of wording discipline the second half of this book needs.

12.6 The Node Runtime Is A Small Event Loop Around A Larger State Machine#

Once setup is done, the main loop is conceptually:

  1. wait for an event from ParentExecutor
  2. write the event to WAL
  3. pass it into state.update(...)
  4. execute the returned commands through ParentExecutor

That is the right way to read the process: MonadState owns most protocol behavior, ParentExecutor owns orchestration and fan-out, and main.rs owns startup and the small outer event loop. If you keep those three roles separate, the node assembly stops feeling monolithic.

That graph is more useful than a crate list because it shows which resources the node actually needs before it can become live.

12.8 monad-rpc Is Its Own Process With Its Own Resource Graph#

monad-rpc is not a thin facade embedded inside the node. It is a separate binary and its own process. That separation is useful because consensus stays focused on protocol work, RPC owns its own thread pools and caches, RPC can restart without taking down consensus, and resource availability can degrade differently on the RPC side than on the node side. The startup path in monad-rpc/src/main.rs makes that explicit.

12.9 The RPC Startup Graph#

The main RPC startup graph looks like this:

flowchart TD
    Args["CLI args + node config"] --> Main["monad-rpc main"]
    Main --> TxBridge["optional txpool bridge"]
    Main --> TriedbEnv["optional TriedbEnv"]
    Main --> Archive["optional archive reader"]
    Main --> EthCall["optional EthCallHandler"]
    Main --> EventRing["optional event ring client"]
    EventRing --> EventServer["EventServer"]
    EventServer --> Buffer["ExecEventsBuffer"]
    TriedbEnv --> Data["DataProvider"]
    Archive --> Data
    Buffer --> Data
    Data --> Handlers["JSON-RPC handlers"]
    EventServer --> WS["WebSocket server"]

That graph has an important consequence: not every RPC capability depends on exactly the same local resource set.

12.10 Be Precise About Type Capability Versus Main Startup Wiring#

The right wording pattern here is: separate architecture from current code from runtime assembly fact. For example, DataProvider<TriedbEnv> can be constructed with or without an event buffer, and can also be constructed with or without an archive reader. But in the current main startup path, if there is no triedb path then there is no TriedbEnv, if there is no TriedbEnv then there is no DataProvider, and if WebSocket support is enabled without an execution event path, startup panics.

So the precise statement is that DataProvider is not a type-system law that requires every auxiliary resource, and the current main RPC wiring still makes triedb the hard prerequisite for the main chain-state read surface. That distinction matters because readers otherwise turn current startup wiring into false architectural absolutes.

12.11 The RPC Process Degrades By Resource#

Different missing resources disable different capabilities.

Missing resourceWhat degrades
txpool IPC pathtransaction submission is unavailable
triedb pathmost stateful chain reads are unavailable because the main DataProvider is not built
archive readerhistorical block-oriented reads are limited to recent retained data
execution event pathWebSocket server cannot run; freshest event-buffered reads disappear
eth-call handlerhosted execution surfaces such as eth_call and trace-style simulation are unavailable

This table is a better mental model than “RPC is either up or down.” Often the process is up — only part of its capability graph is missing.

Architecture, Current Code, Current Caveat#

Architecture monad-node is the protocol process and monad-rpc is a separate edge process. Each assembles a different capability graph around execution-owned resources.

Current code maybe_start_consensus() gates the node’s live transition, while monad-rpc/src/main.rs conditionally assembles tx submission, triedb, archive, hosted execution, and event-ring-backed WebSocket resources.

Current caveat Standard WebSocket newHeads and logs are currently filtered to BlockCommitState::Proposed. Readers who want explicit commit state need the Monad-specific subscription variants.

12.12 One Important latest Nuance#

DataProvider::get_latest_block_number() deliberately returns triedb’s latest proposed block number, not the event buffer’s freshest seen height. The code comment explains why.

There is a race between the live event buffer and triedb-backed state queries. If a wallet calls eth_getBlockByNumber and then immediately calls eth_getBalance, RPC wants those reads to line up more predictably with triedb-backed state. So this is a good example of RPC preferring internal read-surface consistency over whichever component saw the newest event first.

12.13 Four Request Walkthroughs#

The easiest way to make assembly concrete is to follow a few requests end to end.

eth_sendRawTransaction#

  1. client sends JSON-RPC to monad-rpc
  2. RPC uses the txpool bridge over the Unix socket
  3. the txpool inside monad-node performs ingress validation
  4. later, a leader may select that transaction into a proposal

That means transaction submission is really RPC edge in one process and txpool ownership in another process.

eth_getBalance#

  1. request arrives at monad-rpc
  2. handler resolves a block tag or hash into a triedb BlockKey
  3. TriedbEnv reads retained state from triedb
  4. response returns without involving the archive path

The important caveat is that old balance reads only work while the needed version is still retained.

eth_getTransactionReceipt#

  1. RPC first tries ExecEventsBuffer
  2. if not found there, it tries triedb lookup data
  3. if still not found and archive is configured, it tries archive index data

So the receipt path is a good example of a composed read surface: freshest recent path, then retained recent path, then historical block-oriented path.

eth_subscribe#

  1. monad-rpc reads the execution event ring
  2. EventServer fans those events out to local consumers
  3. one consumer populates ExecEventsBuffer
  4. WebSocket clients get their own broadcast subscriptions

That is why WebSocket freshness and WebSocket reliability are tied to the event-stream path, not to triedb alone.

12.14 Standard And Monad-Specific WebSocket Subscriptions Are Different#

SubscriptionKind includes both standard Ethereum-shaped and Monad-specific kinds: newHeads, logs, monadNewHeads, and monadLogs. The important distinction is that standard subscriptions hide commit-state detail behind the usual Ethereum-shaped result, while Monad-specific subscriptions keep commit state attached.

In the current WebSocket handler, standard newHeads and logs are filtered by COMMIT_STATE_FILTER = BlockCommitState::Proposed. So current standard subscriptions are effectively a proposed-head live feed, while Monad-specific subscriptions can surface all commit states explicitly.

12.15 The Event Ring Is A Live Feed, Not A Replay Log#

This point needs unusually careful wording because it affects operators and downstream consumers. The execution event ring provides fresh live events from execution; it does not provide a replayable canonical forever log. That is why two different consumers treat gaps differently.

ExecEventsBuffer#

ExecEventsBuffer::insert(...) ignores Gap events and keeps buffering whatever live events it does see. That is useful for a freshest-recent cache; it is not a proof that no events were missed.

WebSocket Clients#

The WebSocket handler is stricter. It closes the connection on Gap and on local lag on the broadcast channel. That is the correct behavior for a live subscription feed: if the stream is known to have skipped data, the safe thing is to terminate the subscription and force the client to reconnect and resync by normal RPC.

So the right operational model is that WebSocket subscriptions are live feeds, WAL is the node’s replay log, and archive is historical block data — and these are not interchangeable.

12.16 One Final Mental Model#

If you want one compact bottom-up picture, use this: monad-node owns protocol state, sync transitions, and child executors; ParentExecutor turns many local subsystems into one node event loop; monad-rpc is a separate process that assembles whatever read and submission resources are available; and the execution repo supplies triedb, hosted execution APIs, the execution daemon, and the live event ring. That is the real runtime architecture of a node in this checkout.

Open These Files First#

  • monad-node/src/state.rs: startup setup and bootstrap-state loading
  • monad-node/src/main.rs: top-level node assembly, EXECUTION_DELAY = 3, child executors
  • monad-state/src/lib.rs: maybe_start_consensus(...), sync-to-live transition, DoneSync
  • monad-updaters/src/parent.rs: ParentExecutor
  • monad-rpc/src/main.rs: RPC startup graph and resource gating
  • monad-rpc/src/data/mod.rs: DataProvider, get_latest_block_number(), recent or retained or archive composition
  • monad-rpc/src/data/buffer.rs: ExecEventsBuffer
  • monad-rpc/src/websocket/handler.rs: standard versus Monad-specific subscriptions, gap or lag handling
  • monad-rpc/src/types/eth_json.rs: subscription kinds and Monad notification shape
  • cmd/monad/runloop_monad.cpp: execution daemon side of ledger ingestion
  • category/rpc/monad_executor.cpp: hosted execution surface used by RPC-style calls
