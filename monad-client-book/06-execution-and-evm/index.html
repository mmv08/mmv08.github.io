Chapter 6: Execution Boundary and Process Architecture

monad-client-book/06-execution-and-evm.md View source →

Up to this point, the book mostly stayed inside monad-bft. That was the right starting point, because consensus decides what the chain means. But a Monad node does not execute blocks inside one Rust state machine. Execution lives in a different repo, often in a different process, and is also reused through hosted APIs and shared output surfaces.

This chapter introduces the runtime shape: one consensus-side control plane, one execution system, and several bridges between them.

Why This Chapter Matters#

Consensus orders a block, execution validates and executes that block, and RPC later serves reads about that block. These three steps do not all live in one program. They cross repository boundaries, process boundaries, FFI boundaries, local IPC boundaries, and live-output boundaries.

Two acronyms show up repeatedly in this chapter. FFI stands for foreign function interface, meaning Rust code reaches into the execution C/C++ library and calls its functions directly inside the same process, without an RPC hop. IPC stands for inter-process communication, here specifically Unix domain sockets used between two cooperating processes on the same machine. These two boundaries appear repeatedly in the code that follows.

If you only open one execution file first, open cmd/monad/runloop_monad.cpp. That is where ordered-block ingestion, delayed-result validation, and execution-side publication meet.

6.1 The Split At A Glance#

The clean high-level split is:

RepoMain job
monad-bftconsensus, validator networking, txpool, ledger persistence, node assembly, RPC assembly
monadEVM execution, triedb or MonadDB, execution-side Monad rules, execution daemon, hosted execution APIs

So the short execution-side restatement is: one consensus-side control plane, one execution-side state-transition system, and several bridges between them.

6.2 libmonad_execution Is The Shared Execution Core#

Most execution code is built around one shared execution library core. In the build system, the CMake target is monad_execution, and it produces the libmonad_execution library file that every other execution surface links against. This book uses that file name when referring to the shared core.

That matters because it explains why execution shows up in more than one runtime shape without changing ownership. The same execution-owned core is used in three modes: daemon mode (the stand-alone monad execution daemon), hosted mode (execution APIs loaded into Rust-side processes), and developer or test tooling inside the execution repo.

The execution repo owns one execution library core, and that core can be consumed in several runtime modes. This is why repo boundary and process boundary are related but not identical in Monad.

Abridged from production code. The important detail is that the daemon links a larger shared execution library:

# CMakeLists.txt
add_library(monad_execution)
target_link_libraries(
  monad_execution
  PUBLIC monad_core
         monad_async
         monad_trie
         monad_execution_ethereum
         monad_execution_native
         monad_rpc
         monad_statesync
         monad-vm)

# cmd/CMakeLists.txt
add_executable(
  monad
  monad/main.cpp
  monad/runloop_monad.cpp
  monad/runloop_monad_ethblocks.cpp)

target_link_libraries(monad PRIVATE monad_execution CLI11::CLI11)

This shows the structure of the runtime split: monad the executable is an assembly surface over libmonad_execution.

6.3 There Is More Than One Boundary#

Several different boundaries exist at once.

BoundaryExampleWhat crosses it
repo boundarymonad-bft <-> monadownership, source layout, build integration
process boundarymonad-node -> ledger files -> execution daemonordered blocks
local IPC boundarymonad-rpc -> txpool Unix sockettransaction submission
FFI / hosted API boundaryRust wrappers -> execution-owned APIstriedb reads, eth_call, validator-set reads
live-output boundaryexecution daemon -> event ringfreshest execution events

When reading a file, ask two questions: where is execution, and which execution boundary is this code crossing right now?

6.4 The Three Main Ways Execution Is Consumed#

Execution is consumed in three main modes.

Stand-Alone Daemon Mode#

The binary under cmd/monad is a long-running execution service.

In that mode:

  1. monad-node writes ordered consensus blocks to the ledger
  2. the execution daemon reads those blocks from disk
  3. it validates and executes them
  4. it writes recent outputs into triedb
  5. it emits fresh execution events

Hosted Library Mode#

Parts of the execution repo are also linked into Rust-side binaries. That is why monad-node and monad-rpc can use execution-owned services for triedb reads, validator-set reads, eth_call, and event-stream consumption.

Output-Surface Mode#

Execution is also consumed indirectly through the surfaces it keeps fresh: triedb as the retained recent execution database, and the execution event ring as the freshest live stream. This third mode matters because many node behaviors are not “call execution now” but “read what execution already produced.”

6.5 The Execution Daemon Is Not The Node’s Network Identity#

The execution daemon does not run consensus, does not own the validator’s public network identity, and does not speak the validator consensus protocol to peers. The validator’s network identity belongs to the Rust-side node process. Execution is a local partner service that provides block execution, recent-state persistence, and execution-side query logic.

That is why “consensus client” and “execution client” in Monad do not map perfectly onto the language many Ethereum readers expect. Modern Ethereum also splits consensus and execution, but Monad pushes the split further into delayed execution, richer execution-side read surfaces, and more direct execution-backed validator-state reads.

6.6 The Main Runtime Loop#

This is the simplest accurate picture:

flowchart LR
    Node["monad-node"] -->|writes ordered blocks| Ledger["ledger directory"]
    Ledger -->|reads new blocks| Exec["monad execution daemon"]
    Exec -->|writes recent state| Triedb["triedb / MonadDB"]
    Exec -->|publishes live events| Ring["execution event ring"]
    Node -->|hosted reads| Triedb
    RPC["monad-rpc"] -->|hosted reads| Triedb
    RPC -->|live subscriptions| Ring

The direction matters: consensus makes an ordered block exist first, execution consumes that ordered block later, and read paths consume execution outputs after that. This is the process-level version of delayed execution.

One run-loop detail is useful before reading cmd/monad/runloop_monad.cpp: when execution is behind, it walks finalized ledger history first. When it is caught up, it can also follow the proposed head. That is why execution can produce fresh proposed outputs while still respecting finalized canonical history.

Abridged from production code. The important detail is that the execution daemon’s CLI names the storage, state-sync, and optional live-event surfaces:

The event ring is therefore an optional configured output path, not an unconditional property of every execution daemon run.

6.7 One Transaction Across The Boundary#

It helps to watch one transaction cross the ownership lines.

sequenceDiagram
    participant Client as wallet or app
    participant RPC as monad-rpc
    participant Pool as txpool
    participant Node as monad-node
    participant Ledger as ledger files
    participant Exec as execution daemon
    participant DB as triedb
    participant Ring as event ring

    Client->>RPC: eth_sendRawTransaction
    RPC->>Pool: tx over Unix socket
    Pool->>Node: sequenceable candidate
    Node->>Ledger: persist ordered block
    Exec->>Ledger: read ordered block
    Exec->>Exec: validate and execute
    Exec->>DB: write recent state and block data
    Exec->>Ring: publish fresh events
    RPC->>DB: answer later retained reads
    RPC->>Ring: push subscriptions

A few important consequences fall out of this flow. RPC does not directly mutate consensus state, the execution daemon does not decide ordering, and later reads usually come from triedb or the event ring rather than the ledger.

Abridged from production code. The important details are that execution consumes a BFT header/body, derives sender context, validates cheap structure first, runs EVM execution, commits triedb state, then validates the output header it produced. The tracer setup and parent-cache lookup are compressed here so the boundary order stays visible:

Result<BlockExecOutput> propose_block(
    bytes32_t const &block_id,
    MonadConsensusBlockHeader const &consensus_header,
    Block block,
    BlockHashChain &block_hash_chain,
    MonadChain const &chain,
    DbCache &db,
    vm::VM &vm,
    fiber::PriorityPool &priority_pool,
    bool const is_first_block,
    bool const enable_tracing,
    BlockCache &block_cache)
{
    auto const &block_hash_buffer =
        block_hash_chain.find_chain(consensus_header.parent_id());

    BOOST_OUTCOME_TRY(static_validate_consensus_header(consensus_header));
    BOOST_OUTCOME_TRY(static_validate_block<traits>(chain, block));

    auto const recovered_senders =
        recover_senders(block.transactions, priority_pool);
    auto const recovered_authorities =
        recover_authorities(block.transactions, priority_pool);

    std::vector<Address> senders(block.transactions.size());
    for (unsigned i = 0; i < recovered_senders.size(); ++i) {
        if (recovered_senders[i].has_value()) {
            senders[i] = recovered_senders[i].value();
        }
        else {
            return TransactionError::MissingSender;
        }
    }

    auto senders_and_authorities =
        combine_senders_and_authorities(senders, recovered_authorities);
    block_cache.emplace(
        block_id,
        BlockCacheEntry{
            .block_number = block.header.number,
            .parent_id = consensus_header.parent_id(),
            .senders_and_authorities = std::move(senders_and_authorities)});

    BOOST_OUTCOME_TRY(
        static_validate_monad_body<traits>(senders, block.transactions));

    std::vector<std::vector<CallFrame>> call_frames{block.transactions.size()};
    std::vector<std::unique_ptr<CallTracerBase>> call_tracers{
        block.transactions.size()};
    std::vector<std::unique_ptr<trace::StateTracer>> state_tracers{
        block.transactions.size()};
    // The full function fills one call tracer and one state tracer per tx here.

    auto const
        &[grandparent_senders_and_authorities,
          parent_senders_and_authorities] = [&] {
            if (block.header.number > 1) {
                bytes32_t const &parent_id = consensus_header.parent_id();
                BlockCacheEntry const &parent_entry = block_cache.at(parent_id);
                if (block.header.number > 2) {
                    bytes32_t const &grandparent_id = parent_entry.parent_id;
                    BlockCacheEntry const &grandparent_entry =
                        block_cache.at(grandparent_id);
                    return std::tuple{
                        grandparent_entry.senders_and_authorities,
                        parent_entry.senders_and_authorities};
                }
                return std::tuple{
                    empty_senders_and_authorities,
                    parent_entry.senders_and_authorities};
            }
            return std::tuple{
                empty_senders_and_authorities, empty_senders_and_authorities};
        }();

    ChainContext<traits> const chain_context{
        .grandparent_senders_and_authorities = grandparent_senders_and_authorities,
        .parent_senders_and_authorities = parent_senders_and_authorities,
        .senders_and_authorities = block_cache.at(block_id).senders_and_authorities,
        .senders = senders,
        .authorities = recovered_authorities,
    };

    BlockExecOutput exec_output;
    BlockMetrics block_metrics;
    BlockState block_state(db, vm);
    BOOST_OUTCOME_TRY(auto const results, execute_block<traits>(
        chain, block, senders, recovered_authorities, block_state,
        block_hash_buffer, priority_pool.fiber_group(), block_metrics,
        call_tracers, state_tracers, chain_context));

    auto [state, code] = std::move(block_state).release();
    CommitBuilder builder(block.header.number);
    builder.add_state_deltas(*state)
        .add_code(code)
        .add_receipts(results)
        .add_transactions(block.transactions, senders)
        .add_call_frames(call_frames);

    db.commit(block_id, builder, block.header, *state, [&](BlockHeader &h) {
        h.receipts_root = db.receipts_root();
        h.state_root = db.state_root();
        h.transactions_root = db.transactions_root();
        h.gas_used = results.empty() ? 0 : results.back().gas_used;
    });

    exec_output.eth_header = db.read_eth_header();
    BOOST_OUTCOME_TRY(
        validate_live_execution_outputs(block.header, exec_output.eth_header));

    return exec_output;
}

This is the execution boundary in miniature: consensus supplies the ordered input, execution owns the state transition and output publication.

6.8 What Each Consumption Mode Can And Cannot Do#

This table is a good sanity check.

ModeCan doCannot do
execution daemonconsume ordered blocks, execute them, write triedb, emit eventsbecome the validator’s P2P identity
hosted triedb readeranswer retained recent execution readsadvance chain execution by itself
hosted eth_call executorsimulate execution against chosen statecommit a real block
event-ring consumerobserve freshest execution outputreplace durable recent-state storage

Each mode does its own job. Treating one as a substitute for another mixes layers that the code keeps separate.

6.9 The Execution Repo Is Larger Than “The C++ Side”#

The execution repo is primarily C++, but it is more than one daemon binary plus helper code. It contains several major subsystems:

DirectoryWhat lives there
docsexecution architecture and developer overview
cmd/monadexecution daemon assembly and run loops
category/executionblock execution logic and Monad-specific execution rules
category/mpttriedb or MonadDB
category/rpchosted execution APIs such as eth_call
category/statesyncexecution-side state sync
testexecution-side tests, Ethereum fixtures, VM tests

So a better summary is one execution repo, one shared execution core, and several execution-facing surfaces.

6.10 Hosted Mode Does Not Erase The Boundary#

Rust-side triedb readers and eth_call helpers run inside Rust binaries, but they do not move execution ownership into the Rust side. Hosted mode means the same execution repo is reused through libraries, and some execution services run in-process while ownership remains with the execution repo. The repo boundary is therefore stable, while the process boundary depends on which surface is being used.

6.11 Architecture, Current Code, Current Caveat#

Architecture Consensus orders blocks quickly. Execution consumes those ordered blocks later, maintains retained recent execution state, and publishes execution outputs for the rest of the node.

Current code The main ordered-block handoff is ledger-file based, while many recent reads and simulations use hosted execution libraries.

Current caveat Because monad-bft vendors execution code through the monad-execution/ submodule, the source tree can look more unified than the runtime ownership really is.

Then Open These#

  • monad-node/src/main.rs: consensus-side node wiring and execution delay constant

  • monad-rpc/src/data/mod.rs: one Rust-side consumer of execution-owned outputs

What To Remember#

  • Monad execution lives in a separate repo and often in a separate process.
  • The execution repo owns a shared execution core reused in daemon and hosted modes.
  • Repo, process, IPC, FFI, and live-output boundaries all matter, and they are not interchangeable.
  • The execution daemon is not the validator’s external network identity.
  • The cleanest runtime picture is: consensus writes ordered blocks, execution consumes finalized history when catching up and proposed-head work when caught up, and the rest of the node consumes execution outputs after that.
