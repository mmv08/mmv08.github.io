Chapter 8: Execution Services — Triedb, Event Rings, and Hosted APIs

monad-client-book/08-execution-services-triedb-events-and-hosted-apis.md View source →

The previous chapter ended at “execution produced an output.” This chapter asks the practical follow-up: how does the Rust side actually consume that output?

There are four big pieces. Triedb is the durable recent execution database; it is also referred to as MonadDB in some docs and code, and the two names are the same system — a Merkle-trie-backed key-value store holding recent execution state and recent block-associated objects. Around triedb there are narrow and broad Rust-side adapters. The execution event ring is a shared-memory ring buffer that the execution daemon writes freshest execution events into, and that Rust-side consumers read from without blocking either side. And hosted execution APIs such as eth_call (the Ethereum JSON-RPC method for running a contract function in a sandboxed read-only call without sending a real transaction) round out the list. This chapter explains why not every “latest” answer comes from the same place.

Why This Chapter Matters#

Engineers new to the codebase usually make one incorrect assumption first: that there is one database that answers everything. That is not how the node works. Recent execution state, freshest recent events, and long-term historical block data live on different surfaces and are consumed through different adapters. Once that clicks, the RPC chapter becomes much easier.

If you only inspect one Rust module first, inspect DataProvider in monad-rpc/src/data/mod.rs. It is the narrowest place where recent buffers, triedb, and archive composition become concrete.

8.1 Three Read Surfaces, Not One#

The cleanest starting table is this one:

SurfaceWhat it is best atWhat it is not
triedbretained recent execution state and recent block-associated execution datainfinite historical state
event ringfreshest live execution updatesdurable retained state
archiveolder blocks, receipts, traces, and indexesgeneral old-world-state reconstruction

The rest of the chapter just makes that table concrete.

8.2 Triedb Is The Durable Recent Execution Database#

Triedb is the answer to questions like “what is the current retained balance of this account?”, “what code is currently at this address?”, “what recent receipt belongs to this transaction?”, and “what recent header belongs to this hash?”

The important word is retained. Triedb is recent-state infrastructure, not an unlimited historical archive.

Main Namespaces#

A nibble is half a byte, or 4 bits. Triedb is a Merkle-Patricia-style trie whose paths are walked half-byte at a time, so keys are partitioned into logical namespaces by their leading nibble. The schema documented in the execution repo and mirrored in docs/storage_paths.md is:

Prefix nibbleMeaning
0state
1code
2receipts
3transactions
4block header
5withdrawals
6ommers
7tx-hash lookup
8block-hash lookup
9call frames

That list matters because it shows triedb is more than “world state.” It also stores recent block-oriented objects RPC cares about.

8.3 Consensus Reads Triedb Through A Narrow Worker-Thread Boundary#

Consensus is intentionally not allowed to poke triedb from arbitrary places. The main path is:

MonadState
  -> StateBackend trait
  -> StateBackendThreadClient
  -> StateBackendCache
  -> TriedbReader
  -> triedb

This shape gives consensus two things: blocking reads move off the main async event path, and repeated reads can hit a small cache first.

StateBackendThreadClient Is Deliberately Small And Bounded#

The implementation uses one dedicated worker thread, a synchronous caller surface, and a bounded request channel with MAX_INFLIGHT_REQUESTS = 16. That limit is not a random tuning detail — it exists so state access cannot sprawl across consensus code and silently become an unbounded backpressure risk. This is a good example of a design that is simultaneously architectural, operational, and defensive.

The Special Validator-Set Read#

One especially important request here is read_valset_at_block(...). That is not a generic key lookup — it is the dedicated bridge into the execution-side staking reader from the last chapter.

8.4 RPC Uses A Broader Adapter: TriedbEnv#

RPC needs a richer read surface than consensus, so it uses a richer adapter. TriedbEnv does more than expose point reads: it maintains latest finalized, voted, and proposed block metadata, runs a polling path that keeps those keys fresh, and holds small hot-object caches.

That makes the division clean. TriedbReader is the narrow consensus-facing surface; TriedbEnv is the broader RPC-facing surface. This is why not every triedb consumer sees the same interface even though the underlying database is the same.

8.5 Hosted eth_call Is Its Own Execution Path#

eth_call is the hosted execution service that makes this boundary easiest to see. The execution repo exposes a dedicated RPC executor interface under category/rpc/monad_executor.*, and on the Rust side, monad-rpc wraps it through EthCallHandler. That handler is configured with separate pools such as a low-gas pool, a high-gas pool, and block-oriented context resolution, and it also applies concurrency backpressure.

So eth_call is not best understood as a thin synchronous FFI jump. It is better understood as a hosted execution subsystem with its own scheduling and result-shaping concerns.

8.6 The Event Ring Is A Live Stream, Not A Database#

The execution event ring is the freshest output surface. At a high level, the execution daemon publishes events into a shared ring, and Rust-side code subscribes to those events. This is the right surface for subscriptions, very recent block or receipt visibility, and recent event buffering. It is not the durable recent database. That distinction is a mental model the later RPC chapter depends on.

8.7 Live-Stream Guarantees: Fresh, But Gap-Sensitive#

This is the part many walkthroughs skip. The event ring is not only fresher than triedb — it is also gap-sensitive.

In current code, WebSocket handlers treat Gap as fatal for that subscription stream, WebSocket handlers also close when they lag the broadcast channel badly enough, and ExecEventsBuffer itself ignores Gap on insert because it is only a recent cache, not a replay protocol. So the event ring should be understood as a live feed, not a durable canonical replay log. That distinction matters a lot for subscription reasoning.

Do not over-read the buffer ExecEventsBuffer ignoring Gap means “keep the freshest cache entries you still have.” It does not mean the node proved continuity of the stream.

8.8 ExecEventsBuffer Is One Bounded In-Memory Cache#

The event buffer in monad-rpc is easy to describe incorrectly. It is not one proposed database plus one voted database plus one finalized database. It is one bounded in-memory recent buffer, keyed by block height, block hash, and tx hash, plus three latest-height trackers for proposed, voted, and finalized.

What Happens On Insert#

When a new block event arrives, the buffer ignores Verified events entirely, updates the latest proposed/voted/finalized atomics, stores the full recent block by height, stores the block-hash-to-height lookup, and stores the tx-hash-to-receipt location lookup. If another block later arrives at the same height, the old same-height block can be replaced. That tells you exactly what this buffer is — a bounded recent live cache, not a stable historical store.

8.9 Triedb Versus Event Ring#

This is the shortest reliable comparison:

QuestionFreshest useful sourceAuthoritative retained source
what should I push to subscribers right now?event ring or ExecEventsBufferlive stream plus recent cache
what is the retained current balance or storage slot?n/atriedb
what is the recent receipt for this tx?ExecEventsBuffer firsttriedb after that
what is the old receipt for this tx?usually nonearchive

That is why “freshest” and “authoritative retained state” are not always the same thing.

8.10 DataProvider Is A Runtime Composition Layer#

DataProvider in monad-rpc/src/data/mod.rs is the object that combines:

  • optional recent event buffering
  • triedb access
  • optional archive access

In the main RPC startup path, it is constructed like this:

let data_provider = triedb_env.map(|t| DataProvider::new(event_buffer, t, archive_reader));

That wording matters.

Current code In the main RPC startup path, the combined DataProvider exists only when triedb exists.

Runtime assembly fact This is true of the main monad-rpc wiring in this checkout.

Current caveat The type itself can still be constructed directly in tests with mock triedb-like implementations, so this is not a type-system impossibility.

8.11 Popular RPC Methods Map To Different Backing Surfaces#

One explicit matrix is worth keeping handy.

Method or query shapeMain path today
eth_blockNumbertriedb metadata only; latest proposed height from triedb
eth_getBalancetriedb only; no general archive fallback for old state
eth_getCodetriedb only; no general archive fallback for old code
eth_getTransactionReceiptExecEventsBuffer -> triedb -> archive
eth_getTransactionByHashExecEventsBuffer -> triedb -> archive
eth_getLogsrecent path from buffer or triedb, older path may use archive indexes as prefilter and archive receipts as truth
eth_callTriedbEnv resolves block context, then hosted execution runs

That table is one of the quickest ways to stop hand-waving about “the RPC database.”

8.12 Why eth_blockNumber Prefers Triedb#

This specific example captures the design philosophy well. DataProvider::get_latest_block_number() returns triedb’s latest proposed block number, not the freshest event-buffer height.

The reason is consistency. A wallet that calls eth_blockNumber and then immediately calls eth_getBalance should land on a block context the server can actually answer authoritatively from its retained recent-state surface. So the client prefers a slightly less aggressive notion of latest over cross-method inconsistency.

8.13 Archive Is Not A General State Fallback#

Archive is covered in more detail in the storage chapter, but one fact belongs here already because it directly affects RPC reasoning. Archive can answer old blocks, old receipts, old traces, and tx-index lookups. Archive does not generally reconstruct old balances, old storage slots, old code, or old nonces. That is why state queries and history queries have different failure modes.

8.14 Architecture, Current Code, Current Caveat#

Architecture Execution publishes two main read surfaces: durable retained recent state in triedb, and freshest live events in the event ring.

Current code Consensus uses a narrow worker-thread triedb boundary, while RPC uses TriedbEnv, optional recent buffering, and optional archive readers through DataProvider.

Current caveat The same high-level method may read from different backends depending on freshness, retention, and which optional resources are configured at runtime.

What To Remember#

  • Triedb is the durable recent execution database.
  • The event ring is a live stream, not the same thing as triedb.
  • ExecEventsBuffer is one bounded recent cache with commit-state trackers, not three separate databases.
  • Consensus reads execution state through a narrow worker-thread boundary on purpose.
  • RPC uses a broader adapter and composes recent buffer, triedb, and archive differently for different methods.
  • eth_blockNumber intentionally prefers triedb’s latest proposed height for cross-method consistency.
  • Subscriptions are fed by a live stream that is fresher than triedb but also gap-sensitive.
  • Archive is a fallback for some historical query classes, not a general historical state engine.
