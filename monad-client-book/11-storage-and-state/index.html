Chapter 11: Storage and State

monad-client-book/11-storage-and-state.md View source →

Consensus chooses the chain. Storage decides what the node can still prove, replay, serve, and recover after the process restarts. Monad does not put all of that into one database — that is the first storage fact to internalize.

Instead it splits durable data by job: triedb keeps retained recent execution state and recent execution-derived block data, the ledger keeps recent consensus blocks and head markers, the WAL keeps the local event stream for replay, and archive storage keeps older block-oriented history and indexes.

WAL means write-ahead log: the node writes an event there before applying it, so the event stream can be replayed later. If you keep those layers separate, later RPC and sync behavior becomes much easier to reason about.

Why This Chapter Matters#

In some blockchain clients, “archive mode” is a single setting that implies every old query works forever. Monad does not work that way. Retained recent state, durable recent consensus history, replay logs, and older archived blocks, receipts, traces, and indexes are related but not interchangeable.

11.1 Use This Chapter For The Storage Map#

This chapter gives the path names and logical key shapes that matter for reading the client. Use the source files at the end of the chapter when you need implementation-level backend details.

That is the real storage map.

11.3 Triedb Is The Retained Recent Execution Store#

Triedb, or MonadDB in execution-oriented language, is the retained recent execution database. It stores accounts, storage slots, code, recent receipts, recent transactions, recent block headers, tx-hash and block-hash lookup data, and call-frame data. This is why both consensus and RPC depend on it.

Triedb Is Versioned#

A triedb read is not only “give me the latest value.” It can also mean “give me the value at this retained block version.” For proposal views, there is one more wrinkle: two competing proposals at the same height must not collide. That is why proposal reads carry both a numeric block version and a proposal-specific block identity. The important mental model is that triedb is not one mutable latest-state map; it is a versioned recent-state store with separate finalized and proposal views.

Triedb Has Several Logical Namespaces#

The logical key prefixes include namespaces such as:

That table is useful because it reminds you that triedb is more than the account trie — it is also part of the recent block-oriented RPC surface.

Abridged from production code. The important details are that triedb keys encode the version first, then the namespace:

const STATE_NIBBLE: u8 = 0;
const CODE_NIBBLE: u8 = 1;
const RECEIPT_NIBBLE: u8 = 2;
const TRANSACTION_NIBBLE: u8 = 3;
const BLOCK_HEADER_NIBBLE: u8 = 4;
const TRANSACTION_HASH_NIBBLE: u8 = 7;
const BLOCK_HASH_NIBBLE: u8 = 8;
const CALL_FRAME_NIBBLE: u8 = 9;

const PROPOSAL_NIBBLE: u8 = 0;
const FINALIZED_NIBBLE: u8 = 1;

pub enum Version {
    Proposal(BlockId),
    Finalized,
}

pub enum KeyInput<'a> {
    State,
    Address(&'a [u8; 20]),
    Storage(&'a [u8; 20], &'a [u8; 32]),
    CodeHash(&'a [u8; 32]),
    ReceiptIndex(Option<u64>),
    TxIndex(Option<u64>),
    BlockHeader,
    TxHash(&'a [u8; 32]),
    BlockHash(&'a [u8; 32]),
    CallFrame,
}

pub fn create_triedb_key(version: Version, key: KeyInput) -> (Vec<u8>, u8) {
    let mut key_nibbles = vec![];

    match version {
        Version::Proposal(block_id) => {
            key_nibbles.push(PROPOSAL_NIBBLE);
            for byte in block_id.0.0 {
                key_nibbles.push(byte >> 4);
                key_nibbles.push(byte & 0xF);
            }
        }
        Version::Finalized => key_nibbles.push(FINALIZED_NIBBLE),
    }

    match key {
        KeyInput::Address(addr) => {
            key_nibbles.push(STATE_NIBBLE);
            let hashed_addr = keccak256(addr);
            for byte in hashed_addr {
                key_nibbles.push(byte >> 4);
                key_nibbles.push(byte & 0xF);
            }
        }
        KeyInput::BlockHeader => key_nibbles.push(BLOCK_HEADER_NIBBLE),
        KeyInput::TxHash(tx_hash) => {
            key_nibbles.push(TRANSACTION_HASH_NIBBLE);
            for byte in tx_hash {
                key_nibbles.push(byte >> 4);
                key_nibbles.push(byte & 0xF);
            }
        }
        KeyInput::BlockHash(block_hash) => {
            key_nibbles.push(BLOCK_HASH_NIBBLE);
            for byte in block_hash {
                key_nibbles.push(byte >> 4);
                key_nibbles.push(byte & 0xF);
            }
        }
        KeyInput::CallFrame => key_nibbles.push(CALL_FRAME_NIBBLE),
    }

    let num_nibbles: u8 = match key_nibbles.len().try_into() {
        Ok(len) => len,
        Err(_) => return (vec![], 0),
    };
    if !num_nibbles.is_multiple_of(2) {
        key_nibbles.push(0);
    }
    let key = key_nibbles
        .chunks(2)
        .map(|chunk| (chunk[0] << 4) | chunk[1])
        .collect();

    (key, num_nibbles)
}

This is the storage reason proposal reads need a block identity while finalized reads do not.

11.4 Consensus And RPC Consume Triedb Through Different Adapters#

The same underlying DB is exposed through different Rust-side adapters.

Consensus Side#

Consensus reads go through a narrower path:

StateBackendThreadClient -> StateBackendCache -> TriedbReader -> triedb

That path keeps blocking work on a dedicated worker thread and gives consensus a smaller, more controlled read surface.

RPC Side#

RPC uses TriedbEnv. TriedbEnv is broader: it tracks latest proposed, voted, and finalized metadata, exposes more query-style APIs, and maintains small caches used by the RPC process. So when you see “triedb read,” always ask whether it is a consensus-side narrow read or an RPC-side broader read. That distinction matters throughout the rest of the book.

11.5 The Ledger Stores Consensus Blocks, Not Account State#

The ledger is the durable recent block store used by monad-node, block sync, and the execution daemon. At the filesystem level, FileBlockPersist creates headers/ and bodies/ directories, and inside headers/ it also maintains proposed_head, voted_head, and finalized_head.

Those head markers are symlinks. A symlink, or symbolic link, is a tiny filesystem entry that points at another file instead of containing its own payload.

That matters here because a head update can be atomic even though the target block file already exists. The update path creates a temporary <head>.wip symlink to the new target and then renames it into place. So the atomic unit is “install a new symlink by rename,” not “mutate an existing symlink in place.”

What The Files Contain#

Each header file is named by hex(block_id), and each body file is named by hex(body_id). The file contents are raw RLP.

RLP (Recursive Length Prefix) is Ethereum’s compact canonical encoding for arbitrary nested byte strings and lists, used everywhere blocks, headers, and transactions are serialized on the wire or on disk. The persistence layer here stores the same byte-level encoding that goes over the network: header files store ConsensusBlockHeader, and body files store ConsensusBlockBody.

That is a very direct storage model: open file, read bytes, decode exact structure.

The Ledger Write Order Protects Coherency#

The most important write rule is that the body is written first and the header is written second. That way a header never points to a body file that is missing. Then the head markers advance as consensus moves through commit states. That is why the ledger is not only a finalized block store: it also needs to remember broader recent consensus history because execution handoff, block sync, and restart recovery depend on it.

Abridged from production code. The important details are the file layout, RLP payloads, and atomic symlink head update:

pub const BLOCKDB_HEADERS_PATH: &str = "headers";
const BLOCKDB_BODIES_PATH: &str = "bodies";
const BLOCKDB_PROPOSED_HEAD_PATH: &str = "proposed_head";
const BLOCKDB_VOTED_HEAD_PATH: &str = "voted_head";
const BLOCKDB_FINALIZED_HEAD_PATH: &str = "finalized_head";

pub trait BlockPersist<ST, SCT, EPT> {
    fn write_bft_header(&mut self, block: &ConsensusBlockHeader<ST, SCT, EPT>)
        -> io::Result<()>;
    fn write_bft_body(&mut self, payload: &ConsensusBlockBody<EPT>)
        -> io::Result<()>;

    fn update_proposed_head(&mut self, block_id: &BlockId) -> io::Result<()>;
    fn update_voted_head(&mut self, block_id: &BlockId) -> io::Result<()>;
    fn update_finalized_head(&mut self, block_id: &BlockId) -> io::Result<()>;
}

fn atomic_symlink_update(target: &Path, link_path: &Path) -> io::Result<()> {
    let mut wip = link_path.to_path_buf();
    wip.set_extension("wip");
    std::os::unix::fs::symlink(target, &wip)?;
    std::fs::rename(&wip, link_path)?;
    Ok(())
}

fn write_bft_header(&mut self, block: &ConsensusBlockHeader<ST, SCT, EPT>)
    -> io::Result<()>
{
    let mut f = File::create(self.header_path(&block.get_id())).unwrap();
    f.write_all(&alloy_rlp::encode(block)).unwrap();
    Ok(())
}

fn write_bft_body(&mut self, body: &ConsensusBlockBody<EPT>) -> io::Result<()> {
    let mut f = File::create(self.body_path(&body.get_id())).unwrap();
    f.write_all(&alloy_rlp::encode(body)).unwrap();
    Ok(())
}

The ledger is simple by design: content-addressed RLP files plus head markers that move by atomic rename.

Keep the two file roles separate: header/body files contain the block data, while proposed_head, voted_head, and finalized_head are small moving pointers to the currently selected block IDs.

11.6 The WAL Is The Node’s Replay Notebook#

The write-ahead log is the simplest durable layer in the repo. Its job is not to serve RPC. Its job is to record the node’s event stream for replay and debugging. Each record is a 4-byte little-endian length followed by the payload bytes.

Why WAL Exists#

monad-node writes to the WAL before it applies the event to the main state machine. So the WAL records the actual input stream that drove state.update(...), which makes it valuable for replay, crash investigation, and understanding event order. It is not a user-facing query database.

The WAL is also not trying to duplicate every durable side effect. Ledger files, triedb data, archive data, and event-ring output are separate persistence or publication surfaces. The WAL’s job is the node input history needed to replay how the state machine was driven.

WAL Durability Nuance#

The current node wiring does not fsync after every single event write. Normal runtime appends are durable file writes, but not the strongest possible per-event flush posture. Segment rotation still syncs the segment being closed.

That is a practical tradeoff: lower steady-state write overhead and durable-enough replay logs for operational use, balanced against the fact that it is not a guarantee that every individual event was flushed at the instant it was appended.

11.7 Archive Stores Older Block-Oriented History#

Archive storage is the long-term home for old blocks, old receipts, old traces, tx-hash index data, and optionally a logs index. This is the part of the system that gives RPC access to history older than triedb retention.

Archive Is About Historical Blocks, Not Historical State Reconstruction#

This point is important enough to state directly. Archive storage helps answer old questions like “what was block N?”, “what receipt belonged to this old transaction hash?”, and “what traces were recorded for that block?”

It does not mean that old balance, nonce, storage, or code reads can be reconstructed forever. In the current RPC code, account-style historical reads still depend on triedb retention. So archive is best imagined as historical block data plus indexes, not as a universal forever-state database.

ArchiveReader Composes Several Pieces#

ArchiveReader is the higher-level reader surface that can combine a block-data archive, a tx index, optional logs indexing, and optional fallback readers. That is why historical RPC reads often look like “try recent surfaces, try triedb, then try archive” rather than going straight to archive first.

11.8 In-Memory Layers Matter Too#

Not every important read surface is durable. Several in-memory layers matter for freshness and performance: StateBackendCache on the consensus side, TriedbEnv metadata and RPC-side caches, and ExecEventsBuffer in monad-rpc. These are not substitutes for durable storage. They are speed and freshness layers on top of it.

ExecEventsBuffer Is Especially Important#

ExecEventsBuffer is populated from the execution event stream. It keeps a recent ring of blocks, txs, and receipts, plus three atomics for the latest proposed, voted, and finalized heights. That makes it one of the freshest surfaces in the whole system.

It also has different failure modes than triedb or archive. It is live-feed-shaped, it is bounded, and it can miss data if the feed gaps or the consumer lags. That distinction becomes important again in the RPC chapter.

11.9 One Cross-Subsystem Heads Table#

The words proposed, voted, and finalized show up in several subsystems. The same three names refer to the same three states across each one.

ConceptLedgerTriedb / RPC metadataExecEventsBufferRPC and WebSocket surface
proposedproposed_head symlinklatest proposed block keylatest_proposedlatest block tag resolves to proposed; standard newHeads and logs are currently filtered to proposed events
votedvoted_head symlinklatest voted block keylatest_votedsafe block tag resolves to voted
finalizedfinalized_head symlinklatest finalized block keylatest_finalizedfinalized block tag resolves to finalized

Monad-specific subscriptions are a little richer: monadNewHeads and monadLogs keep the commit state attached instead of hiding it behind a standard Ethereum-shaped result.

Execution events also have a verified state: execution outputs and the state root for a block have been included in a finalized later block. ExecEventsBuffer ignores Verified events because its head trackers are proposed, voted, and finalized heights, not proof that delayed output has now been verified.

The single most important storage rule for RPC: old block history and old account state are not the same thing.

11.11 A Few Paths Worth Knowing#

A few paths come up often enough to be worth knowing without consulting the source:

  • ledger headers: ledger_path/headers/<block_id>
  • ledger bodies: ledger_path/bodies/<body_id>
  • ledger heads: ledger_path/headers/proposed_head, voted_head, finalized_head
  • WAL segments: one basename with numbered suffixes such as <base>.0, <base>.1
  • archive keys: block-oriented namespaces like block/<number> and receipts/<number>

11.12 The Storage Picture In One Paragraph#

In one paragraph: consensus blocks land in the ledger; execution turns those blocks into triedb updates and event-stream outputs; monad-node logs its own event stream to the WAL; and monad-rpc serves the freshest recent data from buffers, the retained recent state from triedb, and older block history from archive. That paragraph is enough to predict most later behavior.

11.13 Architecture, Current Code, Current Caveat#

Architecture Monad splits durable state by job: consensus history in the ledger, retained recent execution state in triedb, replay input history in WAL, and older block-oriented history in archive.

Current code FileBlockPersist writes body first, then header, and advances head markers through atomic symlink replacement. RPC then composes buffers, triedb, and archive on top of those durable layers.

Current caveat Archive extends historical block-oriented queries, not historical world-state reads. Fresh recent buffers are useful, but they are still live-feed-shaped and gap-sensitive.

Open These Files First#

  • monad-block-persist/src/lib.rs: file layout, body or header write order, atomic head updates
  • monad-ledger/src/lib.rs: ledger wrapper and blocksync-serving logic
  • monad-wal/src/wal.rs: WAL record format and sync behavior
  • monad-triedb-utils/src/triedb_env.rs: broader RPC-side triedb adapter
  • monad-state-backend/src/thread.rs: consensus-side triedb worker boundary
  • monad-archive/src/model/block_data_archive.rs: archive block store
  • monad-archive/src/archive_reader.rs: composed archive reader
  • monad-archive/src/model/index_repr.rs: tx-index representation
  • monad-archive/src/model/logs_index.rs: logs-index shape
  • monad-rpc/src/data/buffer.rs: ExecEventsBuffer
  • monad-rpc/src/data/mod.rs: one consumer that composes recent, retained, and archived reads

What To Remember#

  • Triedb is retained recent execution state and recent execution-derived block data.
  • The ledger is durable recent consensus block history and head markers, not account state.
  • WAL is the node’s replay notebook, not a user-facing query database.
  • Archive extends historical block-oriented reads, not historical world-state reads.
  • Proposed, voted, and finalized appear across ledger, triedb metadata, buffers, and RPC surfaces.
  • Execution-event verified is a delayed-output proof state, not another ledger head marker.
  • Old block history and old account state use different read surfaces and have different failure modes.
