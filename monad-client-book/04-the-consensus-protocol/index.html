Chapter 4: The Consensus Protocol

monad-client-book/04-the-consensus-protocol.md View source →

The previous chapter covered the documents. This chapter covers the behavior: how proposals are filtered and handled, how certificates advance rounds, how blocks move from valid to coherent to committed, how votes become QCs, how timeouts become TCs, and how recovery decides between reusing a tip and going fresh.

The best single doorway into this chapter is still handle_proposal_message() in monad-consensus-state. But that function only becomes readable once you know which machines are cooperating with it.

Why This Chapter Matters#

The consensus code becomes easier to read once you see that several small state machines are cooperating. The pacemaker, vote state, safety layer, blocktree, and no-endorsement state each protect a different invariant. This chapter is about those invariants.

4.1 The State-Machine Shape#

MonadState is the node’s top-level consensus state machine, defined in monad-state/src/lib.rs. It owns the pacemaker, safety rules, blocktree, vote state, and sync-mode logic. When a new event arrives, this type is the thing that update(...) is called on.

At a high level, the node runs a repeating pattern:

  1. some subsystem emits an event
  2. MonadState consumes the event
  3. internal state changes
  4. commands are emitted back out to child subsystems

That means the code is easiest to read in two halves: internal state machines, and external side-effect executors. The main consensus-side machines are:

ComponentJobMain invariant
Pacemakerround advancement and timeout handlingnever move backward in round-space
VoteStatevote accumulation and QC creationone vote statement per validator per round path
Safetyhonest-node self-defensedo not locally help conflicting proof paths form
BlockTreelive uncommitted block graphremember valid blocks even before full coherency
NoEndorsementStaterefusal aggregationdo not build fresh-proposal authority sloppily

4.2 One Event-To-Command Story#

The abstract shape becomes easier once you see one concrete path.

sequenceDiagram
    participant Router as Router / timer / updater
    participant State as MonadState
    participant CS as ConsensusState
    participant Exec as ParentExecutor children

    Router->>State: event arrives
    State->>CS: handle event
    CS->>CS: mutate pacemaker / safety / blocktree / vote state
    CS-->>State: commands
    State-->>Exec: router, timer, ledger, txpool, statesync commands

That is why main.rs stays small. The protocol logic lives in the state machine, not in the outer process loop.

4.3 Proposal Handling Does Not Start At handle_proposal_message()#

handle_proposal_message() is the main proposal handler, but it is not the first gate. Earlier prefiltering in monad-state/src/consensus.rs handles stale traffic, message classes that do not fit the current mode, and messages that should not be processed in the node’s current status. So the actual path is:

network or updater input
-> early prefilter
-> consensus-state handler
-> emitted commands

That matters because some defensive behavior lives before the state-machine method you are looking at.

4.4 Pacemaker#

The pacemaker owns the current round, the high certificate, and timeout collection state for the live round. Its job is simple to state and easy to underestimate: decide when the node may move forward in round-space.

When a newer QC or TC arrives, the pacemaker can reject stale evidence, install a higher certificate, advance the current round, recompute the active epoch from round scheduling, clear timeout state that no longer matters, and emit commands for the next step. A certificate is not passive historical data. It can immediately change the round context in which the rest of a proposal is judged.

4.5 VoteState#

VoteState accumulates votes into QCs. The important behavior is that it buckets votes by statement, tracks what each validator has already contributed, and attempts aggregate-certificate creation when threshold stake exists.

The failure behavior is the important part: invalid signatures are removed narrowly, and the entire round is not discarded if enough honest stake remains. That pattern repeats across the repository. Remove the bad contribution, not the whole structure.

4.6 Safety#

Safety is the honest node’s self-defense layer. It tracks monotonic local facts such as the highest vote round, highest proposal round, highest no-endorsement round, and highest recovery-request round.

The spirit is simple: do not vote twice for the same or older round, do not propose twice for the same or older round, and do not help conflicting proof paths form. One especially useful check is the timeout-side logic that decides whether it is still safe to piggyback a vote inside a timeout message. That one boolean is small, but it protects a big safety story.

4.7 BlockTree#

BlockTree is the node’s live in-memory view of uncommitted history. It is not the ledger, triedb, or archive — it is the working set of blocks the consensus engine is actively reasoning about.

The crucial property is that BlockTree can hold blocks that are valid enough to store but not yet coherent enough to vote on. That is essential in a delayed-execution design. If the node refused to remember anything before full coherency was known, it would become fragile under out-of-order arrival, delayed state visibility, and missing-ancestor recovery.

4.8 The Proposal Path, Step By Step#

The easiest way to read handle_proposal_message() is as a sequence of gates.

Step 0: Earlier Filtering Already Happened#

By the time we are in this function, the message survived the cheapest rejection layer. That does not mean it is acceptable; it means it was worth deeper processing.

Step 1: Drop Proposals That Are Already Behind The Root#

If the proposal round is already behind the committed root, the proposal is too old to matter and is dropped cheaply.

Step 2: Resolve Epoch Context#

The node derives which epoch is active at proposal_round and which validator set and mapping apply there. This is why Chapter 2’s round-to-epoch scheduling matters so much.

Step 3: Process Embedded Certificates First#

Before validating the rest of the proposal, the node processes the embedded certificates: the block’s QC and the optional previous-round TC. This ordering matters because certificate processing may advance the pacemaker. If the pacemaker advances, the round context for the rest of the proposal changes.

Step 4: Validate The Proposal-Round Story#

Now the node checks proposal-round facts: is this proposal ahead of what is acceptable, is the sender the expected leader for proposal_round, and have we already handled another proposal for that round? This is proposal-message validation, not block validation yet.

Step 5: Validate The Block Itself#

Then the node checks block-level facts: does the block author match the expected leader for block_round, do the signatures line up, does the body actually match the header’s block_body_id, and is the block structurally valid? This is where the difference between proposal_round and block_round stops being theoretical and becomes operational.

Step 6: Add The Block To The BlockTree#

Once structural validation succeeds, the block is stored. At this point it may still be not yet coherent and not yet voteable.

Step 7: Try Commit Logic#

The new block and its QC relationships may make an ancestor committable. If so, the root moves forward, committed blocks are emitted in order, and irrelevant branches are pruned.

Step 8: Update Coherency#

A newly added block or ancestor arrival may also make previously stored blocks become coherent. This is where the delayed-execution model becomes visible in consensus behavior. The node can move blocks through the following progression:

  • invalid → rejected
  • valid but missing ancestor → keep and request block sync
  • valid but incoherent → keep but do not vote
  • coherent → now eligible for vote logic

Step 9: Try To Vote#

Only now does the node consider voting, and only if the block is coherent, proposal timing is acceptable, the proposal matches the live round context, and local safety allows the vote.

Step 10: Try To Propose#

State changes can make the node eligible to propose immediately for the next round, which is why many handlers end by trying local proposal logic too.

4.9 The Validation Layers In One Table#

LayerMain question
prefiltershould this be dropped cheaply before deeper work?
certificate processingdoes embedded evidence change local round state?
structural validationis the block well-formed and correctly signed?
coherency validationdoes the block fit current chain and delayed-execution context?
safety gatingmay this honest node vote or propose without self-contradiction?

This is more precise than saying “the node validates the proposal.” There is no single one-step “proposal validation.”

4.10 Invalid, Incoherent, Missing Ancestor, And Committable#

These words are close enough to blur together if you are not careful. They should stay separate.

StateMeaningTypical response
invalidthe object itself fails validationreject
missing ancestorthe object may be fine, but local ancestry is incompleterequest block sync
incoherentthe object is valid, but current delayed-execution context does not yet support votingkeep, but do not vote
committablecertified parent-child relationship is satisfiedcommit the relevant ancestor if coherency also permits

This distinction explains why the node can store a block before it is safe to vote for it.

4.11 One Missing-Ancestor Story#

Suppose a proposal for block B arrives. The node might learn that the message is not stale, the block is structurally fine, and the parent chain is incomplete locally. That is not the same thing as a bad block. The correct response is to keep what is useful, request block sync, and continue once ancestry arrives. This is why block sync is part of normal protocol operation, not just disaster recovery.

4.12 The Timeout And Recovery Path#

Timeouts are their own subprotocol, not one side branch.

The rough flow is:

  1. local or remote timeout evidence arrives
  2. timeout buckets accumulate stake
  3. enough timeout evidence may produce a TC
  4. the TC carries the best known extension hint
  5. recovery logic decides between:
    • reusing a tip
    • refusing a tip
    • acknowledging no usable tip
  6. fresh proposal authority may later form through an NEC or NoTipCertificate

4.13 The Recovery Decision In Plain English#

The leader does not immediately jump from “timeout happened” to “build any fresh block you want.” It tries to preserve more structure than that. The recovery-side questions are:

  1. did the TC carry a reusable tip candidate?
  2. if yes, is that tip coherent and still worth reusing?
  3. if reused, do enough validators endorse that reuse?
  4. if not, do we now have explicit refusal proof (NEC) or no-tip proof (NoTipCertificate) that justifies a fresh proposal?

That is why Chapters 3 and 4 need all of TC, RoundRecoveryMessage, NoEndorsementMessage, NEC, NoTipCertificate, and FreshProposalCertificate. The recovery protocol is not one fallback flag. It is a small proof-driven state machine of its own.

4.14 One Happy-Path Round#

sequenceDiagram
    participant Leader as Leader r
    participant Validators as Validators
    participant Next as Leader r+1

    Leader->>Validators: ProposalMessage
    Validators->>Validators: prefilter, process certs, validate, store, coherency check
    Validators->>Next: VoteMessage
    Next->>Next: VoteState forms QC
    Next->>Validators: round-advance effects
    Validators->>Validators: Pacemaker enters next round

That is the backbone. The real code adds more guards, but not a different overall shape.

4.15 One Recovery-Path Round#

The recovery backbone is:

proposal stalls
-> validators timeout
-> TC forms
-> pacemaker advances
-> recovery logic inspects TC.high_extend
-> try reusing tip if possible
-> otherwise gather fresh-proposal authority
-> new proposal path resumes

That is the recovery-side skeleton to keep in your head while reading the code.

What To Remember#

  • The node is an event-driven state machine that emits commands back out to subsystems.
  • Proposal handling starts before handle_proposal_message() because prefiltering happens earlier.
  • Embedded certificates are processed before later proposal checks because they can change the local round context.
  • Pacemaker, VoteState, Safety, BlockTree, and NoEndorsementState each protect different invariants.
  • Valid, missing-ancestor, incoherent, and committable are different states with different responses.
  • Timeout handling is a real recovery subprotocol, not one fallback branch.
  • Fresh proposal authority is proof-driven; it does not appear just because a round timed out.
