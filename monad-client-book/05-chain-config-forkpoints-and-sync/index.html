Chapter 5: Chain Config, Forkpoints, Restart, and Sync

monad-client-book/05-chain-config-forkpoints-and-sync.md View source →

The previous chapter described how consensus behaves when the node is already live. But validators are real machines. They crash, get rebooted, get redeployed, get upgraded. Networks lose packets and partition. Disks fill up. The protocol has to keep working through all of that, which means a production client spends much of its complexity on a problem the live-consensus chapter set aside: starting safely from an interrupted state.

When a validator comes back online, it has to answer four questions before it can participate again:

  • Which protocol rules are active right now? (chain config and its forkpoints)
  • Where was the network when I last had a clear view? (the restart anchor)
  • What did I miss while I was gone? (block sync and state sync)
  • When is it safe for me to vote and propose again? (live readiness)

Get any of this wrong and the consequences range from quiet — the node falls behind without anyone noticing — to severe: an honest node accidentally signs something inconsistent with what it signed before the restart, breaking the per-node safety promise the rest of the network relies on. This is why startup is its own subsystem, not a footnote to the live protocol.

If you only open one function first, open maybe_start_consensus() in monad-state/src/lib.rs. That is where delayed-anchor readiness, block sync, state sync, and the sync-to-live transition all meet. The restart path mixes architecture, current implementation, and operational shortcuts in the same function, so this chapter separates them out.

Why This Chapter Matters#

Running consensus safely after restart is not just “read latest block, continue.” A safe restart needs three kinds of context: the right rule set, the right certified restart anchor, and enough recent block and execution state to make live decisions again. If you miss any one of those, the node can become locally inconsistent, too far behind to vote safely, or live in appearance only.

The code in this chapter is mostly about restraint. After a crash or redeploy, the node may have old bootstrap files, a checkpoint that is not the freshest available anchor, missing block ancestry, and execution state that lags behind the consensus root. It should not vote or propose until it has rebuilt the context that makes those actions safe.

The cleanest way to connect this chapter to the previous one is to see restart as the same consensus problem after a pause. The node still needs the right validators, the right high certificate, the right recent block path, and the right delayed execution state. Sync mode exists so the node can rebuild those ingredients before it starts making live statements again.

5.1 Two Kinds Of Config Time#

MonadChainConfig is not just a bag of constants. It governs the chain ID, the epoch length, the epoch start delay, staking activation, rewards and fee-related parameters, consensus revision activations, and execution revision activations.

The first restart question is “which rules am I running?” Monad has to answer that question twice, because consensus and execution do not advance on the same clock. The important subtlety is that MonadChainConfig exposes two different revision lookups: get_chain_revision(round) and get_execution_chain_revision(execution_timestamp_s). That is not duplication. It reflects the fact that consensus rules activate in round-space, while execution rules activate by execution timestamp.

This matters during restart because a node is reconstructing context from persisted data, not simply following the live timer forward. It must recover the consensus rule set from the round context and the execution rule set from execution time. Treating both as one “current version” would hide the fact that consensus and execution cross different activation boundaries.

5.2 A Restart Anchor Is More Than “Latest Block”#

A validator cannot restart safely from only one block hash, one latest height, or one latest state root. It needs enough protocol context to resume safely.

The anchor has to answer two questions at once: what committed block is the node restarting from, and what round-ending evidence tells the pacemaker where to resume? A bare block pointer answers only the first question.

The reason is local safety. Before the crash, the node may already have voted, timed out, or observed a high certificate. After restart, it must not behave as if that evidence never existed. The restart anchor carries the committed position and the proof context needed to resume the same protocol story instead of inventing a new one from storage height alone.

That restart anchor is the forkpoint, which wraps a checkpoint. A checkpoint is the snapshot object produced by consensus that names a safe resumption point. The forkpoint is the persisted file-level wrapper around that checkpoint plus the nearby validator context needed to verify it on disk. Together they carry:

  • committed root — the sequence-number-and-block-id pair that consensus has committed through
  • highest carried round-ending certificate — the newest QC or TC the node can prove it saw, which tells the pacemaker where to resume in round-space
  • bounded locked-epoch validator context — just enough validator history to verify that certificate and survive nearby epoch transitions

This is why restart safety is a consensus problem, not only a storage problem.

5.3 Why Checkpoints Carry Validator Context#

A QC, TC, or other carried round-ending certificate is meaningful only relative to its epoch, its validator set, and the certificate-verification keys for those validators. The node therefore cannot validate a carried high certificate by itself. It needs nearby validator history too. That is why the checkpoint stores a bounded locked-epoch window instead of only a block root.

The checkpoint is really answering one question: if I restart here, do I still know enough validator context to trust the certificate that tells me where “here” is?

5.4 Startup May Replace Local Bootstrap State#

Bootstrap state means the small set of local files the node reads at startup to decide who it is, which chain it belongs to, and which restart anchor it should resume from. It is separate from durable chain storage: chain history lives in the ledger and triedb, while bootstrap state is the outer configuration shell that tells the node how to connect those durable stores together.

NodeState::setup() does more than read local files. It loads node config, chain config, forkpoint config, validator config, key material, and filesystem paths. But it can also refresh bootstrap state from remote sources when local state is too stale.

So the startup rule is not “read local files and trust them forever.” It is “find the freshest trustworthy bootstrap state, replace stale local bootstrap files if necessary, then build the node from that state.” Local bootstrap files are durable working state, but they are not the only source of restart truth.

5.5 The Node Starts In Sync Mode#

This is a runtime fact that shapes the whole startup path in the current client. The node does not boot directly into live consensus. It starts in ConsensusMode::Sync, with that sync-mode state initialized around the forkpoint root, the carried high certificate, and the locked-epoch validators from startup.

That distinction drives the startup path: “the process is running” is not the same as “the validator is safe to participate.” In sync mode, the node immediately asks three questions in sequence. Do I have enough block history? Do I have enough execution state? If not, what must I request next?

This mode split is the code’s guardrail against an eager restart. The node can receive messages, buffer useful proposals, and move its sync target while still refusing to act like a live validator. Only after the missing consensus history and delayed execution state are rebuilt does the code construct the live ConsensusState.

Abridged from production code. The important detail is that sync mode and live mode are not flags on one giant state object. They are two enum variants with different data:

enum ConsensusMode<ST, SCT, EPT, BPT, SBT, CCT, CRT> {
    Sync {
        high_certificate: RoundCertificate<ST, SCT, EPT>,
        block_buffer: BlockBuffer<ST, SCT, EPT>,
        db_status: DbSyncStatus,

        // de-duplicates Sync(n) -> Sync(n') target updates
        updating_target: bool,

        locked_epoch_validators: Vec<ValidatorSetDataWithEpoch<SCT>>,
    },

    Live(ConsensusState<ST, SCT, EPT, BPT, SBT, CCT, CRT>),
}

That is the smallest code shape for the chapter: before the node can vote, it is literally in a different consensus mode.

5.6 BlockBuffer#

While the node is syncing, it still needs to reason about incoming blocks and proposals. It does not use the normal live BlockTree for that job; it uses BlockBuffer. The buffer tracks the current root, ancestor blocks around that root, newer headers above the root, cached proposal data, and recent buffered proposals.

The point is not to become a second live consensus engine. The point is to hold enough local consensus history to decide whether the sync target should move, decide whether block sync is still needed, and allow a safe later transition into live mode.

Think of BlockBuffer as the temporary workspace for rejoining. It does not need every live-consensus capability. It needs to answer practical restart questions: do we know the root path, do we have enough parents behind it, have newer proposals shown us a better target, and can we later seed live consensus with coherent recent history?

Abridged from production code. The important detail is the 2 * execution_delay history requirement, which the source comment ties to TFM — the transaction fee market mechanism, Monad’s base-fee and reserve-balance machinery — because it needs that much committed history to evaluate reserve constraints around the restart point:

pub(crate) struct BlockBuffer<ST, SCT, EPT> {
    max_buffered_proposals: usize,
    resync_threshold: SeqNum,

    // TFM reserve balance checking requires N - 2 * state_root_delay blocks
    min_num_blocks: SeqNum,

    root: BlockId,
    full_blocks: HashMap<BlockId, ConsensusFullBlock<ST, SCT, EPT>>,
    payload_cache: HashMap<ConsensusBlockBodyId, ConsensusBlockBody<EPT>>,
    block_headers: HashMap<BlockId, ConsensusBlockHeader<ST, SCT, EPT>>,
    proposal_buffer: VecDeque<(NodeId<SCT::NodeIdPubKey>, ProposalMessage<ST, SCT, EPT>)>,
}

impl<ST, SCT, EPT> BlockBuffer<ST, SCT, EPT> {
    pub fn new(execution_delay: SeqNum, root: BlockId, resync_threshold: SeqNum) -> Self {
        Self {
            max_buffered_proposals: resync_threshold.0 as usize,
            resync_threshold,
            min_num_blocks: SeqNum(execution_delay.0.saturating_mul(2)),
            root,
            full_blocks: Default::default(),
            payload_cache: Default::default(),
            block_headers: Default::default(),
            proposal_buffer: Default::default(),
        }
    }
}

Sync needs more than the root itself because live rejoin must rebuild a delayed-execution window, not only identify one committed block.

5.7 Sync Mode Still Learns From The Network#

Sync mode is not passive waiting. Incoming proposals can still show the node that the network is farther ahead than its current target, and that its state-sync target should move. That is why BlockBuffer::handle_proposal(...) exists. Even before the node is live, incoming proposals can raise the target root. Sync mode is not live consensus, but it is not blind waiting either.

5.8 Block Sync And State Sync Solve Different Problems#

These are easy to blur together. They should stay separate.

The simplest way to keep them apart is to ask what is missing. If the node is missing ordered blocks and ancestry, block sync is the answer. If the node has the consensus path but execution cannot yet answer state or delayed-result questions for that path, state sync is the answer. A restarting node often needs both, but they repair different parts of the local picture.

Block Sync#

Block sync fetches missing consensus blocks and ancestry. Its job is to rebuild enough ordered block history around the restart root.

State Sync#

State sync fetches recent execution-side state. Its job is to bring the execution database forward enough that the node can validate and serve recent execution views.

So the simple distinction is that block sync repairs consensus history, while state sync repairs execution state. The node needs both before it can safely rejoin.

5.9 The Delayed Anchor#

This is the sync-specific detail to internalize. The node does not choose an arbitrary execution snapshot point; it chooses a point implied by the delayed-execution architecture itself, roughly root_seq_num - execution_delay. That is the delayed anchor.

The arithmetic is only the first approximation. In the code, the node also derives a concrete delayed block ID from the root path and uses the presence of that block’s execution result as the real readiness check.

Why this anchor? Because the node does not need “the freshest imaginable execution state.” It needs enough execution state to safely reason about the delayed-execution window around the current consensus root. This is where sync, delayed execution, and block coherency all meet.

Abridged from production code. The important detail is that DoneSync(n) must reach the delayed target implied by the current root:

StateSyncEvent::DoneSync(n) => {
    let ConsensusMode::Sync { db_status, block_buffer, .. } = &mut self.consensus
    else {
        unreachable!("DoneSync invoked while ConsensusState is live")
    };

    let delay = self.consensus_config.execution_delay;
    let maybe_target = block_buffer
        .root_seq_num()
        .map(|root| root.max(delay) - delay);

    match maybe_target {
        Some(target) if n >= target => {
            assert_eq!(n, target);
            assert_eq!(db_status, &DbSyncStatus::Started);
            *db_status = DbSyncStatus::Done;
            self.maybe_start_consensus()
        }
        _ => Vec::new(),
    }
}

The event is not “state sync finished somewhere.” It is “state sync reached the delayed anchor this root requires.”

There is one robustness nuance in that match. If DoneSync(n) arrives for an older target after the sync target has moved forward, the code ignores it because n < target. State sync is target-tracking; it is not one global boolean that means “some sync finished.”

5.10 One Numeric Delayed-Anchor Example#

Suppose the current root is SeqNum(100) and execution_delay = 3. Then the useful first-pass picture is that the delayed anchor is around SeqNum(97), and the node wants to know whether the execution result for that delayed block is already locally available. If it is, the node may already have enough execution state to finish sync; if it is not, state sync should target the delayed execution result carried on the root path.

That means the node is not asking “do I have execution for the absolute tip?” It is asking “do I have enough execution state at the delayed point that consensus actually depends on?” That is a very Monad-specific restart rule.

5.11 maybe_start_consensus()#

This function is the gatekeeper for the live transition.

The function works as a checklist for safe participation. It does not try to fix every missing thing at once. It fixes ancestry first, then execution readiness, then local runtime state, and only then switches into live consensus.

In the current code, it does that readiness check in stages.

Stage 1: Do We Have Enough Committed Parent Blocks?#

If the block buffer still lacks enough committed parent history, the node requests block sync first. No execution-state request yet, no live transition yet — first fix ancestry.

Stage 2: Compute The Delayed Anchor#

Once enough block history exists, the node computes the delayed anchor: roughly root_seq_num - execution_delay, plus the concrete delayed block ID implied by the root path. That is the point whose execution availability matters for live readiness.

Stage 3: Is The Execution DB Ready There?#

The node checks whether the execution result for that concrete delayed block already exists locally. If yes, it can effectively treat state sync as done for that target. If no, it requests state sync from the delayed execution result carried on the root path.

This is the design choice at the center of the startup path: the node does not pick an arbitrary snapshot point — it uses the delayed-execution structure implied by consensus itself.

Stage 4: Rebuild Live Local Context#

Once DB sync is done, the live-transition path rebuilds more than one local subsystem. It resets block policy from a committed window behind the root, resets the txpool from that same committed window, rechecks staking-backed validator data when staking is active, and builds a fresh live ConsensusState.

Stage 5: Start Execution And Resume Live Flow#

Then the node emits StartExecution, rebuilds live consensus, immediately drives the current-round vote and timeout paths, and replays cached proposals that arrived while syncing. That last step matters because sync mode still kept useful proposal data.

Abridged from production code. The important details are the staged gates and the runtime consequences:

fn maybe_start_consensus(&mut self) -> Vec<Command> {
    let ConsensusMode::Sync {
        high_certificate,
        block_buffer,
        db_status,
        locked_epoch_validators,
        ..
    } = &mut self.consensus else {
        unreachable!("maybe_start_consensus invoked while live")
    };

    let root_parent_chain = block_buffer.root_parent_chain();
    if let Some(block_range) = block_buffer.needs_blocksync() {
        return self.update(MonadEvent::BlockSyncEvent(BlockSyncEvent::SelfRequest {
            requester: BlockSyncSelfRequester::StateSync,
            block_range,
        }));
    }

    let root_info = block_buffer.root_info().expect("root block should be known");
    let delay_seq_num = root_info.seq_num.max(self.consensus_config.execution_delay)
        - self.consensus_config.execution_delay;

    if db_status == &DbSyncStatus::Waiting {
        *db_status = DbSyncStatus::Started;

        // Derived from the root parent chain in the full function.
        let delay_block_id = {
            let delay_child_seq_num = delay_seq_num + SeqNum(1);
            root_parent_chain
                .iter()
                .find(|block| block.get_seq_num() == delay_child_seq_num)
                .map(|block| block.get_parent_id())
                .unwrap_or(GENESIS_BLOCK_ID)
        };
        if self.state_backend
            .get_execution_result(&delay_block_id, &delay_seq_num, true)
            .is_ok()
        {
            return self.update(MonadEvent::StateSyncEvent(StateSyncEvent::DoneSync(
                delay_seq_num,
            )));
        }

        let delayed_execution_result =
            block_buffer.root_delayed_execution_result().expect("root result exists");
        return vec![Command::StateSyncCommand(StateSyncCommand::RequestSync(
            delayed_execution_result
                .first()
                .expect("root carries one delayed execution result")
                .clone(),
        ))];
    }

    assert_eq!(db_status, &DbSyncStatus::Done);
    let mut commands = Vec::new();
    let delay = self.consensus_config.execution_delay;
    let last_two_delay_committed_blocks: Vec<_> = root_parent_chain
        .iter()
        .map(|full_block| self.block_validator.validate(
            full_block.header().clone(),
            full_block.body().clone(),
            None,
            &self.consensus_config.chain_config,
            &mut self.metrics,
        ).expect("majority committed invalid block"))
        .take(delay.0.saturating_mul(2) as usize)
        .rev()
        .collect();
    self.block_policy.reset(last_two_delay_committed_blocks.iter().collect());
    commands.push(Command::TxPoolCommand(TxPoolCommand::Reset {
        last_delay_committed_blocks: last_two_delay_committed_blocks.clone(),
    }));

    let consensus = ConsensusState::new(
        &self.epoch_manager,
        &self.consensus_config,
        root_info,
        high_certificate.clone(),
    );
    let current_round = consensus.get_current_round();
    self.consensus = ConsensusMode::Live(consensus);
    commands.push(Command::StateSyncCommand(StateSyncCommand::StartExecution));
    commands.extend(self.update(MonadEvent::ConsensusEvent(ConsensusEvent::SendVote(
        current_round,
    ))));
    commands.extend(self.update(MonadEvent::ConsensusEvent(ConsensusEvent::Timeout(
        current_round,
    ))));
    commands
}

The five stages are visible in the function body in order. The if let Some(block_range) = block_buffer.needs_blocksync() block is Stage 1: ancestry shortfall, redirected to block sync. The delay_seq_num calculation that follows is Stage 2. The if db_status == DbSyncStatus::Waiting block — checking whether the delayed block’s execution result is already present, otherwise emitting RequestSync — is Stage 3. The last_two_delay_committed_blocks reconstruction with block_policy.reset(...) and TxPoolCommand::Reset is Stage 4. The closing block that builds ConsensusState::new(...), switches self.consensus to Live, emits StartExecution, and immediately drives SendVote and Timeout is Stage 5.

This is the whole sync chapter in one local transition: block ancestry first, delayed execution state second, then local runtime rebuild.

5.13 The Three Threshold Knobs#

ConsensusConfig carries three sync-related thresholds: statesync_to_live_threshold, live_to_statesync_threshold, and start_execution_threshold. The important nuance is not the math — it is how these knobs are currently used.

These knobs exist because “behind” is not one state. A node that is slightly behind may be able to catch up through normal live flow. A node that is far behind should stop acting live and rebuild through sync. A node that has enough execution context may start execution work before every surrounding detail is fresh. The config names those policy boundaries, while the current implementation decides where each boundary is enforced.

What They Mean#

statesync_to_live_threshold says how close a syncing node must be before it is allowed to rejoin live operation. live_to_statesync_threshold says how far behind a live node may fall before it should stop pretending to be current. start_execution_threshold is a config-model notion of how early execution may start relative to the restart target.

Current Code Nuance#

The first two have obvious meaning in the live path. The third is more subtle. The config model exposes it, but the source version used here still emits StartExecution from maybe_start_consensus() when sync completes and live consensus is initialized. The visible sync-to-live branch here is not obviously keyed directly off start_execution_threshold. So the precise statement is: there is a config-level idea, and there is the current startup-path behavior.

Abridged from production code. The important detail is that the current EXECUTION_DELAY feeds more than consensus:

const EXECUTION_DELAY: u64 = 3;

let create_block_policy = || {
    EthBlockPolicy::new(
        GENESIS_SEQ_NUM,
        EXECUTION_DELAY,
    )
};

StateBackendCache::new(triedb_handle, SeqNum(EXECUTION_DELAY));

ConsensusConfig {
    execution_delay: SeqNum(EXECUTION_DELAY),
    statesync_to_live_threshold: SeqNum(statesync_threshold as u64),
    live_to_statesync_threshold: SeqNum(statesync_threshold as u64 * 3 / 2),
    start_execution_threshold: SeqNum(start_execution_threshold as u64),

}

Delayed execution is wired into block policy, triedb caching, and consensus config at node assembly time.

5.14 What Happens On DoneSync#

DoneSync is not a simple boolean flip. In current code, the live-transition path does meaningful work:

The event means “state sync has reached the delayed target this root requires.” That is enough to begin rebuilding live local context, but it is not itself the rebuild. The code still has to reset local policy state, reset txpool, replay committed blocks into the ledger-facing path, check validator data, and then construct live consensus state.

  • marks DB sync complete
  • reconstructs a recent committed block window behind the root
  • resets block policy from that committed window
  • resets the txpool from that same window
  • rechecks staking-backed validator data when staking is active
  • builds a fresh live ConsensusState
  • emits StartExecution
  • sends ConsensusEvent::SendVote(current_round)
  • sends ConsensusEvent::Timeout(current_round)
  • replays cached proposals that arrived while syncing

That is why “done syncing” is better understood as rebuilding live local context from the synchronized anchor, not as flipping one flag.

5.15 One Honest Current-Code Nuance#

The live-transition path has one useful comment: after switching live, it immediately drives a local vote path. The code notes that a stricter model would wait for the vote pacing timer, but the implementation treats the shortcut as acceptable. The same transition also immediately drives the current-round timeout path. So live rejoin primes both vote and timeout behavior instead of waiting for every timer edge to arrive naturally.

5.16 The Validator-Set Recheck On Rejoin#

The live-transition path re-reads staking-backed validator data from triedb and checks that it matches the locked validator context loaded at startup. That feature is real and important.

But the implementation reviewed here also carries a TODO. The read currently uses delay_seq_num — the sequence number at the delayed-execution anchor, roughly root_seq_num - execution_delay, which is the oldest point whose execution results the node already trusts. The comment says root_seq_num — the sequence number of the committed restart root itself, which is newer than delay_seq_num by execution_delay blocks — should be used instead. Relevant code lives in monad-state/src/lib.rs.

5.17 Architecture, Current Code, Current Caveat#

Architecture Safe restart needs three things: a certified consensus anchor, enough recent block history, and enough recent execution state at the delayed anchor the live protocol actually depends on.

Current code The node starts in ConsensusMode::Sync, uses BlockBuffer to reason about the restart root, gates live entry through maybe_start_consensus(), and emits StartExecution during the live transition.

Current caveat Some sync thresholds are more explicit in the config model than in the visible startup path, and the staking-backed validator-set recheck still carries a TODO around which sequence number should be read.
