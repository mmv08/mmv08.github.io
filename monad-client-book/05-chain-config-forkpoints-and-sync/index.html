Chapter 5: Chain Config, Forkpoints, Restart, and Sync

monad-client-book/05-chain-config-forkpoints-and-sync.md View source →

The previous chapter described how consensus behaves when the node is already live. A real validator has a harder problem first: how does it know which rules are active, where does it restart from, how much history must it have locally, and when is it safe to leave catch-up mode and rejoin consensus? This chapter answers those questions.

If you only open one function first, open maybe_start_consensus() in monad-state/src/lib.rs. That is where delayed-anchor readiness, block sync, state sync, and the sync-to-live transition all meet. It is a high-leverage chapter because restart logic is where architecture, current implementation, and operational shortcuts most often get blurred together.

Why This Chapter Matters#

Running consensus safely after restart is not just “read latest block, continue.” A safe restart needs three kinds of context: the right rule set, the right certified restart anchor, and enough recent block and execution state to make live decisions again. If you miss any one of those, the node can become locally inconsistent, too far behind to vote safely, or live in appearance only.

5.1 Two Kinds Of Config Time#

MonadChainConfig is not just a bag of constants. It governs the chain ID, the epoch length, the epoch start delay, staking activation, rewards and fee-related parameters, consensus revision activations, and execution revision activations.

The important subtlety is that it exposes two different revision lookups: get_chain_revision(round) and get_execution_chain_revision(execution_timestamp_s). That is not duplication — it reflects the fact that consensus and execution do not advance on the same clock.

Architecture Consensus feature activation lives in round-space. Execution feature activation lives in execution-time space.

Current code The split is implemented directly in monad-chain-config/src/lib.rs.

5.2 A Restart Anchor Is More Than “Latest Block”#

A validator cannot restart safely from only one block hash, one latest height, or one latest state root. It needs enough protocol context to resume safely.

That restart anchor is the forkpoint, which wraps a checkpoint. A checkpoint is the snapshot object produced by consensus that names a safe resumption point; the forkpoint is the persisted file-level wrapper around that checkpoint plus the nearby validator context needed to verify it on disk. Together they carry:

  • committed root — the sequence-number-and-block-id pair that consensus has committed through
  • highest carried round-ending certificate — the newest QC or TC the node can prove it saw, which tells the pacemaker where to resume in round-space
  • bounded locked-epoch validator context — just enough validator history to verify that certificate and survive nearby epoch transitions

This is why restart safety is a consensus problem, not only a storage problem.

5.3 Why Checkpoints Carry Validator Context#

A QC, TC, or other carried round-ending certificate is only meaningful relative to the epoch it belongs to, the validator set active in that epoch, and the certificate-verification keys for those validators. So the node cannot validate a carried high certificate “in a vacuum” — it needs nearby validator history too. That is why the checkpoint stores a bounded locked-epoch window instead of only a block root.

The checkpoint is really answering one question: if I restart here, do I still know enough validator context to trust the certificate that tells me where “here” is?

5.4 Startup May Replace Local Bootstrap State#

Bootstrap state means the small set of local files the node reads at startup to decide who it is, which chain it belongs to, and which restart anchor it should resume from. It is separate from durable chain storage: chain history lives in the ledger and triedb, while bootstrap state is the outer configuration shell that tells the node how to connect those durable stores together.

NodeState::setup() does more than read local files. It loads node config, chain config, forkpoint config, validator config, key material, and filesystem paths. But it can also refresh bootstrap state from remote sources when local state is too stale.

So the startup rule is not “read local files and trust them forever.” It is “find the freshest trustworthy bootstrap state, replace stale local bootstrap files if necessary, then build the node from that state.” That distinction matters operationally: local bootstrap files are durable working state, but not the only source of restart truth.

5.5 The Node Starts In Sync Mode#

This is a runtime fact that shapes the whole startup path in the current client. The node does not boot directly into live consensus. It starts in ConsensusMode::Sync, with that sync-mode state initialized around the forkpoint root, the carried high certificate, and the locked-epoch validators from startup.

Then the node immediately asks three questions in sequence: do I have enough block history, do I have enough execution state, and if not, what must I request next? So “startup complete” and “safe to participate” are not the same moment.

5.6 BlockBuffer#

While the node is syncing, it still needs to reason about incoming blocks and proposals. It does not use the normal live BlockTree for that job; it uses BlockBuffer. The buffer tracks the current root, ancestor blocks around that root, newer headers above the root, cached proposal data, and recent buffered proposals.

The point is not to become a second live consensus engine. The point is to hold enough local consensus history to decide whether the sync target should move, decide whether block sync is still needed, and allow a safe later transition into live mode.

5.7 Sync Mode Still Learns From The Network#

Sync mode is not passive waiting. Incoming proposals can still teach the node that the network is farther ahead than its current target, and that its state-sync target should move. That is why BlockBuffer::handle_proposal(...) exists: even before the node is live, incoming proposals can raise the target root. So sync mode is not live consensus, but it is also not blind waiting.

5.8 Block Sync And State Sync Solve Different Problems#

These are easy to blur together. They should stay separate.

Block Sync#

Block sync fetches missing consensus blocks and ancestry. Its job is to rebuild enough ordered block history around the restart root.

State Sync#

State sync fetches recent execution-side state. Its job is to bring the execution database forward enough that the node can validate and serve recent execution views.

So the simple distinction is that block sync repairs consensus history, while state sync repairs execution state. The node needs both before it can safely rejoin.

5.9 The Delayed Anchor#

This is the sync-specific detail to internalize. The node does not choose an arbitrary execution snapshot point; it chooses a point implied by the delayed-execution architecture itself, roughly root_seq_num - execution_delay. That is the delayed anchor.

The arithmetic is only the first approximation. In the code, the node also derives a concrete delayed block ID from the root path and uses the presence of that block’s execution result as the real readiness check.

Why this anchor? Because the node does not need “the freshest imaginable execution state.” It needs enough execution state to safely reason about the delayed-execution window around the current consensus root. This is where sync, delayed execution, and block coherency all meet.

5.10 One Numeric Delayed-Anchor Example#

Suppose the current root is SeqNum(100) and execution_delay = 3. Then the useful first-pass picture is that the delayed anchor is around SeqNum(97), and the node wants to know whether the execution result for that delayed block is already locally available. If it is, the node may already have enough execution state to finish sync; if it is not, state sync should target the delayed execution result carried on the root path.

That means the node is not asking “do I have execution for the absolute tip?” It is asking “do I have enough execution state at the delayed point that consensus actually depends on?” That is a very Monad-specific restart rule.

5.11 maybe_start_consensus()#

This function is the gatekeeper for the live transition.

In the current code, it does the readiness check in stages.

Stage 1: Do We Have Enough Committed Parent Blocks?#

If the block buffer still lacks enough committed parent history, the node requests block sync first. No execution-state request yet, no live transition yet — first fix ancestry.

Stage 2: Compute The Delayed Anchor#

Once enough block history exists, the node computes the delayed anchor: roughly root_seq_num - execution_delay, plus the concrete delayed block ID implied by the root path. That is the point whose execution availability matters for live readiness.

Stage 3: Is The Execution DB Ready There?#

The node checks whether the execution result for that concrete delayed block already exists locally. If yes, it can effectively treat state sync as done for that target. If no, it requests state sync from the delayed execution result carried on the root path.

This is the design choice at the center of the startup path: the node does not pick an arbitrary snapshot point — it uses the delayed-execution structure implied by consensus itself.

Stage 4: Rebuild Live Local Context#

Once DB sync is done, the live-transition path rebuilds more than one local subsystem. It resets block policy from a committed window behind the root, resets the txpool from that same committed window, rechecks staking-backed validator data when staking is active, and builds a fresh live ConsensusState.

Stage 5: Start Execution And Resume Live Flow#

Then the node emits StartExecution, rebuilds live consensus, and replays cached proposals that arrived while syncing. That last step matters — sync mode is not a black hole.

5.12 A Restart Timeline#

flowchart LR
    Setup["load config, keys, forkpoint, validator data"] --> Sync["enter ConsensusMode::Sync"]
    Sync --> BlockCheck{"enough block ancestry?"}
    BlockCheck -->|no| BlockSync["request block sync"]
    BlockCheck -->|yes| StateCheck{"execution DB ready at delayed anchor?"}
    StateCheck -->|no| StateSync["request state sync"]
    StateCheck -->|yes| Done["DoneSync path"]
    BlockSync --> StateCheck
    StateSync --> Done
    Done --> Live["rebuild live local state, start execution, become live"]

That is the current client’s restart story in one diagram.

5.13 The Three Threshold Knobs#

ConsensusConfig carries three sync-related thresholds: statesync_to_live_threshold, live_to_statesync_threshold, and start_execution_threshold. The important nuance is not the math — it is how these knobs are currently used.

What They Mean#

statesync_to_live_threshold says how close a syncing node must be before it is allowed to rejoin live operation. live_to_statesync_threshold says how far behind a live node may fall before it should stop pretending to be current. start_execution_threshold is a config-model notion of how early execution may start relative to the restart target.

Current Code Nuance#

The first two have obvious meaning in the live path. The third is more subtle: the config model exposes it, but the checked-out maybe_start_consensus() path still emits StartExecution when sync completes and live consensus is initialized, and the visible sync-to-live branch here is not obviously keyed directly off start_execution_threshold. So this is one of those places where the book has to say both “there is a config-level idea” and “there is the current startup-path behavior” and let the two coexist.

5.14 What Happens On DoneSync#

DoneSync is not a simple boolean flip. In current code, the live-transition path does meaningful work:

  • marks DB sync complete
  • reconstructs a recent committed block window behind the root
  • resets block policy from that committed window
  • resets the txpool from that same window
  • rechecks staking-backed validator data when staking is active
  • builds a fresh live ConsensusState
  • emits StartExecution
  • replays cached proposals that arrived while syncing

That is why “done syncing” is better understood as rebuilding live local context from the synchronized anchor, not as flipping one flag.

5.15 One Honest Current-Code Nuance#

The checked-out live-transition path has one especially useful comment: after switching live, it immediately drives a local vote path, and the code notes that in a stricter idealization it would wait for the vote pacing timer, but in practice it treats the shortcut as acceptable. That is a good example of the difference between protocol idealization and implementation pragmatism, and for a book like this, surfacing that kind of nuance increases trust.

5.16 The Validator-Set Recheck On Rejoin#

This is a good example of “real feature, still slightly unfinished detail.” The live-transition path re-reads staking-backed validator data from triedb and checks that it matches the locked validator context loaded at startup. That is real and important.

But the checked-out implementation also carries a TODO. The read currently uses delay_seq_num — the sequence number at the delayed-execution anchor, roughly root_seq_num - execution_delay, which is the oldest point whose execution results the node already trusts. The comment says root_seq_num — the sequence number of the committed restart root itself, which is newer than delay_seq_num by execution_delay blocks — should be used instead. Relevant code lives in monad-state/src/lib.rs.

5.17 Architecture, Current Code, Current Caveat#

Architecture Safe restart needs three things: a certified consensus anchor, enough recent block history, and enough recent execution state at the delayed anchor the live protocol actually depends on.

Current code The node starts in ConsensusMode::Sync, uses BlockBuffer to reason about the restart root, gates live entry through maybe_start_consensus(), and emits StartExecution during the live transition.

Current caveat Some sync thresholds are more explicit in the config model than in the visible startup path, and the staking-backed validator-set recheck still carries a TODO around which sequence number should be read.

What To Remember#

  • Consensus and execution revisions activate on different clocks.
  • A forkpoint is a restart anchor, not just a latest-block pointer.
  • The node starts in sync mode, not live mode.
  • BlockBuffer exists so sync mode can still reason about useful proposal and ancestry information.
  • Block sync and state sync solve different problems.
  • maybe_start_consensus() is the live-transition gatekeeper.
  • The node syncs to a delayed execution anchor implied by the protocol, not an arbitrary tip snapshot.
  • DoneSync rebuilds more than one subsystem before the node becomes live.
