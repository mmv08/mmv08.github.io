Chapter 7: Execution Data Model and State Transition

monad-client-book/07-execution-data-model-and-state-transition.md View source →

The last chapter explained where execution lives. This chapter explains what execution actually consumes and produces: execution-side block types, delayed-execution fields, static Monad block validation, sender and authority recovery, system transactions, reserve-balance enforcement, and staking-backed validator-set reads. After this chapter, the execution repo should read as a concrete state-transition engine, not as “the other half of the system.”

Why This Chapter Matters#

One sentence needs to feel real before the rest of the chapter makes sense: execution validates more than plain EVM bytecode effects. It also validates Monad-specific block-shape rules, delayed-result bookkeeping, system-transaction ordering, reserve-balance rules designed for delayed execution, and staking-backed validator-set reads.

If you only open one execution file first, open cmd/monad/runloop_monad.cpp. That is where the ordered block arrives, delayed results are checked against canonical history, and execution outputs get published.

7.1 Execution Mirrors Consensus Blocks In C++#

Execution does not consume the Rust block structs directly. It has its own C++ mirror types, defined in files such as category/execution/monad/core/monad_block.hpp and category/execution/monad/core/rlp/monad_block_rlp.cpp.

Important mirrored types include MonadVoteV0, MonadVoteV1, MonadQuorumCertificate, MonadConsensusBlockHeader, MonadConsensusBlockBody, and MonadConsensusBlock. The execution daemon is therefore not operating on vague wire bytes. It decodes into a typed model and validates that model.

7.2 The Mirror Is Close, But Also Versioned#

The execution-side model is close to the Rust-side consensus model, but it is not a timeless one-struct-for-all-history design. One clear example is the vote family: MonadVoteV0 carries parent_id and parent_round, while MonadVoteV1 is smaller. That tells you something useful about the execution repo — it mirrors consensus closely, and it also preserves historical format compatibility explicitly. So “same block model” and “same exact source type” are not the same statement.

7.3 The Execution-Side Header Still Has Four Layers#

At a high level, the execution-side header carries four kinds of information.

Layer 1: Consensus Position#

  • block_round
  • epoch
  • seqno
  • author
  • qc

Layer 2: Time And Proof#

  • timestamp_ns
  • round_signature

Layer 3: Delayed Execution Boundary#

  • delayed_execution_results
  • execution_inputs

Layer 4: Fee And Payload Identity#

  • block_body_id
  • base_fee
  • base_fee_trend
  • base_fee_moment

That third layer is the most Monad-specific part. The Rust and C++ field order is delayed_execution_results first, then execution_inputs. Conceptually, it helps to read the pair like this: here is finalized evidence about earlier delayed execution work, and here is the execution request for this block. The header does not only say “here is a block to execute.” It ties this block to two different points in the delayed pipeline.

Abridged from production code. The important detail is that execution decodes its own typed mirror of the BFT header, including the delayed fields and fee-state fields:

template <class MonadQuorumCertificate>
struct MonadConsensusBlockHeader
{
    uint64_t block_round{0};
    uint64_t epoch{0};
    MonadQuorumCertificate qc{}; // qc is for the previous block
    byte_string_fixed<33> author{};
    uint64_t seqno{0};
    uint128_t timestamp_ns{0};
    byte_string_fixed<96> round_signature{};
    std::vector<BlockHeader> delayed_execution_results{};
    BlockHeader execution_inputs{};
    bytes32_t block_body_id{NULL_HASH_BLAKE3};

    bytes32_t parent_id() const noexcept
    {
        return qc.vote.id;
    }
};

struct MonadConsensusBlockHeaderV2 : MonadConsensusBlockHeaderV1
{
    uint64_t base_fee{0};
    uint64_t base_fee_trend{0};
    uint64_t base_fee_moment{0};
};

The execution side is not guessing at consensus metadata. It has a concrete C++ shape that mirrors the Rust-side block contract.

7.4 The Canonical EXECUTION_DELAY = 3 Timeline#

This is the full version of the first-pass picture from the introduction. Suppose consensus orders blocks B100, B101, B102, and B103, and the current node wiring uses EXECUTION_DELAY = 3. Then the useful mental model is:

Ordered blockWhat the block newly ordersWhat later blocks can say about it
B100new execution work for block 100later delayed results can report what execution concluded for B100
B101new work for block 101still too early to treat B101 as the newest execution truth
B102new work for block 102stale-state safety is still relevant while ordering continues
B103new work for block 103delayed results for older work such as B100 can now be carried and validated

The critical invariant is this: when a delayed execution result claims to belong to an earlier block, execution must check that the earlier block matches the canonical block history this node believes in. That is why delayed-result validation exists. Without it, a malicious or corrupted payload could try to attach an earlier result to the wrong chain context.

7.5 Why BlockHashBuffer Exists#

BlockHashBuffer is a small helper protecting an important invariant. Execution cannot safely accept a delayed result just because the payload says “this result belongs to old block X.”

It has to check which earlier block the result claims, whether that block matches local canonical block history, and whether the delayed result fits the pipeline the local node has seen. That is why runloop_monad.cpp validates delayed results against prior canonical block history through a BlockHashBuffer. The buffer ties delayed results back to real earlier blocks, instead of treating them as standalone blobs.

7.6 Static Validation Happens Before Full State Transition#

Execution-side validation is layered. Two especially important helpers are static_validate_consensus_header(...) and static_validate_monad_body(...), and these cheap checks happen before deeper stateful work. That mirrors the defensive shape we already saw on the Rust side: reject obviously bad structure early, and do expensive stateful work only after the cheap checks pass.

7.7 Monad Block-Body Rules Are Revision-Gated#

This is one of the places where “architecture” and “current code” must stay separate.

The execution-side static Monad block-body checks in validate_monad_block.cpp are revision-gated.

A brief note on the naming: the execution side names Monad protocol revisions with an ordinal suffix, MONAD_ZERO, MONAD_ONE, MONAD_TWO, and so on up through MONAD_NINE in the current code (see category/vm/runtime/storage_costs.hpp). Each revision is a protocol version that turns on a specific bundle of rule changes at a configured block. Writing MONAD_FOUR+ means “this rule is active at MONAD_FOUR and every later revision.”

In the current implementation, the body checks discussed here are active for MONAD_FOUR+. So when you read a rule table like this one, read it as current behavior for relevant revisions, not as timeless law for every historical block version.

Concrete Static Rules Enforced Here#

RuleWhy it matters
header timestamp must match execution_inputs.timestampconsensus metadata and execution request must describe the same block
V2 header base_fee must match execution_inputs.base_fee_per_gasfee state must stay aligned across layers
system transactions must come first in the blockprotocol-owned work must not drift into the user-transaction section
there may be at most one reward transactionreward handling stays deterministic and bounded
reward value is capped at 25 MONmalformed blocks cannot smuggle an arbitrary reward

Those are not generic EVM rules. They are Monad block-shape rules around execution.

Abridged from production code. The important details are the revision gate, the system-transaction prefix rule, and the bounded reward rule:

Result<void> static_validate_monad_body(
    std::span<Address const> const senders,
    std::span<Transaction const> const txns)
{
    if constexpr (traits::monad_rev() < MONAD_FOUR) {
        return outcome::success();
    }

    auto const first_user_sender = std::find_if_not(
        senders.begin(), senders.end(), [](Address const &sender) {
            return sender == SYSTEM_SENDER;
        });

    auto const bad_system_sender =
        std::find(first_user_sender, senders.end(), SYSTEM_SENDER);
    if (MONAD_UNLIKELY(bad_system_sender != senders.end())) {
        return MonadBlockError::SystemTransactionNotFirstInBlock;
    }

    auto const end_system_txn =
        txns.begin() + std::distance(senders.begin(), first_user_sender);
    auto const is_reward = [](Transaction const &tx) { return tx.value > 0; };

    auto const first_reward_txn =
        std::find_if(txns.begin(), end_system_txn, is_reward);
    if (MONAD_UNLIKELY(first_reward_txn == end_system_txn)) {
        return outcome::success();
    }

    auto const another_reward =
        std::find_if(std::next(first_reward_txn), end_system_txn, is_reward);
    if (MONAD_UNLIKELY(another_reward != end_system_txn)) {
        return MonadBlockError::MultipleRewardTransactions;
    }

    constexpr uint256_t MAXIMUM_BLOCK_REWARD = 25 * staking::MON;
    if (MONAD_UNLIKELY(first_reward_txn->value > MAXIMUM_BLOCK_REWARD)) {
        return MonadBlockError::InvalidRewardValue;
    }

    return outcome::success();
}

This is why “system transactions come first” is not only a convention. It is a block validity check.

7.8 Sender Recovery Is Not The Whole Story#

runloop_monad.cpp does more than recover transaction senders. It also recovers EIP-7702 authorities and carries those into later reasoning.

EIP-7702 is an Ethereum Improvement Proposal that lets an externally-owned account temporarily delegate its code to another address for the duration of a transaction, by signing an authorization list embedded in that transaction. Each authorization entry is itself signed, so recovery has to extract the per-authority signer, not just the outer transaction sender.

That matters because several later policies depend on more than the plain transaction signer. Txpool ingress limits, nonce and authority bookkeeping, and reserve-balance behavior around delegated accounts all look at authorities too. Sender recovery is necessary, and authority recovery is also part of the full state-transition path.

7.9 System Transactions Are Explicit Protocol Objects#

System transactions are not hidden side effects. They are explicit transactions derived deterministically from block context.

On the Rust side, monad-system-calls decides which system transactions should exist. On the execution side, validate_system_transaction.* checks them and execute_system_transaction.* applies them. That shared determinism is what makes them safe: if Rust and C++ derive different expected system transactions for the same block context, the block is invalid.

They also have a narrow concrete shape. In this source version, system transactions use the reserved system sender, legacy transaction form, staking precompile target, zero gas fields, no EIP-7702 authorization list, and a checked system nonce.

After the leading system-transaction prefix, ordinary user transactions are explicitly forbidden from using the system sender or restricted staking call shapes. So “system transaction” does not mean “any transaction generated by protocol code”; it means a tightly validated protocol object.

A Concrete Two-Block Example#

The generator is clearest across two neighboring blocks rather than one block that does everything. If staking is active, a boundary block can include Snapshot and Reward, and the first block of the next epoch can include EpochChange and Reward.

Those transactions must appear before user transactions, and the execution-side static validator enforces that ordering.

One activation edge case matters. If staking activates at epoch 2, the generator also carries a genesis-adjacent special case that can emit EpochChange at the first live block. That does not change the steady-state picture above. It means the table is the common case, not the whole generator.

Abridged from production code. The important detail is that system transactions are both generated and then re-derived for validation:

fn generate_system_calls<CCT, CRT>(
    proposed_seq_num: SeqNum,
    proposed_epoch: Epoch,
    parent_block_epoch: Epoch,
    block_author_address: Address,
    chain_config: &CCT,
) -> Vec<SystemCall> {
    let epoch_length = chain_config.get_epoch_length();
    let staking_activation = chain_config.get_staking_activation();
    let mut system_calls = Vec::new();

    let generate_snapshot_txn = proposed_seq_num.is_boundary_block(epoch_length)
        && proposed_seq_num.get_locked_epoch(epoch_length) >= staking_activation;
    if generate_snapshot_txn {
        system_calls.push(SystemCall::StakingContractCall(
            StakingContractCall::Snapshot,
        ));
    }

    let is_first_epoch_block =
        parent_block_epoch != proposed_epoch && proposed_epoch >= staking_activation - Epoch(1);
    let is_genesis_block =
        proposed_seq_num == GENESIS_SEQ_NUM + SeqNum(1) && staking_activation == Epoch(2);
    if is_first_epoch_block || is_genesis_block {
        system_calls.push(SystemCall::StakingContractCall(
            StakingContractCall::EpochChange { new_epoch: proposed_epoch },
        ));
    }

    if proposed_epoch >= staking_activation {
        let block_reward_mon = chain_config.get_block_reward_mon(proposed_epoch);
        let block_reward = U256::from(StakingContractCall::MON) * U256::from(block_reward_mon);
        system_calls.push(SystemCall::StakingContractCall(
            StakingContractCall::Reward { block_author_address, block_reward },
        ));
    }

    system_calls
}

And later, block policy validates the prefix against the same derived calls:

let expected_sys_calls = generate_system_calls(
    block_header.seq_num,
    block_header.epoch,
    parent_block_epoch,
    block_header.author.pubkey().get_eth_address(),
    chain_config,
);

if expected_sys_calls.len() != sys_txns.len() {
    return Err(SystemTransactionValidationError::UnexpectedSystemTransaction);
}

for (expected_sys_call, sys_txn) in expected_sys_calls.into_iter().zip(sys_txns) {
    expected_sys_call.validate_system_transaction_input(sys_txn)?;
}

The leader does not get to invent protocol-owned execution work. Honest nodes regenerate the expected work and compare.

7.10 Reserve Balance: Why The Rule Exists#

Reserve balance only makes sense once delayed execution has clicked. Consensus decides whether to accept a transaction using state that is behind the newest ordered tip. That creates a problem: a sender may look solvent at the lagged state, earlier delayed blocks may already consume that sender’s future gas-paying capacity, and by the time the later transaction reaches execution, the sender may no longer be able to pay for what was already ordered.

Reserve balance is the protection against that stale-state overbooking. The short rule is that reserve balance protects gas-paying ability across the delayed window, not that it is just “always leave 10 MON behind.”

7.11 Reserve Balance Lives In Two Places#

Reserve balance is not one check in one file. It is a cross-layer rule.

Rust-Side Policy#

On the consensus side, monad-eth-block-policy reconstructs recent in-flight pressure and asks whether a new transaction or block would oversubscribe the protected budget. Important entry points include compute_account_base_balances(...), try_add_transaction(...), and try_apply_block_fees(...).

C++ Execution Enforcement#

On the execution side, category/execution/monad/reserve_balance.cpp enforces the rule during real execution. So the full picture is that Rust tries to avoid ordering an overcommitted future, and C++ enforces the same promise when execution catches up. That is the correct step-by-step story.

The Emptying-Transaction Nuance#

The rule is not simply “an account must always leave 10 MON behind.” The code is more specific: plain non-delegated accounts get a narrow emptying-transaction allowance, delegated accounts are treated more conservatively, and recent pending-history windows matter. That is why the best short summary is still that reserve balance protects gas-paying ability across the delayed window.

Abridged from production code. The important detail is that execution enforcement is revision-gated and checks recent sender/authority history before allowing a sender to dip into reserve:

void ReserveBalance::init_from_tx(
    Address const &sender,
    Transaction const &tx,
    std::optional<uint256_t> const &base_fee_per_gas,
    uint64_t i,
    ChainContext<traits> const &ctx)
{
    constexpr bool tracking_disabled = []() {
        if constexpr (!is_monad_trait_v<traits>) {
            return true;
        } else {
            return traits::monad_rev() < MONAD_FOUR;
        }
    }();

    if constexpr (tracking_disabled) {
        tracking_enabled_ = false;
        return;
    }

    bool const sender_can_dip = can_sender_dip_into_reserve<traits>(
        sender, i, is_delegated(*state_, sender_code_hash), ctx);

    tracking_enabled_ = true;
    sender_ = sender;
    sender_gas_fees_ = uint256_t{tx.gas_limit} *
        gas_price<traits>(tx, base_fee_per_gas.value_or(0));
    sender_can_dip_ = sender_can_dip;
}

bool can_sender_dip_into_reserve(
    Address const &sender,
    uint64_t const i,
    bool const sender_is_delegated,
    ChainContext<traits> const &ctx)
{
    if (sender_is_delegated) {
        return false;
    }
    if (ctx.grandparent_senders_and_authorities.contains(sender) ||
        ctx.parent_senders_and_authorities.contains(sender)) {
        return false;
    }
    if (ctx.senders_and_authorities.contains(sender)) {
        for (size_t j = 0; j <= i; ++j) {
            if (j < i && sender == ctx.senders.at(j)) {
                return false;
            }
            if (std::ranges::contains(ctx.authorities.at(j), sender)) {
                return false;
            }
        }
    }
    return true;
}

This is the delayed-execution intuition made concrete: recent unexecuted pressure changes whether a later transaction may consume the protected budget.

7.12 Reserve-Balance Enforcement Is Not The Same Thing As The Reserve-Balance Precompile#

These are two different ideas.

ConceptCurrent gate in codeWhat it means
reserve-balance enforcementMONAD_FOUR+execution actually enforces the stale-state safety rule
reserve-balance precompile exposureMONAD_NINE+contracts and tools can query reserve-balance information through a dedicated precompile

If those get merged into one sentence, the revision story becomes wrong.

There is one more naming caveat. Rust chain config exposes execution revision activation fields such as V_ZERO, V_ONE, V_TWO, and V_FOUR, while execution-side code also uses internal MONAD_* revision names for VM, storage, precompile, and validation gates. Do not assume every execution-side MONAD_* constant has a one-to-one field in Rust chain config.

7.13 Gas-Charging Nuance: Real Execution Versus Hosted eth_call#

This is one of the few places where a reader can build an incorrect model from technically correct fragments.

For real Monad transaction execution in current Monad revisions, the execution tests show that from MONAD_ONE onward, gas charging is based on the full gas limit in the Monad path being exercised there, and gas refunds are treated as zero in those Monad execution paths. That is one reason oversized gas limits are more expensive than an Ethereum reader may expect.

Hosted eth_call exposes two different user-facing surfaces. The top-level RPC result still needs a meaningful “actual gas used” answer for call and trace reporting. Traced final call frames can still report gas_used equal to the gas limit because refunds are zero.

So read the hosted path this way: the underlying Monad execution rules still apply, the top-level call result still reports actual gas used, and the final traced call frame can still report gas_used equal to the gas limit. On-chain Monad execution economics and hosted eth_call reporting are related, but not identical.

RPC gas methods add one more layer on top of that hosted execution path. In the source version used by this book, eth_estimateGas searches for a gas limit that lets the simulated transaction execute successfully. eth_fillTransaction uses the same estimation machinery for missing gas, but it runs in a different mode: execution errors and reserve-balance violations can be terminal enough to fill a gas limit, because the method is trying to construct a signable transaction rather than promise that the transaction will succeed on chain.

7.14 Staking Integration: Three Validator Views#

The execution-side staking contract maintains more than one useful validator view.

The most important ones are:

ViewWhat it means
execution viewexecution-side validator records such as keys and contract-owned metadata
consensus viewthe stake-ordered set consensus wants for the next admissible epoch read
snapshot viewa frozen current-epoch view used during the epoch-delay window

read_valset(...) does not return one raw internal contract blob. It combines keys from execution-side validator records with stake from the currently admissible consensus-facing view.

7.15 read_valset(...) Has Strict Epoch Admissibility#

The execution-side validator-set read is narrow by design. read_valset(db, block_num, requested_epoch) can return only the current contract epoch, or the next epoch (and only when in_epoch_delay_period is true). Requests that are too old or too far in the future return nullopt. This is the execution-side half of the validator lifecycle from Chapter 2.

7.16 The Full State-Transition Shape#

Execution is not just “call the EVM.”

It is a structured pipeline:

flowchart LR
    Ledger["consensus block from ledger"] --> Decode["decode execution-side block model"]
    Decode --> Static["static header/body validation"]
    Static --> Recover["recover senders and authorities"]
    Recover --> Delayed["validate delayed results against canonical earlier block history"]
    Delayed --> MonadRules["apply Monad-specific checks"]
    MonadRules --> Execute["run block execution"]
    Execute --> Commit["build commit data"]
    Commit --> Triedb["write recent state and block data"]
    Commit --> Events["emit execution events"]

That is the right level of abstraction to carry forward.

7.17 Execution Outputs Are For Other Consumers Too#

Execution does not “finish” when it computes a state transition. It finishes when the rest of the node can consume the result. The main outputs are finalized delayed-execution result data for future blocks, triedb updates for retained recent state and block data, and event-ring updates for live consumers. So the last stage of execution is not only state mutation — it is also publication.

7.18 Architecture, Current Code, Current Caveat#

Architecture Execution validates block shape, delayed-result consistency, and Monad-specific state-transition rules in layers before publishing durable and live outputs.

Current code runloop_monad.cpp validates delayed results against canonical block history, validate_monad_block.cpp applies revision-gated block rules, and read_valset.cpp exposes a narrow epoch-admissible validator read path.

Current caveat Hosted eth_call exposes two gas-reporting surfaces: the top-level result still reports actual gas used, while traced final call frames can still report gas_used equal to the gas limit because refunds are zero in current Monad revisions.

What To Remember#

  • Execution consumes its own typed C++ mirror of the consensus block model.
  • Delayed execution is visible directly in the header shape through execution_inputs and delayed_execution_results.
  • Delayed results are validated against canonical earlier block history, not blindly trusted.
  • Monad-specific block validation adds revision-gated structural rules beyond ordinary EVM execution.
  • System transactions are explicit deterministic protocol objects with a narrow validated shape, not generic hidden side effects.
  • Reserve balance is a cross-layer stale-state safety rule, with Rust-side policy checks and C++ execution enforcement.
  • Reserve-balance enforcement and the reserve-balance precompile are different concepts with different activation gates.
  • On-chain Monad gas behavior and hosted eth_call reporting should not be collapsed into one sentence.
  • Validator-set reads are execution-backed and epoch-admissibility constrained.
