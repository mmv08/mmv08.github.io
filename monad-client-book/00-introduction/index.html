The Monad Client: A Bottom-Up Code Walkthrough

What This Book Is#

This book is a code-first walkthrough of how a Monad node works.

It is written for engineers who already know Solidity, Ethereum transactions, and the basics of blocks, receipts, logs, and JSON-RPC. JSON-RPC is the HTTP-and-JSON request format that Ethereum clients expose to wallets, scripts, and block explorers.

This book starts from that familiar surface and follows the code inward: how Monad orders blocks, how execution is wired into ordering, how the repositories are split, how the running processes cooperate, and where to start reading without getting lost.

The goal is not to memorize crate names. The goal is to build a mental model that stays correct when you open the code.

The main path is concrete. A wallet request enters the txpool, the in-memory pool of pending transactions. A leader may include it in a proposal. As consensus advances through proposals, votes, certificates, timeouts, and commits, monad-node persists block data and proposed/voted/finalized head markers to the ledger. Execution later processes those ordered blocks. TrieDb stores the resulting recent execution state in MonadDB. RPC responses and subscriptions expose that result back to users.

What This Book Is Not#

This book is not a formal consensus spec, a public RPC reference, a substitute for reading tests, or a promise that every current implementation detail is permanent.

Some parts of Monad are stable architecture. Some parts are current wiring. Some parts are still marked as TODOs in the code. This book calls out those differences when they matter.

The First Picture To Lock In#

Before reading any chapter, keep four facts in view. Monad is one client system split across two repositories. A real node is usually several cooperating processes. Execution is intentionally delayed. And “latest” depends on which subsystem you are asking. Those four facts explain many code paths that otherwise look unrelated.

For the consensus chapters, keep one smaller through-line in view too. Consensus is the part of the client that lets many validators agree on one ordered chain even when messages are delayed and some validators may behave incorrectly or maliciously. The code keeps returning to four questions:

  1. who is allowed to act?
  2. what exact statement did they sign?
  3. has enough stake signed the same statement?
  4. what is this node now safe to do?

Chapters 1 through 5 build that through-line from the bottom up. Chapter 1 gives the clocks, identities, hashes, and signature roles. Chapter 2 explains who may act and how leader choice works. Chapter 3 introduces the signed statements and certificates. Chapter 4 shows the live state machines that process those objects. Chapter 5 shows how a restarted node rebuilds enough context to rejoin without breaking the same safety rules.

One Client, Two Repos, One Shared Execution Library#

Monad is split across two repositories:

  • monad-bft: the Rust-side consensus, networking, sync, txpool, node, and RPC repo
  • monad: the execution repo, centered on the execution engine, MonadDB, TrieDb, hosted execution APIs, and the execution daemon

MonadDB is the lower-level database engine in category/mpt. TrieDb is the execution-state layer built on top of it. TrieDb stores recent accounts, storage slots, contract code, receipts, transactions, headers, and block lookup data in MonadDB. Rust code reads that layer through triedb handles and adapters such as TriedbEnv. Hosted execution APIs are execution functions loaded into Rust-side processes so they can be called without an extra process.

That split is architectural, not cosmetic.

At the same time, the execution repo is not “just the daemon repo.”

Most execution code is built around a shared execution library. CMake, the build system used by the execution repo, builds this library through the monad_execution target. That target produces libmonad_execution, the library file that other execution surfaces link against.

That execution-owned core is consumed in more than one way: by the stand-alone execution daemon, by hosted execution APIs loaded into Rust-side processes, and by tools and tests in the execution repo itself.

So the stable picture is this: the repository boundary and ownership boundary stay constant, but the process boundary depends on which execution surface is being used. Monad can feel hard to read at first because repository boundaries and process boundaries are related, but they are not identical.

One Node, Usually Three Core Processes#

In normal day-to-day operation, the core validator/RPC path is usually three cooperating processes:

  • monad-node: consensus, validator networking, sync, txpool ownership, and ledger persistence
  • monad-rpc: JSON-RPC and WebSocket edge
  • monad: the execution daemon that reads ordered blocks from the ledger and writes execution outputs

There is also one more execution mode that does not get its own process: hosted execution APIs loaded directly into Rust-side processes.

Deployments can include supporting services around this core path, such as archive, index, checker, or upload jobs. Those services matter operationally, but they are not the minimal process split this book follows first.

That matters because execution is not only the stand-alone daemon. The same execution repo is also consumed through hosted APIs for triedb reads, eth_call, execution-event consumption, and staking-backed validator-set reads.

So the right mental model is one consensus repo, one execution repo, one shared execution core, and several execution consumption paths — not one Rust program that somehow also “does execution.”

The deployment files make the process split concrete. Abridged from the pinned systemd units:

# debian/usr/lib/systemd/system/monad-bft.service
ExecStart=/usr/local/bin/monad-node \
    --mempool-ipc-path /home/monad/monad-bft/mempool.sock \
    --statesync-ipc-path /home/monad/monad-bft/statesync.sock \
    --ledger-path /home/monad/monad-bft/ledger \
    --triedb-path /dev/triedb

# debian/usr/lib/systemd/system/monad-execution.service
ExecStart=/usr/local/bin/monad \
    --db /dev/triedb \
    --block_db /home/monad/monad-bft/ledger \
    --statesync /home/monad/monad-bft/statesync.sock

# debian/usr/lib/systemd/system/monad-rpc.service
ExecStart=/usr/local/bin/monad-rpc \
    --ipc-path /home/monad/monad-bft/mempool.sock \
    --triedb-path /dev/triedb

The important detail is not systemd itself. It is that consensus, execution, and RPC cross real runtime boundaries through sockets, ledger files, and triedb.

The excerpt is also intentionally the core shape, not every optional wire. WebSocket subscriptions and the freshest event-buffered RPC paths require execution event-ring wiring, such as an execution-side event ring path plus the RPC-side --exec-event-path. Chapter 12 shows that if WebSockets are enabled without that event path, current RPC startup fails fast.

The Runtime Boundaries That Actually Matter#

When you read the code, do not only ask where a feature lives. Also ask which boundary that feature is crossing right now. These are the main boundaries that show up repeatedly:

One Transaction, End To End#

Before diving into types, hold one concrete story in your head.

The Short Story#

  1. A wallet sends a transaction to monad-rpc.
  2. monad-rpc forwards it over a Unix socket to the txpool owned by monad-node.
  3. The txpool validates it against current retained state plus delayed-window policy.
  4. When the node is leader, proposal construction combines deterministic system transactions with eligible user transactions from the txpool.
  5. Consensus advances through proposals, votes, certificates, timeouts, and commits.
  6. As those states advance, monad-node persists block files and proposed/voted/finalized head markers to the ledger.
  7. The execution daemon later reads the ordered block from the ledger.
  8. Execution validates the Monad-specific block shape, executes the block, writes triedb updates, and emits fresh execution events.
  9. monad-rpc answers different methods from different surfaces: triedb for retained recent state, recent in-memory event buffers for the freshest recent outputs, and archive readers for older block-oriented history.

Delayed Execution In One First-Pass Timeline#

Delayed execution is the most important Monad-specific idea in this book. You do not need every detail yet, but you do need one stable first picture.

In the current monad-node wiring, EXECUTION_DELAY = 3, which means the useful first-pass model is:

When block is orderedWhat is true right awayWhat happens later
block N is orderedconsensus can keep movingexecution of N finishes later
block N+1 is orderedconsensus still has not fully “caught execution up” to the tipmore delayed pipeline work accumulates
block N+2 is orderedvalidators are still reasoning over a lagged execution viewreserve-balance rules matter because ordering sees stale state
block N+3 is ordereda later block can now carry delayed execution results for older work such as Nexecution validates those delayed results against canonical earlier block history

One consequence of this is that a single Monad block can talk in two time directions at once: forward, “here is the new work this block orders,” and backward, “here are delayed execution results for earlier ordered work.”

This single fact explains several later details. Coherency is not the same thing as structural validity. Block headers carry both execution_inputs and delayed_execution_results. Reserve balance exists. State sync targets a delayed execution anchor. And “latest ordered block” and “latest executed state” are different questions.

Later chapters make this exact timeline precise. The appendix keeps one canonical version handy: Appendix: Glossary, Timelines, and Reading Maps.

What This Book Means By “Ordered”#

This book often says “ordered block” to mean a consensus block that has entered the ordered block pipeline. Other subsystems can now reason about that block.

That is not always the same thing as finalized. When commit state matters, the book uses the more precise words proposed, voted, finalized, and, for execution-event output, verified.

The Three Main Clocks#

Monad does not run on one time axis. Three clocks show up everywhere:

ClockWhat it countsWhy it exists
Roundone consensus attemptpacemaker logic, proposal timing, timeouts, certificates
SeqNumordered consensus block heightancestry, delayed execution inputs, restart anchors
Epochvalidator-set eraquorum accounting, validator selection, leader election

The most common early mistake is to blur Round and SeqNum. Keep three questions separate. Round asks which consensus attempt we are on. SeqNum asks how deep the ordered chain is. Epoch asks which validator set is allowed to act for this round.

Rounds can advance without a new committed block. Sequence numbers advance only when a new ordered block exists.

Two More Round Words You Must Not Blur#

Later chapters will introduce block_round and proposal_round. For now, keep the short version.

block_round is when the block was originally authored, and it lives as a field on the block header itself. proposal_round is when the current proposal message is being sent, and it lives on the proposal message, not the header.

The two live in different places in the code: one is fixed in the block header at authoring time, and the other travels with whichever proposal message is currently carrying that header.

On the happy path they match. On recovery paths they can diverge. That split is one of the reasons the recovery code feels unfamiliar at first.

Freshness Words: proposed, voted, finalized#

Several subsystems use the same three freshness words — proposed, voted, and finalized — and they do not mean “three completely different worlds.” They mean progressively stronger views of the chain.

WordShort meaning
proposednewest observed head
votedstronger intermediate head
finalizeddurable committed anchor

These words show up in ledger head markers, triedb metadata, execution events, recent buffers, RPC method resolution, and WebSocket subscriptions. So “what is latest?” is not enough.

Ask three smaller questions instead: latest according to which subsystem, latest retained by which store, and latest safe for which kind of read?

There is also a fourth execution-event state worth knowing early: verified. In this codebase, verified means execution outputs and the state root for a block have been included in a finalized later block.

It is part of the execution-event vocabulary, while proposed, voted, and finalized are the main head words you see across ledger, triedb metadata, buffers, and RPC block-tag resolution.

Later chapters map Ethereum-style block tags such as latest, safe, and finalized onto these freshness views and the read surfaces that can actually answer them. Do not assume one hidden universal database is sitting underneath all three.

The appendix has one cross-subsystem table for this too: Appendix: Glossary, Timelines, and Reading Maps.

The Main Read Surfaces#

Monad does not put all durable and recent information into one database. That split is deliberate.

SurfaceBest mental modelMain consumers
ledgerdurable consensus block historyrestart, execution daemon, block sync
triedbretained recent execution state and recent block-oriented execution dataconsensus reads, RPC reads
event ringfreshest execution-event streamWebSockets, recent buffers
WALreplay notebook of node inputsreplay tools, debugging
archiveolder block-oriented historyhistorical RPC

The practical consequence is simple: different RPC methods are backed by different surfaces, and the freshest observable event and the most authoritative retained state may come from different places.

A Working Glossary#

These definitions are worth learning early because later chapters reuse them without apology.

valid
Structurally and cryptographically acceptable.

coherent
Valid and also consistent with the chain and delayed-execution state context the node currently has.

missing ancestor
The block may be fine, but local ancestry is incomplete.

lagging state
The node’s execution-side state is too far behind to participate safely.

forkpoint
The restart anchor: committed root plus high certificate plus nearby validator context.

block sync
Fetch missing consensus blocks and ancestry.

state sync
Fetch recent execution state so the node does not replay everything from genesis.

MonadDB
The lower-level Merkle-Patricia-trie database engine.

triedb / TrieDb
The retained recent execution-state layer built on MonadDB.

event ring
The freshest live execution-event stream.

archive
Older block-oriented history. Not a general historical world-state engine.

For the larger reference version, use the appendix: Appendix: Glossary, Timelines, and Reading Maps.

How To Use This Book#

Read the chapters in order. Each one builds on the vocabulary and mental model set up by the previous one, and that progression is part of the pedagogy. If you want to jump ahead, the table of contents in the sidebar is there for you, but the default assumption is a start-to-finish read.

Each chapter tries to answer four questions:

  1. What problem is this subsystem solving?
  2. What minimum nouns do you need before opening the code?
  3. What real path through the code should you follow first?
  4. Which details are architecture, and which are only current wiring?

The fastest way to get value from a single chapter is to read it once for the mental model, open the listed files and entrypoints, follow one real path through the code, and then come back and read the chapter again more slowly.

What To Keep In Your Head Before Chapter 1#

If you keep only nine facts from the introduction, keep these:

  • Monad is one client system split across two repos.
  • A real node is usually several cooperating processes, plus hosted execution APIs.
  • The execution repo owns a shared execution core reused in daemon and hosted modes.
  • Consensus repeatedly asks who may act, what was signed, whether enough stake signed it, and what is safe next.
  • Round, SeqNum, and Epoch are different clocks for different jobs.
  • block_round and proposal_round are different because recovery is a real path.
  • Consensus ordering and execution are intentionally separated by a delay.
  • Different read surfaces answer different kinds of “latest.”
  • “Latest ordered block” and “latest executed state” are not the same question.
