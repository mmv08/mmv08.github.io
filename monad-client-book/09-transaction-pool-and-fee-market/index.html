Chapter 9: Transaction Pool and Fee Market

monad-client-book/09-transaction-pool-and-fee-market.md View source →

Now that execution concepts are on the table, the txpool becomes much easier to read. The txpool sits at a busy crossroads: it receives transactions from RPC and peers, it applies execution-aware validation, it feeds leaders when they build proposals, and it reacts to commits, rounds, and extending-path state. That is why this chapter belongs after the execution chapters rather than before them.

Why This Chapter Matters#

If you only think of the txpool as a mempool that sorts by fees, you will miss most of the interesting logic. Monad’s txpool has to reason about delayed execution, reserve balance, system transactions, per-sender nonce continuity, and extending-path transactions that are not yet executed but already matter.

One of those words deserves a quick inline definition here. Reserve balance is a per-sender admission rule that Monad applies at ordering time. Because execution runs behind ordering, the txpool cannot see each sender’s freshest post-execution balance, so instead it reserves a worst-case debit per pending transaction. A sender’s pending transactions are only admissible if their reserved debit fits within this stale-state-aware budget. Chapter 15 goes deeper into why this exists.

9.1 The Txpool Lives On The Rust Side#

The main crates are monad-eth-txpool, monad-eth-txpool-executor, monad-eth-txpool-ipc, and monad-eth-txpool-types. This is a Rust subsystem, not part of the execution daemon, and that is deliberate: the txpool needs tight contact with consensus rounds, proposal assembly, forwarding behavior, and local block-commit updates.

9.2 There Are Three Sources Of Transactions#

Transactions enter proposal construction from three broad sources:

  1. RPC ingress over the txpool IPC socket
  2. forwarded peer traffic
  3. deterministic system-transaction generation

The third source should be kept mentally separate from the first two. System transactions are not just another mempool lane — they are protocol-required contents derived from block context.

9.3 User Ingress Is Fenced Off From System-Owned Behavior#

The txpool does not accept any valid-looking Ethereum transaction and sort it out later. It applies hard fences up front.

Reserved System Sender Is Rejected#

The txpool rejects transactions whose signer is the reserved system sender.

Restricted System Calls Are Rejected#

Normal user ingress also rejects restricted system calls that try to mimic protocol-owned staking or other system behavior.

That means a user cannot smuggle protocol behavior into the mempool by crafting a lookalike transaction.

EIP-7702 Authorization Length Limit Is A Local Policy#

EIP-7702 (introduced in more detail in Chapter 7) is an Ethereum Improvement Proposal letting an externally-owned account delegate its code for the duration of a transaction through a signed authorization list. Each entry in that list is itself a signature that the node must recover, so the list length directly controls local verification cost.

The txpool enforces a maximum authorization-list length for EIP-7702 transactions. This deserves precise wording: it is a txpool ingress policy, it bounds local verification cost, and it is not the whole chain rule by itself. That distinction matters because readers otherwise mistake a local defense for a global protocol invariant.

9.4 PoolTx Wraps More Than The Raw Transaction#

PoolTx is the main txpool object. It wraps the recovered transaction, sender, nonce, max-value and max-gas accounting, recovered EIP-7702 authorizations, and forwarding or ownership metadata. One useful split inside PoolTx is between Owned and Forwarded — that is the txpool-native distinction. System transactions are generated outside this normal ingress path.

9.5 Validation Happens In Layers#

The txpool does not validate everything in one monolithic step.

Static Validation#

This covers chain ID, signature structure, encoded-length limits, unsupported transaction types, and restricted system-like behavior on user ingress. These checks do not need live account state.

Dynamic Validation#

This covers nonce against committed account state, balance sufficiency, and reserve-balance-related checks. This is where the execution chapters start to matter. Even though the txpool is Rust-side, its dynamic reasoning is execution-shaped.

9.6 Future Nonces Can Be Stored Without Being Sequenceable#

One common misunderstanding is that if an account’s nonce is 5, a nonce-7 transaction must be rejected. That is not how this txpool works: a future-nonce transaction can be valid enough to store but not yet valid enough to sequence. That is why the txpool tracks per-sender order instead of one giant global heap.

9.7 Delayed Execution Changes Nonce Reasoning#

Delayed execution means the txpool cannot look only at committed state. It also has to account for extending-path transactions that have already been selected locally, and for pending nonce usage implied by those extending blocks. This is why the policy layer uses NonceUsageMap and related helpers — the txpool is reasoning over committed state, extending blocks, and candidate transactions all at once.

9.8 One Worked Example: Sender Heads Versus Sender Backlog#

Suppose committed state says sender A is at nonce 5. Now suppose an extending block has already consumed nonce 5, the pool contains nonce 6, and the pool also contains nonce 7. Then the proposer should reason like this: the next sequenceable head for A is nonce 6, and nonce 7 is stored but not yet a head.

Now add sender B, whose committed next nonce is 3, with one ready transaction at nonce 3. The sequencer’s real competition is A nonce 6 versus B nonce 3, not every transaction from A and B in one flat fee heap. That is the point of the per-sender-head design.

9.9 Proposal Construction Has Two Inputs, Not One#

When a leader builds a proposal, there are really two transaction sources.

System Transactions#

These are generated deterministically from the proposed sequence number, the proposed epoch, the parent block epoch, the block author address, and the chain config.

User Transactions#

These are selected from txpool state according to sender-head ordering, fee priority, gas and byte budgets, and block-policy validation. Block policy is the monad-eth-block-policy crate’s set of rules that say which transactions a block may contain given current retained state and Monad’s delayed-execution constraints. It is stricter than Ethereum’s mempool filter because it also enforces reserve-balance accounting and coherency with the delayed-execution window.

So proposal construction is not “pick the most profitable raw transactions.” It is “first derive required protocol transactions, then fill the remaining budget with user transactions that are currently sequenceable.”

9.10 A Concrete System-Transaction Timeline#

The generator in monad-system-calls is easier to remember as a timeline.

If staking is active:

Block positionSystem transactions you may see
boundary block at the end of an epochSnapshot, Reward
first block of the next epochEpochChange, Reward
ordinary non-boundary block in an active epochReward

All of those are generated before user sequencing finishes, and execution-side validation later enforces the expected order and shape.

One edge case is worth keeping in the back of your mind. If staking activates at epoch 2, the generator also has a genesis-adjacent special case that can emit EpochChange at the first live block. That does not change the steady-state table above — it just means the table is the common case, not the whole generator.

9.11 ProposalSequencer Uses A Heap Of Sender Heads#

The key file is monad-eth-txpool/src/pool/sequencer.rs. The sequencer builds a heap of sender heads, not a heap of all transactions, which preserves per-sender nonce order naturally.

Ordering Priority#

Among currently usable heads, the main comparison uses transaction-kind priority first, then effective tip per gas, then gas limit.

Virtual Time#

Each sender-head group also carries virtual_time, which acts as a fairness-oriented tie-breaker as groups are replenished.

Partial Shuffle#

Before the heap is finalized, candidate heads are partially shuffled:

heap_vec.partial_shuffle(&mut rand::thread_rng(), tx_limit);

The point is not randomness for its own sake. It is to reduce deterministic starvation patterns among otherwise similar heads. This is a leader-local proposal-quality heuristic applied before the heap is finalized, not a protocol randomness source.

9.12 Why This Randomness Does Not Break Protocol Determinism#

This is the obvious question a careful reader should ask. If proposal sequencing uses local randomness, why is that okay in a consensus system? Because proposal construction and leader election are different kinds of logic.

Leader election must be globally deterministic: every honest node must agree who the leader is for a round. Proposal contents do not need to be globally identical on every honest node before the proposal is seen; they only need to be locally valid for the elected leader and checkable by everyone else once proposed. So leader-election determinism is a protocol safety requirement, while txpool shuffling is a local proposal-quality heuristic. Those belong to different categories.

9.13 Block Policy Still Has Final Say#

Even after the sequencer picks a candidate, inclusion can still fail if the transaction would exceed gas limits, exceed byte-size limits, violate reserve-balance-aware policy, or fail other block-policy checks. So the sequencer is not a blind sorter — it is a guided builder operating inside execution-aware constraints.

9.14 Replacement And Eviction Are Separate From Correctness#

The txpool also has to manage pressure.

Replacement#

If two transactions compete for the same (sender, nonce) slot, the txpool may replace the earlier one with the higher-priority one. One useful nuance in the code comments is that Monad does not require the same style of minimum fee-bump rule many Ethereum clients use. The local reasoning is that replacement happens after most insertion cost is already paid, and Monad’s propagation model is different from a global shared gossip mempool.

Eviction#

Under pressure, lower-priority content can be evicted and expiry becomes more aggressive. That is a healthy separation: correctness rules decide what is valid, while pressure-management rules decide what the local pool keeps.

9.15 The Fee Market Carries More Than One Scalar#

Monad’s fee market lives in monad-tfm. The block header carries base_fee, base_fee_trend, and base_fee_moment, which means the fee market carries more state than Ethereum’s most familiar “single base fee” mental model. The practical takeaway is that base_fee is the current level, base_fee_trend describes movement, and base_fee_moment carries another piece of fee-control state across blocks. You do not need the full formula in this book; you do need to notice that block production and validation carry a richer fee state than a single scalar.

9.16 EthTxPoolExecutor Makes The Txpool Event-Driven#

EthTxPoolExecutor is the runtime shell around the pool. It receives commands such as BlockCommit, CreateProposal, EnterRound, and Reset, and it emits events such as new proposal data, forwarded transactions, and sender-gas contribution data. That is why the txpool is not just a container — it is a real subsystem attached to the node event loop.

9.17 Architecture, Current Code, Current Caveat#

Architecture Proposal construction combines protocol-derived system transactions with locally sequenceable user transactions under execution-aware policy.

Current code ProposalSequencer builds a heap of sender heads, applies a leader-local partial_shuffle before truncating that candidate set, and still routes selected transactions through block-policy checks before inclusion.

Current caveat The system-transaction timeline in this chapter is intentionally the steady-state picture. The generator also carries a genesis-adjacent activation edge case when staking starts at epoch 2.

What To Remember#

  • The txpool is a Rust-side subsystem tightly coupled to consensus and proposal assembly.
  • User ingress is explicitly fenced off from system-owned sender and restricted system-call behavior.
  • Future nonces can be stored even when they are not yet sequenceable.
  • Delayed execution means txpool nonce reasoning must account for extending-path transactions too.
  • Proposal construction has two inputs: deterministic system transactions and txpool-selected user transactions.
  • ProposalSequencer operates on sender heads, not one giant global bag of transactions.
  • Local tx ordering heuristics such as partial shuffle do not violate protocol determinism because only leader identity, certificate validation, and similar protocol facts need global determinism.
  • Block policy still has final say after sequencing.
  • The fee market carries base_fee, base_fee_trend, and base_fee_moment, not just one scalar.
