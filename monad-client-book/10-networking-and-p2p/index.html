Chapter 10: Networking and Peer-to-Peer Communication

monad-client-book/10-networking-and-p2p.md View source →

Consensus correctness is useless if the node cannot move the right message to the right peer quickly enough.

Monad’s networking code becomes much easier to read once you stop looking for one networking crate, one transport, or one peer type. The code does not have any of those. Instead it has a layered stack:

  • monad-dataplane owns sockets, pacing, bans, and ingress or egress queues
  • monad-wireauth turns one UDP path into an authenticated session with replay defense
  • monad-leanudp fragments large direct UDP messages
  • monad-peer-discovery maintains the peer table and role awareness
  • monad-peer-score and monad-fair-queue decide who gets priority
  • monad-raptorcast and monad-router-multi turn router commands into concrete delivery behavior

Three acronyms show up throughout this chapter:

  • TCP (Transmission Control Protocol) is the ordered, reliable, connection-oriented transport that retransmits lost packets on your behalf. If you need every byte delivered in order, TCP is the easy answer.
  • UDP (User Datagram Protocol) is the unordered, unreliable, connectionless transport that just sends datagrams and forgets them. It is smaller and faster, but delivery guarantees are whatever you build on top.
  • P2P (peer-to-peer) means nodes speak directly to each other rather than through a central server. Every validator is simultaneously a client and a server for its peers.

This chapter walks that stack from the bottom up.

Why This Chapter Matters#

Many networking bugs get described as “the network is flaky,” “consensus is slow,” or “peers are missing messages.” Those descriptions are too vague to be useful. The real questions are more specific:

  • did the node bind the right socket?
  • did discovery trust that peer yet?
  • did authenticated UDP succeed?
  • did the message take the primary validator path or the secondary full-node path?
  • did direct UDP work, or did it need a different delivery path?
  • did local queueing or peer scoring deprioritize that traffic?

Monad’s networking code stays understandable largely because it keeps those questions in separate layers.

10.2 Monad Uses Several Delivery Shapes, Not Just “TCP And UDP”#

If you ask only “does Monad use TCP or UDP?”, you lose the important part of the design. The code really distinguishes delivery shapes.

Delivery shapeTypical useWhy that shape exists
framed TCPreliable ordered point-to-point trafficcorrectness matters more than minimum latency
authenticated UDPvalidator traffic that wants low latency but still needs identity and replay defensefast authenticated peer-to-peer delivery
direct UDP with fragmentationlarge direct one-to-one messagesavoid one-datagram size limits without giving up the direct UDP path
raptor broadcastvalidator one-to-many disseminationmake broadcast efficient and resilient
secondary raptor fanoutvalidator-to-full-node distributionlet full nodes follow live validator traffic without pretending they are validators

Raptor broadcast (named after the RaptorQ-family of rateless fountain erasure codes) is the idea of slicing a large payload into many small encoded chunks such that receiving any sufficient subset reconstructs the original — so the sender can send chunks to many peers in parallel and each receiver keeps listening only until it has gathered enough. In Monad this is the backbone of efficient validator-to-validator block dissemination.

So the right summary is not “Monad uses TCP and UDP.” It is “Monad uses different transport shapes for different jobs.”

10.3 monad-dataplane Owns The Real Sockets#

monad-dataplane is where networking stops being abstract and becomes operating-system I/O. The router stack pulls out concrete sockets such as TcpSocketId::Raptorcast, UdpSocketId::Raptorcast, UdpSocketId::AuthenticatedRaptorcast, and UdpSocketId::DirectUdp. That is already visible in build_raptorcast_router(...) and MultiRouter::new(...).

This is a useful fact to internalize early: different logical traffic classes really do have different sockets, and that makes later transport decisions much less mysterious.

What monad-dataplane Actually Adds#

It is not just “open socket, read bytes, write bytes.” It also owns connection limits, rate limiting, pacing, trusted or banned address handling, TCP listeners and outbound connections, and UDP ingress and egress queues. So when a message “fails at the network layer,” the bug may still be below peer discovery or consensus entirely.

10.4 TCP And UDP Mean Different Things In This Codebase#

TCP#

TCP is used when Monad wants ordered delivery, reliable delivery, and normal point-to-point stream semantics. Monad still adds message framing above TCP so higher layers see discrete messages instead of one endless byte stream.

UDP#

UDP is used when Monad wants lower latency, tighter control over packet handling, broadcast-friendly behavior, or more customized session rules than stock TCP gives. But raw UDP is not enough on its own. Above UDP, Monad adds WireAuth for authenticated sessions, LeanUDP for fragmentation and reassembly of large direct messages, and raptor-style broadcast logic for validator dissemination. So “UDP” in Monad really means UDP plus protocol-specific structure.

10.5 monad-wireauth Gives One UDP Path Identity, Encryption, And Replay Defense#

Raw UDP does not answer several questions consensus needs answered: who really sent this, can the sender actually receive replies at that address, is this packet old or replayed, and can a spoofed flood force the receiver to do too much work? monad-wireauth is the answer to those questions.

What It Adds#

At a high level, it adds a handshake, encrypted authenticated packets after the handshake, cookie-based proof of return reachability under load, and counter-based replay filtering.

Why Cookies Matter#

The cookie challenge is not a side detail. It is a cheap anti-spoofing defense. Under pressure, the responder can require the initiator to come back with a valid cookie before spending more effort — that shifts work back onto the claimant and proves the source can actually receive replies.

Why Replay Filtering Matters#

Once a session is live, the receiver still has to reject duplicate counters and counters outside the replay window. That is why monad-wireauth has an explicit replay filter rather than trusting the network to never duplicate or reorder packets.

10.6 monad-leanudp Exists For Large Direct Messages#

Raptor broadcast and direct peer-to-peer delivery are not the same problem. monad-leanudp is for the direct side. When one logical direct message is too large for one datagram, LeanUDP handles fragmentation, fragment transmission, reassembly, and cleanup of incomplete or abusive state. That is different from the primary raptor broadcast path.

A useful distinction is that LeanUDP is one message split for one receiver, while raptor broadcast is one message family encoded for one-to-many dissemination. If you merge those into one concept, the router code becomes harder to read.

10.7 Discovery Is About Trustworthy Peer Tables, Not About Consensus Logic#

monad-peer-discovery does not validate blocks or choose leaders. Its job is simpler and more operational: learn who peers claim to be, decide when to trust that network identity enough to route traffic, keep track of current and next-epoch validator needs, and coordinate validator-to-full-node publisher or client relationships.

NameRecord Is The Core Identity Object#

The signed NameRecord carries an IPv4 address, a TCP port, a UDP port, an authenticated UDP port, an optional direct UDP port, capability bits, and a monotonically increasing sequence number. A signed record says “this node identity claims these addresses and ports.” That is enough to advertise a location. It is not enough yet to trust it.

Discovery Prefers Pending First, Trusted Later#

New peers do not go straight into the active routing table. They first enter pending_queue, discovery sends a Ping, and only after a successful ping or pong roundtrip does the peer move into routing_info. That design separates signed self-description from proven reachability — one of the clearest places where Monad prefers a stronger peer table over faster admission.

Sequence Numbers Prevent Name-Record Rollback#

Discovery also refuses to regress to an older name record. If the node already knows a same-or-newer record for that peer, lower-sequence updates are ignored. So peer identity is not “latest packet wins” — it is “newer signed record wins, once reachability and table rules are satisfied.”

Socket-Collision Handling Protects Identity Coherency#

Peer discovery keeps a socket-to-identity map and does not casually accept two different node identities claiming the same UDP address story. That is why socket collisions are treated as a real defense event rather than a bookkeeping oddity. The invariant is that identity, socket address, and trusted routing entry should all line up.

10.8 Discovery Tracks Current And Next-Epoch Validator Needs#

Peer discovery is not only maintaining a generic peer graph. It is explicitly aware of current-epoch validators and next-epoch validators. That matters because a node can need a peer for protocol reasons before that peer is just one more neighbor.

During refresh, discovery looks for missing validators from both current_epoch and current_epoch + 1, chooses peers to query, and can send targeted lookup requests for those missing validators. So discovery is not passive gossip — it is an active search for the identities consensus will soon need.

10.9 Full Nodes And Validators Do Not Share The Same Networking Role#

The discovery layer has explicit role states such as ValidatorPublisher, ValidatorNone, FullNodeClient, and FullNodeNone. That is the first sign that Monad does not treat “full node = validator minus a few permissions.” From a networking perspective, the roles really do differ.

Secondary Raptorcast Is The Full-Node Distribution Path#

The primary validator router is not the whole live dissemination story. Monad also has a secondary raptorcast path for validator-to-full-node distribution. A full node running in client mode can request a downstream connection to a validator publisher, and the validator can accept or refuse based on whether it is actually in publisher mode, whether group size is already full, and whether the requester is prioritized or ordinary. The connection state is tracked explicitly as None, Pending, or Connected — a real protocol inside peer discovery, not a convenience flag.

Participation Matters After Connection Too#

Even after a full node is connected, discovery keeps participation_info with fields like status, retry count, and last active round. That lets the node prune or reset stale secondary connections rather than letting dead downstream relationships linger forever.

10.10 Epoch Changes Can Change Networking Role Before They Change Traffic#

One subtle but important detail is that discovery reacts to validator-set updates, not just to message traffic. When a full node becomes a validator in the current epoch, its role can flip from full-node mode into validator mode. When a full node is about to become a validator in the next epoch, it can proactively ping next-epoch validators to advertise its fresh name record. When a validator is going to be demoted, it can move toward full-node behavior instead of pretending nothing changed until the last second. That is a good example of networking serving consensus timing rather than only reacting after the fact.

10.11 Peer Score And Fair Queue Are Delivery Policy, Not Consensus Rules#

Once a node has peers and transports, it still has to decide who should get bandwidth first, who is currently behaving well, and who should be deprioritized. That is where monad-peer-score and monad-fair-queue come in.

monad-peer-score#

monad-peer-score maintains a smoothed identity score. The smoothing is an EMA (exponentially weighted moving average), a running average in which newer samples carry more weight than older ones. Each new observation nudges the score toward its value, and older observations decay exponentially. The important idea is not one exact formula but that peer reputation changes over time, short-term blips should not dominate forever, and routing and forwarding can use that score without pushing consensus logic into the networking crate.

monad-fair-queue#

monad-fair-queue then splits bandwidth between competing queues so one traffic class or one peer cannot monopolize local resources too easily.

These crates matter because production networking bugs are often not “the packet format is wrong.” They are “the wrong peers or queues are getting starved.”

10.12 MultiRouter Combines Primary Validator Routing With Optional Secondary Full-Node Routing#

monad-router-multi is the easiest place to see final router assembly. MultiRouter owns one primary RaptorCast instance, an optional secondary RaptorCastSecondary instance, shared peer discovery state, and the epoch and validator-set awareness needed to flip roles.

A key design detail is that the primary and secondary instances share peer discovery, but only the primary owns the actual dataplane sockets. That is why MultiRouter creates explicit channels between the two instances for group messages from primary to secondary, group-assignment info from secondary back to primary, and outbound secondary traffic forwarded back through the primary. That is a very concrete design choice — the secondary router is not a second independent network stack, it is a secondary dissemination role layered on top of the primary stack.

10.13 Router Commands Are Higher-Level Than Socket Calls#

Consensus and discovery do not talk in terms of “send this byte array on this file descriptor.” They emit higher-level router commands, and then the router layer decides target identity, delivery shape, whether authenticated UDP is available, whether direct UDP can be used, and whether the traffic belongs on the primary or secondary path. That is why RouterCommand is an important seam in the code — it is the boundary between protocol intent and transport mechanics.

10.14 A Good Inbound Mental Model#

When a packet arrives, the useful bottom-up model is:

  1. monad-dataplane receives bytes on a concrete socket
  2. the socket role determines which higher transport logic sees the bytes
  3. authenticated UDP traffic goes through wireauth session validation
  4. direct fragmented traffic may go through LeanUDP reassembly
  5. raptorcast decodes or reconstructs higher-level messages
  6. peer discovery may update peer-table state
  7. validated protocol messages emerge as router events for the node

That model is much better than imagining that packets somehow become consensus messages. There are several explicit gates in between.

10.15 How To Debug Networking Without Getting Lost#

When networking goes wrong, start with these questions in order:

  1. Is this the primary validator path, the secondary full-node path, or a direct point-to-point path?
  2. Which socket should this traffic use: TCP, authenticated UDP, normal UDP, or direct UDP?
  3. Has peer discovery actually promoted the peer from pending_queue into routing_info?
  4. Is the node in the role that would accept or originate this traffic right now?
  5. Did authentication or replay filtering reject the packet before consensus ever saw it?
  6. Is the peer being deprioritized by local scoring or queueing?

Those questions match the code structure. That is why they work better than staring at consensus logs first.

10.16 Architecture, Current Code, Current Caveat#

Architecture Networking is a layered delivery stack: sockets and queues at the bottom, authenticated transport above that, discovery and role awareness above that, and routing policy above that.

Current code MultiRouter combines one primary validator RaptorCast path with an optional secondary full-node dissemination path, while peer discovery supplies the role and peer-table state both of them depend on.

Current caveat The primary and secondary paths are not two independent network stacks. They share peer discovery, and only the primary path owns the underlying dataplane sockets in this checkout.
