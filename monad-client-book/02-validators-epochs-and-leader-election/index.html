Chapter 2: Validators, Epochs, and Leader Election

monad-client-book/02-validators-epochs-and-leader-election.md View source →

Chapter 1 gave us the nouns. This chapter answers two practical questions: who is allowed to act right now, and who is expected to lead this round? Those answers are not hard-coded. They come from validator sets, locked epochs, execution-backed staking reads, epoch scheduling, and deterministic leader election.

Why This Chapter Matters#

The easiest way to misunderstand Monad consensus is to imagine that validator membership changes at one clean instant. The current code is more exact than that: there are distinct moments for locking the next epoch, reading the next validator data, scheduling the start round, and activating the new validator set. If you blur those into one instant, later pacemaker and recovery code becomes much harder to trust.

2.1 What Consensus Actually Needs From A Validator Set#

Consensus does not need “a list of validators” in the abstract. It needs stake-weighted answers to concrete questions:

  • is this node a member?
  • what is the total stake?
  • how much stake signed this statement?
  • has a supermajority threshold been crossed? — meaning has at least 2/3 * total_stake + 1 of the stake signed, the standard Byzantine fault tolerance bar for agreement
  • has the honest threshold been crossed? — meaning has at least 1/3 * total_stake + 1 of the stake signed, which guarantees at least one honest validator is among the signers even if up to one-third of the stake is Byzantine

That interface lives behind ValidatorSetType, the Rust trait (a set of required methods) that concrete validator-set types must implement. Think of it as the contract saying “any type that claims to be a validator set must answer these questions.” At a reader level, the important thing is not the trait name — it is the list of questions the trait exists to answer, because that list tells you what consensus really depends on.

2.2 Creation Invariants#

The default ValidatorSet is simple on purpose: a map from NodeId to Stake, plus cached total stake. The constructor enforces a few invariants early — the set cannot be empty, zero-stake validators are rejected, and duplicate validators are rejected — which is why later code gets to assume it is working with a sane set.

The threshold formulas are exactly what the code says: the supermajority bar is 2/3 * total_stake + 1, and the honest threshold is 1/3 * total_stake + 1. Signer-stake calculation rejects duplicate signers before summing, so one validator does not get to increase influence by appearing twice.

2.3 Identity Versus Certificate Key, Again#

This distinction becomes operational here, not just theoretical. Consensus needs two related answers: which validator is this, and which key verifies this validator’s certificate contribution? That is why validator identity and certificate-verification keys are modeled separately — NodeId answers the first question, and ValidatorMapping answers the second.

This matters in production because the current intuition is that validator identity is secp-shaped while certificate verification is BLS-shaped. So a later QC, TC, or NEC verification step needs both the validator set (for stake accounting) and the validator mapping (for certificate verification).

2.4 Before Staking Activation Versus After#

Staking activation is a configured epoch number in MonadChainConfig that marks when validator data starts coming from execution-side staking state instead of static node config. Before this epoch, the set is fixed at launch; after it, validators are determined by stake recorded in the staking contract.

The validator-set lifecycle has two regimes.

Before Staking Activation#

Before the locked epoch reaches staking_activation, the next validator data comes from config. That is still deterministic; it is just not yet execution-backed.

After Staking Activation#

After the locked epoch reaches staking_activation, the next validator data comes from execution-backed staking state. That is where the repo boundary becomes real: consensus in monad-bft needs the next validator set, execution-owned staking state in monad provides it, and the bridge between them is a dedicated validator-set read path rather than a generic “read arbitrary contract storage” hack.

2.5 The Three Important Validator Views On The Execution Side#

Once staking activation is live, consensus does not read one giant undifferentiated validator blob from execution.

The execution side exposes more than one useful view:

ViewWhat it meansWhy it exists
execution viewexecution-side validator data such as keys and contract-owned metadataexecution needs the live contract state
consensus viewthe stake-ordered set that consensus should use for the next admissible epoch readconsensus needs a cleaned-up selection view
snapshot viewthe frozen current-epoch view used during the epoch-delay windowcurrent-epoch reads must stay stable while the next epoch is being prepared

That split is why the validator-set reader feels narrower than a generic contract read. It is not trying to expose every staking detail; it is trying to expose the exact validator views consensus needs.

2.6 read_valset(...) Is Deliberately Narrow#

read_valset(db, block_num, requested_epoch) is the execution-side C++ function that exposes validator-set data to consensus. It is the one formal bridge where the consensus world asks the execution world “who are the validators for this epoch?” and gets back a concrete set. The current implementation is stricter than first readers usually expect: requesting the current epoch returns the current admissible view; requesting the next epoch only works during the delay-period window; and requesting an older or too-far-future epoch returns nullopt.

That means the bridge is intentionally not “read any epoch you want whenever you want.” It is “read the current or next admissible consensus-facing validator data at the right block boundary.” This is one of the biggest “trust the code, not your first intuition” places in the whole client.

2.7 A Full Boundary-Block Example#

Suppose epoch_length = 4, execution delay around the staking contract creates a boundary-delay window, blocks 0, 1, 2, and 3 belong to epoch 1, and block 3 finalizes. Then the faithful story is:

  1. block 3 is still in epoch 1
  2. block 3 locks epoch 2
  3. consensus now knows which future epoch number it is preparing for
  4. if staking activation is live, execution-backed validator data for epoch 2 becomes the next thing consensus wants to read
  5. that read is only admissible in the correct window
  6. EpochManager schedules the round at which epoch 2 actually becomes active
  7. only when that round arrives does epoch 2 become the live validator set

This is more faithful than the shortcut “epochs change at block boundaries.” They do not. Boundary blocks lock the next epoch; activation happens later in round-space.

2.8 The Most Useful read_valset(...) Table#

The execution-side tests make the behavior especially clear:

SituationRequest current epochRequest next epoch
before boundary delay windowcurrent epoch reads the normal current consensus-facing viewrejected
during boundary delay windowcurrent epoch reads the frozen snapshot-style current viewnext epoch reads the prepared consensus-facing next view

That table is one of the most useful validator-set facts in the whole codebase. It explains why consensus-side validator updates need both the correct block number and the correct epoch context.

2.9 EpochManager Turns Block Events Into Round Activation#

EpochManager is the bridge between block events and round activation. At a reader level, it owns three ideas:

  • epoch_length: how many sequence numbers make up an epoch interval
  • epoch_start_delay: how many rounds after the boundary the next epoch activates
  • epoch_starts: the concrete schedule from epoch number to start round

This is the type that turns “block B locked epoch E + 1” into “epoch E + 1 becomes active at round R.” That translation is the reason proposal and timeout handlers later ask “what epoch is active at this round?” instead of “what sequence number are we near?“

2.10 The Lock -> Read -> Schedule -> Activate Lifecycle#

This is the core lifecycle of epochs in current code.

flowchart LR
    Boundary["finalized boundary block"] --> Lock["lock epoch E+1"]
    Lock --> Read["load validator data for E+1"]
    Read --> Schedule["schedule start round for E+1"]
    Schedule --> Activate["pacemaker reaches scheduled round"]
    Activate --> Live["epoch E+1 becomes active"]

Each step solves a different problem:

StepWhat becomes true
lockthe next epoch’s validator data is determined
readthe node has the next validator set and certificate mapping in memory
schedulethe exact activation round is known
activateconsensus starts using the new set

This is why Monad needs both block-space reasoning and round-space reasoning.

2.11 Leader Election In Current Code#

Every round needs an expected proposer. Consensus only wants a deterministic answer to one question: for this round and this validator set, who should lead? Determinism is the non-negotiable property. If honest nodes derive different leaders from the same inputs, the rest of the protocol falls apart immediately.

2.12 Why WeightedRoundRobin Does Not Look Like Classical Round Robin#

The production-sounding name can mislead readers. The current implementation is not a literal circular list with validators repeated by stake. In the checked-out code, WeightedRoundRobin does this:

  1. seed ChaCha20Rng — a cryptographically-seeded pseudo-random number generator based on the ChaCha20 stream cipher, which means the same seed always produces the same output sequence — from the round number
  2. sample a value in [0, total_stake)
  3. walk cumulative stake bounds
  4. choose the validator whose stake interval covers the sampled value

So the current implementation is best described as deterministic stake-weighted sampling keyed by round, not naive cyclic round robin. The historical name stays because the job is still “stake-weighted repeated leader selection over rounds” — the modern implementation just does that with deterministic sampling rather than a crude repeated-list schedule.

2.13 Where Leader Election Gets Checked#

Leader election is not only used when the local node decides to propose. It is also used to validate whether an incoming proposal author matches the expected leader for proposal_round, whether the block author matches the expected leader for block_round, which node should receive point-to-point votes, and whether the local node is allowed to emit a proposal at all.

That last point matters: leader election is both a receiving-side validation rule and a local self-discipline rule.

2.14 Two Kinds Of Determinism#

This chapter is also a good place to separate two ideas that later chapters rely on. Validator selection must be globally deterministic, while proposal contents do not need to be globally identical on every node. Leader election belongs in the first bucket; txpool proposal construction belongs in the second. That distinction becomes important in Chapter 9.

2.15 Architecture, Current Code, Current Caveat#

Architecture Epoch changes are multi-step: lock next epoch, load validator data, schedule the start round, then activate it.

Current code After staking activation, validator data comes from execution-backed staking state through a dedicated read_valset(...) path with strict epoch admissibility.

Current caveat The validator-set recheck on live rejoin is real, but the checked-out code still carries a TODO around which sequence number should be used for that recheck path. Chapter 5 comes back to that.

What To Remember#

  • Validator sets are stake-weighted maps with strong creation invariants.
  • Validator identity and certificate-verification keys are related but distinct roles.
  • A finalized boundary block locks the next epoch; it does not activate it immediately.
  • read_valset(...) is deliberately narrow and epoch-admissibility constrained.
  • EpochManager schedules epoch activation in round-space.
  • The current leader-election implementation is deterministic stake-weighted sampling keyed by round.
